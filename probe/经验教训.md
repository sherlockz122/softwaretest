## A. 数据源：先想清楚"谁写的、写的算什么"

### A1. 机器人提交必须排除

**现象**：ActiveMQ 2026 年有 437 条提交，其中 `dependabot[bot]` 占 175 条（40%）；全仓 377 条（2.3%）。

**问题**：`build(deps): bump xxx from A to B` 只改一个版本号字符串，**永远不可能是缺陷引入提交**。但会以"超小改动"的样子进入特征矩阵，把低风险样本稀释掉。

**做法**：作者名含 `[bot]` / `dependabot` / `renovate` / `github-actions` 一律排除。

### A2. 同一个人有多个身份 —— 必须归一化

**现象**：ActiveMQ 有 **224 种姓名写法，实际只有 206 个人**。

| 类型 | 例子 |
|---|---|
| 中间名缩写 | `Timothy A. Bish` vs `Timothy Bish` |
| 词序颠倒 | `Bosanac Dejan` vs `Dejan Bosanac` |
| 昵称 + 用户名 | `JB Onofré` / `Jean-Baptiste Onofré` / `jbonofre` |
| 用户名 | `Gary Tully` vs `gtully` |

**问题**：Kamei 的 `EXP` / `REXP` / `SEXP` 全靠开发者身份。不归一化，同一人的经验被拆散，**特征系统性偏低**。

**做法**：并查集 —— **共享邮箱 或 共享归一化姓名 → 判为同一人**。
归一化姓名 = 去括号后缀 + 丢单个字母 + 词排序。

**残留**：`Robert Davies` / `Rob Davies` 这类**昵称**要人工别名表，脚本抓不到。

### A3. 提交数有两种口径，别混

| 口径 | commons-cli | activemq | 用不用 |
|---|---|---|---|
| 默认分支 `rev-list --count HEAD` | 2,257 | **12,600** | ✅ 产品只用这个 |
| 全分支 `--all` | 2,325 | 16,378 | ❌ 含发布分支 |

**"可算特征 ≠ 非合并提交"**：合并提交天然没有 diff，已经含在"无 diff"里，**不要重复扣减**（这是真踩过的坑）。

## B. 标注算法：每个假设都要验

### B1. fix 正则要逐词验伪，不能凭感觉

| 词 | 只被它命中 | 判决 | 依据 |
|---|---|---|---|
| `fix` | 2,838 | ✅ 留 | — |
| `bug` | 25 | ✅ 留 | — |
| **`patch`** | 462 | ✅ **留** | 550 条样本人工核对**全是真修复**（`[AMQ-7126] Prevent OOM...`） |
| `resolve` | 290 | ❌ 删 | 混入 `resolve build warnings` |
| `close` | 153 | ❌ 删 | 混入 `Close to compiling` |
| `defect` | **0** | ❌ | 本仓库一次都没出现 |

**定案**：`\b(fix(e[sd])?|bug|patch|defect)\b` → fix 占比 23.6%（文献 15%~30%）

> **交叉验证**：Kamei 2013 原文 Purpose 维度用的关键词就是 **`bug, fix, defect, patch`** —— 和我们的规则**完全一致**。

**别被表象骗了**：`Merge pull request #1359 from coheigea/patch-1` 里的 `patch-1` 是 **GitHub 网页改文件的默认分支名**，不是补丁。但它在**合并提交**里，排除合并后自然消失（实测 0 条）。

### B2. 标注对正则选择不敏感（正面结论）

| | 松正则 | 规则 C |
|---|---|---|
| fix 提交数 | 399 | **233（−42%）** |
| **缺陷引入率** | 9.9% | **9.6%** |

**fix 数掉 42%，缺陷引入率只动 0.3 个百分点。** 松正则多抓的 fix，大多 blame 到同一批引入提交。

### B3. `git blame` 默认输出**缩写 sha** —— 这是最坑的一个

**症状**：SZZ 命中数直接是 **0**，而且**一声不吭**（四个计数全是 0，看不出哪里错）。

**原因**：`git blame` 默认给 7~8 位缩写 sha，而我们建映射表用的是 `git log --format=%H` 的**完整 40 位**。`字典.get(缩写)` 永远查不到。

**修法**：
1. 用 `git blame --porcelain` 强制拿完整 sha
2. 拿到后**硬校验 40 位，不是就抛异常**

**更重要的教训**：**任何跳过路径都要有计数器，禁止静默 `continue`**。
加的 `TS 未命中` 计数器如果一开始就有，这个 bug 第一次跑就暴露了。

### B4. 统计口径必须"按引入提交去重"

**现象**：commons-cli 上 **2,886 条代码删除行只对应 171 个引入提交（17 : 1）**。

**问题**：一个批量提交（许可证头更新）删 500 行，这些行**全 blame 到同一个老提交** → 产生 500 个完全相同的"bug 存活时间" → 分布里出现**假尖峰**（实测 417 条挤在 15 天里）。

**做法**：按引入提交去重，**取最早一次修复**。

### B5. 合并提交：不是"没改动"，是"改动属于别人"

**准确说法**：合并提交**自己不产生代码改动**——改动来自被合并分支上的提交，而那些提交本来就在历史里、各自会成为样本。**排除合并是避免重复计数，不是丢数据。**

**工程上的硬理由**：合并提交有两个父提交，**git 无法定义"合并提交的 diff"**。PyDriller 实测返回空（5 个合并提交，`modified_files` 全是 0）。

**占比**：commons-cli 53（2.3%）、ActiveMQ 825（6.5%）

**已知盲区**：**冲突解决时写进合并提交的代码会被漏掉**。

## C. 时间窗口：这里有两个不同的"窗口"，别混

### C1. 数据窗口 vs 标签观察窗口

| | 是什么 | ActiveMQ 取值 |
|---|---|---|
| **数据窗口** | 数据集覆盖哪一段时间 | **2013-01-01 ~ 今天**（6,028 条） |
| **标签观察窗口** | 窗口**末尾**留多久不打标签 | **24 个月** |

**"暖机期"的准确含义**：不是丢掉历史，而是"**历史照算特征，只把窗口内的提交放进数据集**"。`age` / `exp` / `rexp` 都要靠历史才算得出来。

### C2. ⚠️ 同期群（cohort）口径 —— 最隐蔽的坑

**问题**：blame 会追到数据窗口**之前**的提交。如果 fix 也只扫到窗口末尾，那么窗口前引入的 BIC，**它真正的首次修复落在扫描范围外**，我们就会记成更晚的一次修复 → **gap 被系统性拉长**。

**证据**：

| | 修正前 | 修正后 |
|---|---|---|
| 6 个月覆盖率 | 27.7% | **44.6%** |

**做法**：**fix 一直扫到今天**（`TO=None`），但**统计时只保留 `引入时间 ≥ SINCE` 的 BIC**。

### C3. 观察窗口**不是常数**，必须按仓库实测

| 窗口 | commons-cli | activemq |
|---|---|---|
| 6 个月 | **67.1%** ← 拐点 | 43.7% |
| 12 个月 | 73.1% | 54.3% |
| **24 个月** | 80.2% | **68.1%** ← 拐点 |
| 36 个月 | 84.4% | 73.9% |

**两个仓库差 4 倍。** 原因：ActiveMQ 有 25,207 个文件，改到冷门文件的 bug 能躺好几年；commons-cli 小而活跃，改完很快就修。

**定窗口的方法**：算**边际收益 vs 数据成本**
- ActiveMQ：18→24 个月是 **+1.02 点/月**，24→36 个月降到 **+0.48 点/月**，而数据成本恒为约 39 条/月 → **拐点在 24 个月**

## D. 度量与数据质量

### D1. 测试代码会大量进数据集

**实测 ActiveMQ**：

| 口径 | 数值 |
|---|---|
| **只改测试文件**的 BIC | **22.2%** |
| 碰过测试文件的 BIC | **76.2%** |
| 改动行数里测试相关的 | **约 67%** |
| 改动行数里主代码的 | 26.2% |

**原因**：ActiveMQ 的标准做法是"**改代码 + 带测试**"，fix 提交删掉的行里混着大量测试行，blame 回去就落在"写那行测试的提交"上。

**做法**：给每条 BIC 打 `is_test` 标记（方案 B），训练时可分层或排除。

### D2. 非语义行过滤：先量，别假设

| 类别 | 剔除比例 | 结论 |
|---|---|---|
| 注释 / 空行 | 30.8%（commons-cli） | ✅ 有效——被剔除组的 P75 是保留组的 2.7 倍，确实是噪声 |
| **`import` / `package`** | +6.1% | ⚠️ **实测无影响**（覆盖率差 <1 点），但方法上正确，保留 |

**我原以为 import 是主要污染源，实测不是。** 假设要用数据验。

### D3. `<1 天` 间隔要人工抽查

**现象**：提交级代码行组里 **8.8%（91 条）**的 bug"存活时间"不到 1 天。

**抽查 12 条结果**：**真阳性 7 条（58%）**、可疑 4 条、无法判 1 条。

**主要误报类别**：① 只改测试文件的提交；② `fix typo` / `fix formatting` 这类**非缺陷修复**。

**`fix typo/format` 有多少？全仓只有 39 条**（占 fix 总数 1.1%）→ **不值得为它改规则**。

**为什么这一步重要**：其他所有数字都是脚本算的，**只有这条是人工核对的**。

## E. 工程与测量

### E1. 同一任务两次跑，耗时差 29%

```
SZZ（1,337 fix / 31,852 行）：3,764.9 s  vs  4,847.6 s
```

**所有耗时数字必须注明是哪一次。**

### E2. 混合架构：分片数按性能核，不按逻辑核

Intel Core Ultra 7 155H = **6 性能核 + 8 能效核 + 2 低功耗核 = 16 核 22 线程**。

按 22 开进程，**调度到能效核的分片会慢数倍，拖累整体的永远是最慢那个**。
→ **分片数 = 6**。而且要实测加速比，**不能按 6 倍硬算**。

### E3. 线性成立才能外推

```
200 条   → 158.7 ms/条（含预热）
500 条   → 126.7 ms/条
1000 条  → 128.7 ms/条
2000 条  → 133.4 ms/条      ← 稳定，可以外推
```

→ 12,600 条约 **28 分钟**（单进程）。

### E4. 一次性索引成本极低，别怕建

建 `sha→时间` 映射 **0.25 s**；建文件历史索引（25,207 文件 / 150,742 条记录）**1.42 s**。
→ `NUC` / `NDEV` / `AGE` 这三个"看起来要查历史"的特征，成本可以忽略。
