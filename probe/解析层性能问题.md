# 解析层性能问题：每提交 26 次 git 子进程，比特征内核慢 28 倍

**发现于**：探针参数实测（Sprint 0 技术探针收尾）
**日期**：2026-10-19
**提出**：李展鸿
**涉及模块**：`packages/repositories/parser.py`（`NativeReader`）
**相关决策**：`docs/decisions/2026-10-19-探针参数决策.md` §4.1.2

---

## 1. 摘要

在 ActiveMQ（12,600 个提交，平均 6.22 文件/提交）上跑 `scripts/probe_causal_features.py`：

| 规模 | 结果 |
|---|---|
| **100 提交** | 成功，**134 秒**（1.34 秒/提交） |
| 200 提交 | `REPOSITORY_PARSE_TIMEOUT` |
| 1,000 提交 | `REPOSITORY_PARSE_TIMEOUT` |

按 1.34 秒/提交线性外推：

| 规模 | 端到端预计 |
|---|---|
| 1,000 提交 | 约 22 分钟 |
| **1,340 提交** | **约 30 分钟** |
| 12,600 提交（全仓） | 约 **4.7 小时** |

**同一份特征内核单独压测，全仓只要 586.7 秒（9 分 47 秒）。** 差距 28 倍，耗时几乎全在解析阶段。

## 2. 瓶颈不在特征内核

用 `probe/probe_real.py` 直接调用 `packages.mining.features` 的 `compute()`，跳过解析阶段：

| 阶段 | 每提交耗时 | 全仓 12,600 提交 |
|---|---|---|
| 特征内核 `features.compute()` | **0.047 秒** | **586.7 秒（9 分 47 秒）** |
| 端到端（含解析） | **1.34 秒** | 约 **4.7 小时** |
| 差距 | **28 倍** | — |

内核耗时随规模呈 **1.71 次方**增长（低于平方），实测 6 个规模点：200 / 500 / 1,000 / 2,000 / 5,000 / 12,600 提交 =
0.490 / 1.672 / 7.562 / 22.063 / 113.135 / 586.736 秒。

**所以优化特征内核收益很小，优化解析收益很大。**

## 3. 定位

### 3.1 `blob()`：每个 blob 起两个子进程

`packages/repositories/parser.py:152-156`

```python
def blob(self, sha, mode):
    if set(sha) == {"0"} or mode == "160000":
        return b""
    size = int(self.command(["cat-file", "-s", sha]).strip())            # 子进程 1
    return None if size > BLOB_LIMIT else self.command(["cat-file", "blob", sha], BLOB_LIMIT)  # 子进程 2
```

先单独查大小，再单独取内容——两次进程创建。

### 3.2 `files()`：每个文件读新旧两个 blob

`packages/repositories/parser.py:245`

```python
old_content, new_content = self.blob(old_blob, old_mode), self.blob(new_blob, new_mode)
```

→ **每文件 2 个 blob × 2 次调用 = 4 次子进程**

### 3.3 `record()`：每个提交再一次

`packages/repositories/parser.py:159`

```python
raw = self.command(["cat-file", "commit", sha])
```

### 3.4 合计

```
每提交子进程数 = 1 + 文件数 × 4
ActiveMQ 平均 6.22 文件/提交  →  1 + 6.22 × 4 ≈ 26 次
实测 1.34 秒/提交 ÷ 26 ≈ 每次子进程 52 ms
```

52 ms 与 Windows 上的进程创建开销量级一致。

### 3.5 第二层放大：`command()` 的轮询与磁盘检查

`packages/repositories/parser.py:88-124`

```python
output, errors = self.attempt / "parse.out", self.attempt / "parse.err"
with output.open("wb") as stdout, errors.open("wb") as stderr:
    process = subprocess.Popen(...)
    while True:
        self.tick()                              # 内含 shutil.disk_usage 磁盘检查
        if time.monotonic() >= self.deadline:
            raise RepositoryError(422, "REPOSITORY_PARSE_TIMEOUT")
        if errors.stat().st_size > 65536: ...
        if output.stat().st_size > limit: ...
        if process.poll() is not None:
            break
        time.sleep(0.02)                         # 20 ms 粒度空转
```

每次 git 调用都额外叠加：

- 两次文件重定向（`parse.out` / `parse.err`）
- **20 ms 粒度的轮询空转**
- **每轮一次 `tick()`**，而 `tick()` 里有 `shutil.disk_usage(ROOT)` 磁盘统计

## 4. 建议（按收益排序）

| # | 改法 | 预期效果 |
|---|---|---|
| **1** | `blob()` / `record()` 改用 **`git cat-file --batch`** 常驻进程，流式发送请求 | 每提交 26 次子进程 → **1 次**，最大收益 |
| 2 | 轮询换 `process.wait()` | 去掉 20 ms 粒度空转 |
| 3 | `tick()` 中 `disk_usage` 降频（如每 64 次调用查一次） | 去掉每次子进程的磁盘统计 |

按收益估算，第 1 条单独落地就能把端到端从 1.34 秒/提交降到 0.1 秒量级。

> 改动属产品代码。按 `AGENTS.md`，应先在 `openspec/changes/` 建立场景与任务，再动实现。

## 5. 一个必须先确认的前提

仓库里另有 `packages/mining/feature_reads.py` 与 `packages/mining/indexed_features.py`（v2 文件历史索引）。

- 本报告的数字不代表生产耗时，需要按 v2 重新测量
- 但若 v2 内部同样是逐 blob 起子进程，问题依然存在，只是被其他优化掩盖

**建议先由王凯确认生产路径，再决定优化对象。**

## 7. 影响

1. **直接改变「输入上限」这个参数**：按端到端口径，30 分钟只能处理 **约 1,300 个提交**；而按内核口径可以到 24,000。两者差 18 倍，参数应以端到端为准。
2. **ActiveMQ 全仓（12,600 提交）端到端需要约 4.7 小时**，远超单任务 30 分钟的预算。
3. 在解析优化落地前，**任何大仓库的端到端跑批都不可行**，只能靠缩小窗口。
