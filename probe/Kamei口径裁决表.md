## 3. 三处争议，逐条给判断

### 3.1 Entropy 是否归一化 —— 建议**保留归一化**

| 方向 | 证据 |
|---|---|
| **支持归一化** | ① 正文显式声明"has been normalized by the maximum Entropy log₂n **to account for differences in the number of files across changes**"；② 归一化的目的正是消掉"文件数"混杂——**不归一化时 10 文件提交天然比 2 文件提交熵高**；③ 算例 `1.46` 只是在演示 `H(P)` 本身 |
| **支持不归一化** | ① 同一段的算例给的是 **1.46**（n=3 归一化应为 0.92），正文自相矛盾；② 论文**完全没讨论 n=1 时 `log₂1=0` 的除零**，而单文件提交是最常见情形之一，作者不可能不处理；③ 第三方复现普遍未归一化（Ng & Cheng 2021 在 Trac 上报告 entropy 均值 **1.2246**、标准差 2.0082，值域明显 >1） |

**判断**：**保留归一化**。显式声明 + 明确目的 > 算例推断；n=1 已由内核特判为 0 解决；开源实现不归一化属于"实现走样"，不宜作为口径依据。

**但必须做的事**：在对照文档里把这条标为"**原文自相矛盾，本项目取归一化口径**"，而不是假装没矛盾。

**升版影响**：保留 → **不升版**；改不归一化 → **必须升版**，且要改 `tests/test_features.py:298` 那条专门用来区分的断言（`# NF=3 distinguishes normalized entropy (1) from raw log2(3)`）。

---

### 3.2 REXP 年年数取整还是连续 —— 建议**保留连续**，成本最低

| 方向 | 证据 |
|---|---|
| 取整 | 论文 "n is measured in years" + 算例全是整数年 |
| 连续 | 论文没说取整；连续是整数年的自然极限；无年界跳变 |

**判断**：**保留连续小数年**（即保持内核现状）。理由不是"更对"，而是：**REXP 最终被论文剔除出模型**（与 EXP 共线，脚注 7 最低 Spearman 0.91），差异的实际影响最小，为它升版不划算。

**必须做的事**：在文档里写明"本项目取连续年，与论文整数年示例有差异"，并说明"REXP 在本项目是否进模型另行决定"。

**升版影响**：保留 → 不升版；改取整 → 升版（影响极小，不建议）。

---

### 3.3 AGE 加权还是简单平均 —— 建议**保留加权**，但这与论文确有差异

| | 论文 | 内核 |
|---|---|---|
| 公式 | 简单平均 `(3+5+4)/3 = 4` | `Σ(文件 churn × 距上次变更天数) / Σchurn` |
| 语义 | 涉及文件"平均多久没动" | "改动量大的文件多久没动"权重更高 |

**判断**：**保留加权**。理由：它是**更有信息量的口径**（一次提交改 500 行的文件和改 1 行的文件，不该等权），而且已经随 `kamei14-dg-v1` 上线并写在 `03-数据与算法规格.md:85`。**为它升版、重跑全部特征轮次，收益不抵成本。**

**必须做的事**：对照文档补一行，标明这是**已知偏差**而非疏忽。

> 注意区分两件事：**计算方式**（加权 vs 简单平均，保留现状）与**方向表述**（02 文档"越大越危险"是**明确错误**，必须改成"AGE 越大越安全"，Table I 的 Rationale 原文："The **lower** the AGE, the more likely a defect will be introduced"）。

## 4. 新发现：FIX 缺"缺陷编号"

**原文**（§3 Purpose 维度）：

> we search the change logs for keywords like "bug," "fix," "defect," or "patch," **and for defect identification numbers**.

**现状**：`经验教训.md:62` 记的是"Kamei 用的关键词就是 `bug, fix, defect, patch`——和我们的规则完全一致"。**关键词部分确实一致，但漏掉了"缺陷编号"这一条。**

**为什么重要**：ActiveMQ 上大量提交形如 `[AMQ-7126] Prevent OOM ...`，**不含任何关键词但含缺陷编号**。若论文口径含编号，我们的 fix 集合会**系统性偏小**，进而影响：fix 总数 → BIC 数 → 缺陷引入率（现测 18.5%）→ 全部下游指标。

### 4.1 先对口径：三个数字各是什么

动笔前发现报告里同时存在三个"ActiveMQ fix 数"，先对清楚，否则结论互相打架。

| 数字 | 产出脚本 | 提交范围 | 文本字段 | 其它过滤 |
|---|---|---|---|---|
| **1,337** | `probe_szz.py`（PyDriller） | **默认分支** | **完整消息** | 2013 起 / 剔合并 / 剔机器人 |
| **3,566（23.6%）** | `probe_fixrule.py` | **全分支 `--all`** | **仅标题 `%s`** | 剔合并 / 剔机器人，分母 15,097 |
| 3,448（27.4%） | 本次复核脚本 | 默认分支 | 完整消息 | **含合并 / 含机器人** |

**复现验证**：取默认分支 + 2013 起 + 剔合并 + 剔机器人 + **完整消息**，规则 C 命中 **1,337**，与 `探针结论表.md:48` **完全一致**。三个数字互不矛盾——它们是三套不同人口。

**由此得到两条方法学发现，需要写回结论表**：

1. **`probe_fixrule.py` 只用了标题 `%s`**，同一人口下比完整消息少 **219 条（−16.4%）**（1,118 vs 1,337）。Kamei 搜的是 changelog（完整消息），`probe_szz.py` 用的也是完整消息。→ **规则选型（剔除 `resolve` / `close`）是在"仅标题"人口上做的**，与实际 SZZ 人口不一致。结论方向大概率不变，但必须在结论表注明。
2. **`probe_fixrule.py` 跑的是 `--all`（16,378）**，而 `探针结论表.md:38` 明确写"全分支提交数（**不采用**）16,378"。→ **3,566 / 23.6% 落在团队不采用的人口上**，不应再作为 ActiveMQ 的 fix 结论对外引用；对外统一用 **1,337**。

### 4.2 缺陷编号影响面（已换到 SZZ 人口实测）

人口：默认分支 / 2013 起 / 非合并 / 非机器人 = **5,025** 条；规则 C 命中 **1,337**（26.61%）。

| 增量来源 | 条数 | 相对规则 C |
|---|---|---|
| **仅 JIRA 型编号**（`AMQ-1234`），关键词漏掉 | **2,475** | **+185.12%** |
| 仅 `#` 编号、无 JIRA，关键词漏掉 | 178 | +13.31% |
| └ 其中行尾 `(#NNNN)`（GitHub PR 特征） | 149 | — |

**JIRA-only 那 2,475 条的语义构成**（按标题关键词粗判）：

| 性质 | 条数 | 占比 |
|---|---|---|
| 像功能/改进（add / support / improve / build / bump …） | 1,047 | **42.3%** |
| 像缺陷（fix / bug / error / exception / incorrect …） | 91 | **3.7%** |
| 无法判断（仅 `[AMQ-xxxx] 描述`） | 1,337 | 54.0% |

典型"像功能"样例：
```
[AMQ-9692] Support destination gc sweep of destinations with only wildcard consumers
[AMQ-9775] Add the maxBrowsePageSize attribute to the JMX destination MBean
[AMQ-9806] Add H2 database support
AMQ-8525: Improve execution time for CI
```

**若全量采纳**：fix 1,337 → **3,990**，占比 26.6% → **79.4%**。文献区间是 15%~30%，**明显失真**。

### 4.3 裁决：**保持规则 C，不采用缺陷编号条款，不升版**

三条理由：

1. **`#NNNN` 在本仓库是 GitHub PR 编号，不是缺陷编号。** squash-merge 会稳定产生行尾 `(#NNNN)` 形态，直接纳入等于把 PR 当缺陷。
2. **`AMQ-xxxx` 是 JIRA issue 编号，但 JIRA 混了 Bug / New Feature / Improvement。** 粗判只有 3.7% 明确像缺陷，42.3% 明确像功能，54% 从标题看不出来。
3. **全量纳入会让 fix 占比失真。** 1,337 → 3,990，占比 26.6% → **79.4%**，远超文献 15%~30%。

**根本原因**：论文那条成立的前提是 **CVS + Bugzilla**——Bugzilla 里 issue 全是缺陷，编号即缺陷。迁到 **Git + JIRA + GitHub PR** 环境后编号语义变了，条款不能平移。

**要做对的前提**：必须 join JIRA 的 issue type（Bug vs New Feature/Improvement）。这需要外部数据源，项目当前没有，也不应为此引入。

> 反向验证：现有规则 C 的 fix 占比 26.6% 落在文献 15%~30% 内；加编号会冲到 79.4%，明显不合理。**这次实测反过来支持了现有规则。**
