> **提交数口径**：一律用**默认分支（HEAD）**。
> 理由：产品只处理默认分支；且 US-02 AC3 要求"页面提交数与 `git_commit` 实际行数一致"。
>
> **"可算特征 ≠ 非合并提交"**：合并提交天然没有 diff，已包含在"无 diff 85"里，**不要重复扣减**（这是真实踩过的坑）。

### 2.2 时间分布（决定时间窗口的依据）

| 时段 | 提交 | fix | fix 占比 |
|---|---|---|---|
| 2002–2013（12 年） | 764（33.9%） | 139 | 18.2% |
| 2014–2018（5 年） | 141（6.2%） | 18 | 12.8% |
| 2019–2021（3 年） | 214（9.5%） | 25 | 11.7% |
| **2022–2025（4 年）** | **1003（44.4%）** | 207 | 20.6% |
| 2026（未完） | 135（6.0%） | 11 | **8.1%** |

**观察**：

- **一半提交挤在最近 5 年**，2014–2018 几乎停滞（年均 28 条）。
- **2026 年 fix 占比断崖降到 8.1%**（其他年份 20%+）。**这不是标签截尾造成的**（fix 提交的识别与"以后有没有人看"无关），更像**开发阶段切换**（2024–2025 提交量暴增，疑似大重构期）。**待抽样核实。**
- 2014（4 条）、2018（3 条）、2012（10 条）样本过小，可视化和切分时要跳过这些稀疏段。

### 2.3 探针用的时间窗口

> **探针窗口：2022-01-01 ~ 2025-12-31 → 1003 条提交**

理由：正好千级规模；避开 2014–2018 停滞期；2026 年留给观察窗口消耗。

> **概念澄清**：特征计算**照样跑全历史**（`age`、`exp`、`rexp` 都要靠历史算）。
> **"暖机期"不是丢掉历史，而是"历史照算，只把窗口内的提交放进数据集"。**

### 2.4 ⚠️ commons-cli 不能当演示仓库

全量实测只有 **223 个缺陷引入提交**。8:1:1 切分后 test 折约 **22 个正样本**——**在这个规模上算 MCC / Popt20 是噪声**。

| 仓库 | 角色 |

| commons-cli | **探针仓库**：跑通链路、定参数、验证脚本 |
| ActiveMQ 量级 | **演示仓库**：出真实指标 |

## 三、SZZ 标注口径与实测（全量）

### 3.1 算法口径

1. 识别 fix 提交：`\b(fix(e[sd])?|bug|patch|defect|resolve[sd]?|close[sd]?)\b`（大小写不敏感）
2. 取 fix 提交**相对父提交**的 diff 中**被删/被改**的行（在父版本中的行号）
3. 剔除注释行与空行（非语义变更过滤）
4. 对剩余行在**父提交**上逐行 `git blame`，命中的最后修改提交 = 缺陷引入提交（BIC）
5. **统计口径：按引入提交去重，取"最早一次被修复"的间隔**

**时间戳**：统一用**作者时间**（`%at` / `author_date`），不混用提交者时间。

### 3.2 实测结果（399 个 fix 提交，全量）

| 项 | 值 |
|---|---|
| 删除行（.java） | 4207 |
| 其中注释/空行 | **1321（31.4%）** |
| 其中代码行 | 2886 |
| blame 成功率 | **4207 / 4207 = 100%** |
| 边界提交（追到初始提交） | **0** |
| 无法 blame / sha 失配 / 负间隔 | 0 / 0 / 0 |
| **去重后引入提交（BIC）** | **223**（代码行命中 171 + 仅注释行命中 52） |
| **缺陷引入率** | **9.9%** |

> **重要（统计口径）**：2886 条代码删除行只对应 **171 个引入提交**（**17 : 1**）。
> 说明**按行计数会被批量提交严重放大**（一个批量 fix 删 500 行、全 blame 到同一个老提交 → 500 个相同间隔 → 假尖峰）。
> **因此一律用"按引入提交去重"的口径报数。**

> **边界提交为 0 的说明**：两种判定方法（porcelain 的 `boundary` 标记 / 判断被 blame 提交有无父提交）**结果一致为 0**，且分布逐位相同。根提交存在且被正确识别，但**没有任何一行的来源是它**。这是数据事实，不是缺陷。

### 3.3 bug 存活时间（间隔 = 修复时间 − 引入时间）

| 分位 | 行级·代码行 | **提交级·代码行（推荐）** | 行级·注释行 | 提交级·仅注释行 |
|---|---|---|---|---|
| P10 | 3.8 天 | 1.3 天 | 2.1 天 | 0.0 天 |
| P25 | 34.3 天 | 13.6 天 | 20.0 天 | 0.4 天 |
| **P50** | 107.6 天 | **90.5 天（3.0 月）** | 124.7 天 | 122.7 天 |
| **P75** | 182.2 天 | **464.4 天（15.3 月）** | 486.1 天 | **777.1 天（25.6 月）** |
| P90 | 1342.4 天 | 1653.3 天 | 2490.4 天 | 2580.2 天 |
| max | 7902.8 天 | 5470.3 天 | 7920.1 天 | 3901.0 天 |
| `<1 天` 占比 | 2.3% | **9.9%** | 4.3% | **28.8%** |

**注释过滤的价值（实证）**：

- 剔除比例 **31.4%**；
- **仅被注释行命中**的引入提交有 **52 个，占全部 BIC 的 23%**——全部来自许可证头更新、javadoc 整理这类批量变更，**是误标**；
- 这些误标的 P75 达 **25.6 个月**，而代码行组为 **15.3 个月**。

> 结论：非语义变更过滤**不是无差别削减数据，是在去噪**。

**长尾是真的**：`max = 21.7 年` 来自"某个近期修复 blame 到一个 2002 年的非根提交"，**不是边界伪影**。这是 SZZ 的已知局限（老代码 / 批量变更吸走 blame）。
