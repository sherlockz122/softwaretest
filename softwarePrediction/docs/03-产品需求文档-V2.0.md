## 三、文档说明

### 1. 术语

| 术语 | 定义 |
|---|---|
| JIT 缺陷预测 | 以一次代码变更（commit/PR diff）为粒度，估计该变更引入缺陷的概率 |
| Fix commit | 有证据表明用于修复缺陷的提交；Issue 编号本身不等于缺陷证据 |
| SZZ | 从 fix commit 删除/修改的行回溯到较早提交，以推断候选缺陷引入提交的算法 |
| Buggy / Clean / Unknown | 已发现缺陷引入、观察期内未发现缺陷、标签尚未成熟或证据不足。Unknown 不参与监督训练 |
| Kamei 14 | NS、ND、NF、Entropy、LA、LD、LT、FIX、NDEV、AGE、NUC、EXP、REXP、SEXP 十四个变更度量 |
| 候选变更 | 尚未合入默认分支的 commit、分支或 PR diff，用于真正的“合入前”预测 |
| Effort | 审查工作量，V2 统一用 `LA + LD`（新增行数 + 删除行数）近似 |
| PofB20 | 按模型排序审查累计 20% Effort 时捕获的缺陷比例；本文不再重复列同义的 Recall@20%Effort |
| Popt | 模型排序的 effort-aware 曲线相对最优与最差排序的归一化表现 |
| SHAP | 解释模型输入特征对当前预测的贡献，不代表缺陷的因果根因 |
| OpenSpec | 规范驱动开发产物链：proposal → specs → design → tasks → implementation/test → archive |
| 故事点 | 团队对复杂度、风险和工作量的相对估算，不换算为固定人日 |

### 2. 文档目的

本文档定义产品要解决的问题、V2 范围、用户故事及验收口径。实现细节以设计文档和 OpenSpec 为准；接口、表结构、测试与用户故事的映射见追踪矩阵。

## 四、需求背景

### 1. 问题与机会

代码评审资源有限，团队需要判断“哪些变更值得优先细审”。静态规则可以指出确定的代码问题，但不能利用项目自身历史回答“这次变更未来引入缺陷的概率是多少”。Git 历史、缺陷 Issue 和修复提交为构建提交级训练数据提供了可能，JIT 模型可以作为评审排序信号。

本产品不承诺自动判定代码正确，也不把概率当作合并结论。它提供：

1. 可追溯的数据标注与模型评估；
2. 对历史提交的风险回溯；
3. 对候选分支/PR diff 的合入前预测；
4. 模型因素解释和审查建议，供人做最终判断。

### 2. 两类核心场景

| 场景 | 输入 | 输出 | 使用时点 |
|---|---|---|---|
| 历史分析 | 默认分支历史提交 | 标签、特征、训练数据、模型、历史风险与趋势 | 模型构建、质量复盘 |
| 合入前评审 | 候选 commit/branch/PR diff + 基线 ref | 风险概率、等级、影响因素、建议关注文件 | 合并前 |

仅扫描已合入默认分支的提交不能支持“进入主干前预警”，因此 V2 将候选变更预测列为核心验收链路。

### 3. 用户研究状态

当前未提供可核验的访谈纪要、招募记录或录音授权，V1 中“访谈 5 人、5/5 提及”等数据不作为事实引用。以下内容均为**待验证假设**：

| 假设 | 验证方式 | 通过标准 | 影响需求 |
|---|---|---|---|
| H1 评审者需要风险排序 | 访谈至少 3 名有评审经验的开发者 + 任务观察 | ≥2 人能用排序更快选出优先审查项 | US-18、US-19 |
| H2 只有概率不足以建立信任 | 对比“仅分数”和“分数+因素”的可用性测试 | 后者任务解释正确率更高 | US-17 |
| H3 管理者需要趋势复盘 | 访谈 1 名团队负责人 | 能明确说出至少 1 个周会决策用途 | US-20 |
| H4 标签追溯是模型采信前提 | 展示 SZZ 证据链并访谈 | 用户能从 fix 定位到 blamed commit/line | US-05 |

调研完成后应保存匿名化记录、结论与需求变更；未完成前不得在答辩中将其表述为实证结论。

### 4. 替代方案与差异化

| 方案 | 长处 | 局限 | 本项目取舍 |
|---|---|---|---|
| SonarQube 等静态规则工具 | 规则可解释、定位到行 | 不针对项目历史训练的提交级概率 | 不替代；可作为未来外部信号 |
| Git 热点/变更频率分析 | 数据获取简单、可用于复盘 | 不等于缺陷概率 | 作为看板辅助信息 |
| 学术 JIT 脚本 | 研究方法较完整 | 缺少数据、任务、界面和评审流程集成 | 产品化为可追踪流水线 |
| 人工评审 | 结合业务上下文 | 时间有限、顺序依赖经验 | 模型只负责排序和解释，人保留决策权 |

### 5. 目标用户与价值

| 用户 | 主要任务 | 产品价值 |
|---|---|---|
| 代码评审员/开发负责人 | 在合入前选择优先细审的变更 | 风险排序、因素解释、证据下钻 |
| 算法/数据工程成员 | 构建标签、特征、数据集和模型 | 版本化、可复现、防泄漏的实验流程 |
| 质量负责人 | 复盘风险与缺陷趋势 | 可追溯的统计和模型表现 |
| 平台管理员 | 管理任务、用户和运行状态 | 可观测、可重试、权限隔离 |

## 五、产品目标、非目标与成功标准

### 1. 产品目标

- 完成真实开源仓库从采集到历史风险列表的闭环；
- 支持候选变更的合入前预测；
- 满足课程硬指标：SZZ、Kamei 14、至少两类且合计不少于 8 种模型、两类评估指标、概率与解释、前端看板、工程化证据；
- 使数据版本、标签来源、训练配置、模型工件和预测结果可追溯。

### 2. 非目标

- 不证明某提交一定会或不会产生缺陷；
- 不自动替代代码评审或直接阻止合并；
- V2 不承诺 SaaS 多租户、移动端、跨语言统一模型或生产级高可用；
- V2 不把 SHAP 解释描述为因果根因分析。

### 3. 成功标准

| 类别 | 标准 | 证据 |
|---|---|---|
| 业务闭环 | 完成“仓库→解析→标注→特征→数据集→训练→评估→候选变更预测→解释”演示 | E2E 录像/测试报告 |
| 硬指标 | 14 特征；经典 ML + 深度学习共 ≥8 模型；双类指标 | 特征测试、模型注册表、评估报告 |
| 数据可信 | Unknown 排除训练；时间顺序切分；训练集内拟合预处理/采样 | 数据审计报告 |
| 可复现 | 任一模型运行可追溯代码 SHA、数据集、特征/标签版本、随机种子和参数 | model_run 记录 |
| 过程证据 | User Story → OpenSpec → PR → test → archive 可追踪 | 追踪矩阵、Git/看板记录 |

### 2. 范围分级

课程合规级别与交付优先级分开管理：

- **Must/Optional**：是否为课程硬指标；
- **P0/P1/P2**：当前交付优先级，可在 Sprint Review 后重估。

Sprint 1 的 MVP 是一条可运行的历史链路，不要求在一个 Sprint 内完成全量大仓库、8 模型、认证和全部看板。Sprint 2 才完成课程核心能力和合入前预测，Sprint 3 以测试与加固为主。

| ID | 用户故事 | 合规/优先级 | 验收标准（含异常） |
|---|---|---|---|
| US-06 | 我想提取 Kamei 14 特征，以便训练基线模型。 | Must/P0 | 对已解析提交生成 14 个值；公式和单位与设计文档一致；同版本重算幂等。 |

## 八、关键交互与低保真原型

### 1. 主流程

```mermaid

    B --> C[Fix 证据]
```

## 九、非功能需求

| ID | 质量属性 | V2 验收目标 | 验证方法 |
|---|---|---|---|
| NFR-01 | 安全 | 仓库 URL 阻止 loopback、私网、链路本地地址；DNS 解析及每次重定向后重新校验；密钥不入日志；RBAC 生效 | SSRF 用例、权限集成测试、日志检查 |
| NFR-02 | 可靠性 | 长任务有幂等键、心跳、最多 3 次重试；Worker 中断后可恢复或明确失败；重复请求不产生重复数据 | 故障注入、幂等测试 |
| NFR-03 | 性能 | 在最终指定演示环境与数据规模下，候选变更预测（不含首次模型加载与仓库拉取）P95 ≤ 1 s；列表查询 P95 ≤ 1 s | 固定硬件、固定数据集、至少 100 次请求的压测报告 |
| NFR-04 | 隐私 | 作者邮箱默认哈希/别名化；导出和日志不包含访问令牌、密码、原始邮箱 | 数据与日志审查 |
| NFR-05 | 可复现 | 训练记录包含代码 SHA、数据集、特征/标签版本、依赖锁、随机种子、参数和工件摘要 | 随机抽取 1 个 run 重跑并比对 |

性能数值是待验证目标，不是当前实测结果；若测试环境或模型不同，报告必须同时给出环境与口径。

## 十、迭代计划

### 1. Sprint 目标

| 阶段 | 目标 | 可演示增量 | 明确不塞入本阶段的内容 |
|---|---|---|---|
| Sprint 0（1–3 周） | 需求、设计、仓库与规范基线；完成小数据技术探针 | V2 文档、低保真原型、追踪矩阵；OpenSpec `add-data-collection` 评审；在小仓库验证解析接口 | 大仓库全量跑数、8 模型 |
| Sprint 1（4–6 周） | 首条历史数据 MVP | 公开仓库/限定提交窗 → 解析 → baseline SZZ → Kamei 14 → 时间切分 → LR/RF → 指标 → 历史风险列表 | 认证、全量大仓库、全部模型、SHAP 完整 UI |
| Sprint 2（7–9 周） | 满足核心硬指标并接入评审前场景 | ≥8 模型（6 经典 + MLP + TextCNN/DeepJIT-inspired）、语义输入、双类指标、校准概率、解释、候选 ref/diff 预测、趋势/任务页 | 低价值附加功能 |
| Sprint 3（10–14 周） | 功能冻结、测试与加固 | 安全/可靠性/性能证据、E2E、缺陷闭环、OpenSpec 归档；必要时补管理员能力 | 未评审的新功能 |
| Final（15–16 周） | 验收与答辩 | 可运行系统、测试报告、代表性 change 全链路、演示脚本 | — |

### 2. 模型交付组合

- 经典模型 6 种：Logistic Regression、Gaussian/Complement Naive Bayes（按最终输入分布选型）、SVM、Random Forest、XGBoost、LightGBM；
- 深度模型至少 2 种：MLP（14 维数值输入）与 TextCNN/DeepJIT-inspired（message + diff token）；
- BiLSTM、CodeBERT 为 P2 候选，不作为达标前提；
- 只有 TF-IDF + 14 维输入的普通分类器不得命名为 DeepJIT。

### 3. 估算与容量规则

- 故事点只作相对估算，不写“1 点 = 1 人日”；
- 每个 Sprint 只承诺团队平均速度的约 80%，保留 20% 用于联调、缺陷与文档；
- Sprint Review 后依据实际速度重估剩余 Backlog，并同步看板与 OpenSpec tasks；
- 课程 Must 未完成前不得启动 P2 模型或高保真视觉优化。

## 十二、风险与待确认事项

| 风险/决策 | 当前处理 |
|---|---|
| 大仓库跑数超时 | 先用小仓库/固定提交窗口验证，再全量；支持断点与缓存 |
| SZZ 噪声和时间截尾 | 保存证据、人工抽样；使用 Unknown 与观察窗口；报告标签版本 |
| 类别不平衡与指标虚高 | PR-AUC/MCC/PofB20/Popt 优先；采样仅限训练集 |
| 深度模型依赖语义输入 | Sprint 2 同步交付最小 tokenizer；不把 MLP 冒充语义模型 |
| GitHub 推送权限 | 当前只验证公开读取，未在命令行验证写权限；在新的干净克隆目录中登录后再推送 |
| 演示仓库选型 | 待小样本探针后决定；不得在测量前声称具体提交数、耗时或缺陷率 |
| 团队与管理工具 | 组员、责任人、看板工具、部署环境仍需团队确认 |
