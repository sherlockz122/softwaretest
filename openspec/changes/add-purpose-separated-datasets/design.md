# Design: add-purpose-separated-datasets

## Context

现有 MySQL、异步任务、outbox（事务外投递表）、租约栅栏（用租约令牌挡住旧执行者的写入）和本机不可变资产，这次直接复用，不重复实现。API 与 Worker 以只读方式挂载 public-assets（公开资产目录）；独立的数据集工件目录由专用初始化创建，只给 Worker 写、API 读，不把本机路径暴露给请求。

数据集构建复用现有的任务协调、投递、幂等和审计能力，只扩展数据相关的业务参数和页面。迁移、任务、权限、接口和页面组成一条完整链路，这条链路之外的能力不在这次改动里重新实现。

## Goals / Non-Goals

**Goals:**

- 把已经保存的公开资产接成应用内可创建、可查询、可追溯的数据集，固定用途、来源、政策和成员。
- 交付可恢复的 dataset.build（数据集构建任务）、A17～A19 接口与页面，以及研究用 12 个数值的 CSV（逗号分隔值）导出。
- 用真实的固定源验证无损数值、分区可复现和原子发布。

**Non-Goals:**

- 不训练模型，也不做模型发布评估。
- 不接入历史用途和候选用途的资格，不修改旧的 FeatureRun（特征轮次）、原资产和复核记录。
- 不支持其它数据格式、多语言和类型资格，也不提高生产环境的资源限制。

## Decisions

### 决策 1：请求只绑定受控资产，创建在一个事务里完成

任务请求绑定 asset_id（资产编号）、manifest（资产清单）的 content_hash（内容摘要），以及固定的 purpose（用途）、policy（政策）和 name（名称）。创建接口在同一个数据库事务里完成权限检查、幂等检查，并写入数据集记录和 outbox 待投递记录，要么全部成功，要么全部回滚。这样重复请求不会造出第二份数据集，投递也不会和落库脱节。

### 决策 2：规划和成员批次确定，重试从已提交处接续

Worker 先在数据库锁之外核验完整源，并计算一份确定的构建计划。之后每个批次在事务里检查最新任务、执行令牌、租约和取消状态，成员和进度一起提交。重试时复用同一个根任务、同一份计划和已经提交的成员，不重新规划，也不重复发布。这样中断只会让进度停住，不会留下半份数据。

### 决策 3：工件在隔离目录生成，由最终栅栏事务发布

最终导出写到按尝试（attempt）隔离的目录里。等完整工件生成并校验之后，再用最后一个栅栏事务同时发布引用和成功任务。没有经过这个事务的成员和工件不能下载，也不能被训练读取。

### 决策 4：两种切分策略各自固定边界

time_ordered（按时间排序切分）以已发布的作者时间戳（published author epoch）作为后验研究的顺序，同一时间组不会被拆到不同分区。repository_holdout（按仓库留出）按 canonical（规范化）仓库标识分组，不把 HDFS 和 MAPREDUCE 当成两个独立仓库。

缺类、空分区和重复冲突都要明确失败。相同身份、相同内容的记录去重，同时保留原来的行号和 cohort（项目分组）引用。研究固定使用 12 个数值，不含 LT（变更前文件的代码行数总和）这一项，不含已发布的 fix 特征，也不做拟合和重采样。

### 决策 5：研究资格只属于新数据集，不改旧结论

research ready（研究就绪）只表示新数据集对声明目标和切分的结构资格，不表示标签是金标、噪声率合格，也不表示模型可以发布。原资产和旧的 false（不满足）结论不改；历史、候选、语义、类型和定位这几项资格仍然为 false。

数据集要记录实际创建时间和源取得时间、许可、原始与派生摘要，以及每个仓库和 cohort 的支持数，并把这些限制一起写进元数据。

### 决策 6：迁移先预检，再执行任何建表语句

0009 迁移在执行前，先预检整个请求的降级路径，以及数据集任务和引用。只要受影响的数据非空，就不执行任何 DDL（建表、改表这类数据定义语句），更不会自动清空正常数据。0010 迁移沿用同样的预检规则，非空的成员不得转回有损的 JSON。

### 决策 7：高精度数值用无损文本保存，失败版本原样保留

真实 106674 条源数据第一次走 JSON 数值持久化时，发现末位发生变化。精确校验挡住了这次发布，没有用容差把它放过去。新增 0010 迁移，把成员数值改成无损的 canonical JSON（规范化文本），编码结果和规范化代码摘要都绑定到元数据和任务上。

0009 已经在本机执行过，保留它的历史。新出现的失败版本和成员不删除，也不在事后晋升；旧规则摘要的重试一律拒绝，新规则要重新创建版本。比例最多保留六位小数，避免任务 JSON 隐含更高精度的变化；原始的 12 个数值不舍入，也不用容差隐藏误差。

### 决策 8：权限沿用现有角色，下载只发已发布的固定文件

下载只允许已发布并通过校验的固定 partition（分区）文件，不接受任意路径。Viewer 可以读，Member 可以创建，任务由 Owner 或 Admin 管理。原来的用户会话和 RBAC（基于角色的访问控制）保持不变。

### 决策 9：容量按物理输出挂载检查，整轮有时限

容器镜像根目录 /app 显示的可用空间约 948 GiB，属于容器虚拟层，不能代表物理 D 盘的实际情况；本机输出挂载实测约 77 GiB。构建任务因此直接检查专用的输出挂载和实际父目录，每 2 秒要求保留 2.5 GiB，也就是 2 GiB 的最终保护和约 0.5 GiB 的本轮剩余增长。整轮限时 900 秒，源读取和导出各自另有上限。

启动、构建和回归仍然按包装器的 ExpectedGrowthGiB（预计增长量）估算，并以 D 盘的实际预算为准。虚拟层显示的余量不能替代宿主机检查，任何情况下都不回退到 C 盘。

### 决策 10：列表只做元数据预览，重活交给 Worker

源核验和导出都是有界重任务，Web 列表不会重复扫描整个 CSV。列表里的资产元数据只是预览，不声明数据已经完整；Worker 会重新验证完整来源，并核对请求摘要。

生产用途的 1000 个提交、10000 个文件、32 MiB 和 30 秒限制不提高；研究资产沿用 200000 行、256 MiB 和 180 秒的源预算，任务和导出分阶段另外限额。只有 csv 源且许可元数据合格的资产能用于这个研究目标；合成 fixture（测试夹具）只用于工程验收。

## Risks / Trade-offs

| 风险/权衡 | 说明 |
|---|---|
| 容器虚拟余量不等于宿主机余量 | /app 显示的 948 GiB 是容器虚拟层的数字，本机输出挂载只有约 77 GiB。如果拿前者做判断，任务会在宿主机磁盘已经告急时继续写盘，所以只能按实际父目录检查，并保留 2 GiB 的最终保护。 |
| 有损 JSON 保存会丢掉浮点末位 | 106674 条源数据已经实际遇到这个问题。0010 改成无损文本后不再丢位，但 0009 的历史必须保留，失败版本也不能删除或事后晋升，代价是数据库里同时存在两种编码。 |
| 降级可能把无损数值转回有损格式 | 0010 的回退路径如果直接改列，非空成员会丢精度。因此降级在任何 DDL 之前全量预检，非空一律拒绝，宁可降级失败也不破坏正常数据。 |
| 列表页若全量扫描 CSV 会拖慢 Web | 列表只返回元数据预览，并标明尚未由 Worker 核验。代价是用户看到的资产信息不是完整性证明，真正的结论要等后台核验。 |
| 研究预算与生产限制不能互换 | 研究资产沿用 200000 行、256 MiB 和 180 秒，生产限制仍是 1000 个提交、10000 个文件、32 MiB 和 30 秒。两者各自有界，不能拿一套额度去证明另一套安全。 |
| 合成夹具不能证明真实数据可行 | 夹具只能验证迁移、权限、源漂移和原子发布这些工程路径。真实资格要由 106674 条固定源和许可元数据验收，夹具通过不能替代。 |
| D 盘余量不足时任务会直接失败 | 系统不转 C 盘，也不清空已有数据。代价是大构建在空间紧张时只能停下，需要人工腾出空间后重试。 |

## Validation

- 用独立的 MySQL 和 Worker 跑迁移、源漂移、故障恢复和边界专项。
- 用真实的 106674 条固定源完成有界构建和导出核验，确认原始源和复核守卫没有被改动。
- 对 0009 和 0010 的全降级路径做预检，确认受影响数据非空时在任何 DDL 之前拒绝。
- 核对高精度数值经过 MySQL 往返后与原始解析值逐项一致，CSV 成员不回写来源资格。
- 验证两种切分、重复去重、冲突拒绝，以及每个分区是否都包含两类样本，并确认相同输入重算得到相同的成员和分区摘要。
- 验证取消、租约过期、旧令牌和最终事务失败都不会发布可用的数据集。
- 验证权限、分页列表、详情和受控下载，包括 360 像素宽度下的页面布局与键盘横向滚动。
- 完成必要的完整回归、独立新卷浏览器验收、静态检查、合同检查、存储检查和安全检查。
