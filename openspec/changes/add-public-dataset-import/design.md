# Design: add-public-dataset-import

## Context

内置公开资产走「原始文件 → 归一化 JSONL → 内容哈希密封 → 研究数据集构建」的管线。外部数据集只有格式不同这一个差异，其余（去重、切分、批次入库、防漂移、下载）全部可以复用。核心问题是把外部文件无损地接入归一化管线，并防止「猜列」出错（把缺陷列当成某个特征之类）。

## Goals / Non-Goals

**Goals:**

- 用户上传（或给出本地路径）一个 CSV/JSONL，声明列映射后走完整构建管线。
- 与内置资产同等的审计能力：源哈希、归一化一致性、防漂移、重复提交去重、可下载、可训练。
- 身份列（仓库、提交、时间、标签）必须齐全；数值特征列 v1 要求 12 个全部映射（训练矩阵契约以十二维为最小完整集）；fix 列可选，缺的按「未提供」处理。

**Non-Goals:**

- 不做在线 URL 抓取（网络不确定性、可复现性差）。
- 不自动推断列语义，列映射必须由用户显式声明。
- 不承诺任意格式；只收 CSV/JSONL。
- v1 不支持数值特征列部分缺失的导入（缺列拒绝并列出缺口）；缺失特征要贯通成员行、CSV 工件、审计重建与训练页勾选，另立 change 实施。

## Decisions

### 决策 1：导入走归一化资产管线，而不是单独一套数据集构建路径

技术选型：导入文件先被归一化成与内置资产相同的 normalized 记录结构（identity + numeric12 + published_fix_metadata），密封成资产后复用 `research_dataset.prepare` 与 `dataset_service`。只新增「归一化器」（把用户列映射转成 normalized 记录），其余全部复用。

备选路径：① 导入后直接切分入库，绕过资产密封——防漂移、幂等、审计全部要重写一遍，且与内置数据两条链路口径会漂移；② 让用户直接贴数据到表单——行数一大就不可用。不采用。

### 决策 2：用户显式声明列映射，系统只做格式校验

技术选型：导入请求带 `columns` 映射：四个身份列（canonical_repository、commit_id、event_epoch、label）为必填，12 个数值特征名（la、ld、nf、nd、ns、ent、ndev、age、nuc、aexp、arexp、asexp）在 v1 全部必填，fix 列可选。映射声明与许可声明进资产 identity（幂等键的一部分）。

备选路径：① 按列名自动匹配 + 模糊猜测——「bug」「defect」哪个是标签列一旦猜错，训练直接学反，风险不可接受；② 要求用户把文件改成系统内置格式再上传——把格式负担推给用户，违背「可以加载」的诉求。不采用。

### 决策 3：数值特征列 v1 要求齐全，fix 列可选

技术选型：v1 只要求四个身份列 + 12 个数值特征列全部有映射，缺任一数值特征列即拒绝并在错误里列出缺列清单（引导用户补齐列或换文件）；fix 列未映射不拒绝，成员行 fix 为 null 并带原因 `import_source_omits_fix`，摘要 limitations 记录。理由：训练矩阵契约（`reference()` 的 features 检查、CSV 工件、审计重建）以十二维为最小完整集，缺列要贯通成员行、工件、审计与训练页勾选，属于另一个 change 的范围。

备选路径：① v1 就做缺失特征全链路（成员行该特征为 null、训练跳过缺失特征）——需要动训练矩阵核心契约，风险过大且超出本 change 范围，列为 Non-Goal；② 缺的列补 0/均值——伪造数据。不采用。

### 决策 4：来源信息入摘要与幂等键，不新建与资产表并列的表结构

技术选型：资产 acquisition 记录 `source_kind: "user_import"`、导入许可声明、列映射与 fix 映射情况，随 metadata 进入数据集摘要（`source_kind` 内置为 `builtin_asset` / 导入为 `user_import`），详情页展示来源与映射；幂等键 = 资产 content_hash(identity)，同一文件同一映射同一许可 → 同一 asset_id，不同映射是两次独立请求。存储上复用资产目录结构（导入文件落资产区，清单与哈希照旧），不新建表。

备选路径：① 新建 `dataset_import` 表记录导入批次——导入同步完成、元数据已随 acquisition 密封，为元数据建表是多余的一层；② 把来源只写进日志不落摘要——详情页无法追溯来源，违背审计诉求。不采用。

### 决策 5：上传与本地路径双通道，统一进同一个密封入口

技术选型：接口接受两种来源——文件字节上传（原始请求体，不引入 multipart 依赖）或服务器本地路径（仅管理员），二者都落到资产目录后走同一套「清单 + 内容哈希 + 密封」流程，后续完全一致。

备选路径：① 只做上传——大文件（几百 MB 的公开数据集）上传超时与内存风险高，本地路径是刚需；② 只做路径——普通用户没有服务器文件系统访问权，通道对多数人不可用。不采用，双通道成本低且入口收敛。

## Risks / Trade-offs

| 风险 / 权衡 | 说明 |
|---|---|
| 列映射错误导致标签学反 | 映射由用户显式声明，导入前展示映射预览与「标签口径」确认；映射入幂等键可追溯。 |
| 大文件归一化耗时 | 导入同步执行，受行数（20,000）与字节（32 MB）上限约束；超限报错引导缩小文件或走服务器本地路径（同样受限）。 |
| 缺失特征对训练的影响 | v1 特征列不全直接拒绝并列出缺列；fix 列缺失按「未提供」带原因，不进模型计算。 |
| 恶意/损坏文件 | 沿用密封与校验链：非法行、哈希漂移、超限行一律按既有错误码拒绝。 |

## Validation

- 单元：列映射解析（必填缺失、未知列名、重复映射、缺特征列报缺列清单）、归一化记录生成、fix 列缺失口径、幂等键（同文件同映射相等、不同映射不相等）。
- 集成：真实 MySQL 导入一份小 CSV 走完整构建（去重、切分、下载、训练），来源摘要与 limitations 断言。
- 前端：导入表单（上传/路径、映射预览、标签确认）、数据集详情来源展示。
- 契约检查与追踪矩阵更新后整体跑一遍。
