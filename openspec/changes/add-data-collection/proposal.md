# Change: add-data-collection

## Why

JIT 缺陷预测要有真实仓库的提交历史才能训练，而系统目前没有任何数据入口，
模型这条线根本无从开始。

这个入口又特别容易做错，而且一旦做错，后面整条链都补救不回来：
数据来源不可信、中断之后跑不下去、修复提交的判定说不清依据——
任何一项出问题，下游的 SZZ 标签和特征都会失去意义。

所以先把数据采集这条基线立起来，给后面的 SZZ 标注和特征工程一个确定的输入。

## What Changes

- 支持接入公开的 HTTPS Git 仓库，并做好 URL、DNS 和重定向的安全校验与仓库信息管理。
- 支持异步克隆，解析提交与文件变更并落库，包括哈希、作者、时间、提交消息、父提交和变更明细。
- 任务做成幂等的，带心跳、分批检查点和失败重试状态，进程中断后可以接着跑。
- 识别哪些提交是缺陷修复，并给出分级证据：缺陷关键词记 medium，已确认的 bug Issue 记 high；
  只在消息里出现普通 Issue 编号的，不当作修复，只留一条低置信线索。
- 支持增量同步：基于独立的同步窗口和祖先关系判断。遇到强制推送或默认分支被改写时停下来等人工复核，
  不偷偷改历史。
- 为采集模块补齐单元测试、集成测试、安全测试和异常测试。

## Capabilities

### New Capabilities

- `data-collection`：公开 HTTPS 仓库的安全接入、提交解析、增量同步与缺陷修复证据识别。

### Modified Capabilities

没有。这只是扩展框架任务的业务参数，不改变任何已经验收过的能力行为。

## Impact

**数据库**

新增 repository、author_identity、git_commit、file_change、defect_evidence 五张表，
后续切分还会补上同步窗口和 Fix 轮次相关的表。
异步任务表和 outbox 表继续复用已有框架，不再造一套平行系统。

**后端**

新增仓库接入、数据采集、Fix 证据三个模块，扩展已有任务服务的业务参数，接口覆盖 A07～A12。

**存储与资源**

仓库数据放在 D 盘的 runtime/repositories 目录，由 API 和 Worker 共享挂载。
默认每个仓库最多 2 GiB、最长 900 秒，Worker 并发数为 1。
磁盘空间不够时直接拒绝，不会转去写 C 盘。

**不在本次范围内**

SZZ 标注、Kamei 特征计算和模型训练由后续 change 实现；
历史分叉的人工批准与重新基线、受控归档，以及其它代码托管平台的适配，也都不在这一批。
