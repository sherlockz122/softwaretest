# Design: add-public-dataset-audit

## Context

项目需要判断一件事：公开研究数据集能不能作为历史评估的来源。

难点在于「可用时间」的口径。生产合同要求标签在某个历史时刻已经可知，
而公开数据集给出的是它的发布者当时采用的口径，两者并不等价。

这次只做审计，把差异查清楚并报告，不试图去弥合。

## Goals / Non-Goals

**Goals:**

- 用固定的、来源可核对的公开数据，做出一份确定性的可行性审计。
- 把「研究发布标签」和「生产观测合同」严格分开表述。
- 给出按项目的历史时间切分可行性结论，以及明确的阻碍清单。

**Non-Goals:**

- 不做历史回放本身（另见 `add-historical-replay`）。
- 不做生产数据集持久化与 A17～A19。
- 不做模型训练。
- 不把外部数据交给生产内核，也不对历史标签的可用时间做回填或拟合。

## Decisions

### 决策 1：来源固定与完整性

- 下载只固定 Zenodo 5907002 和固定的 NeuroJIT Git revision。
- 保留原始 CSV、许可与出处、实际的下载时间，以及 SHA256。
- 发布方的 MD5 和 Git blob SHA1 用来核对发布一致性；SHA256 用来标识本机的内容身份。
- 不执行复现包里的代码，也不加载 pickle 模型。

### 决策 2：只读审计的严格口径

- 严格校验 CSV 的表结构、「项目 + 提交号」的唯一性、布尔标签、UTC 时间，以及有限非负数值。
- 异源日期表必须匹配项目、SHA、标签、用途和年份。
- 不同的事件时钟显式计数并标记为待来源核验；
  不因为作者时间和提交时间的合法差异就直接拒绝，也不静默改写。

### 决策 3：特征口径不冒充

- `apachejit-published-13-v1` 是原始的 12 个数值加上 fix，一共 13 维，不冒充本项目的十四维。
- 作者时间不冒充提交时间。
- 缺失的 LT 这一维特征、公式差异、fix 输入的可知性，全部标记为待核验。
- 离线的发布标签只是外部 SZZ 研究标签，不是人工确认，也不代表「无缺陷」这个事实。

### 决策 4：切分规则

- 每个项目独立按作者日期分组，做 70 / 15 / 15 切分。
- 同一事件组不跨集合；排序必须稳定。
- 切分比例不按评估效果调整。
- 两类分布、重复和缺失的审计只说明结构可行性，不能推导出生产发布可行性。
- 没有修复日期的外部正例，不得编造标签可用时间；clean 也不得仅凭年龄就自动取得生产负标签。

### 决策 5：时间语义的边界

- 下载时间是真实发生的下载时间；外部修复日期只作来源报告用。
- 本批不对历史标签的可用时间做回填、拟合或训练。
- 后续的历史回放需要单独定义：修复时间重建、负标签观察覆盖与删失，
  特征在当时是否可知，以及版本与来源证据。

### 决策 6：输出与隐私

- 报告不输出提交消息、diff 或原始身份。
- 源文件有大小、行数和时限限制；默认把输入读取放在 `runtime/` 下。
- 命令行工具只输出本机 JSON，原始数据不提交进仓库。
- 规划不足时，先修正文档并解释阻碍，再动手实现。

### 决策 7：随本批一并修复的问题

验收过程中暴露了三个跟这次改动相关的缺陷，一并修复：

**一是 Windows 受控 Git 的长路径问题。**
全量回归发现 Windows 下 Git 的深私有路径受限。
采集那边先补上长路径的约定，克隆组件改成在 Windows 上单独给 Git 打开长路径支持，
旧的安全边界和算法都保留，并补了深路径实测。

**二是只读存储统计的完整性。**
存储统计遇到测试临时目录时枚举失败。
改成：只读测量要么明确标出这次统计不完整，要么给出未统计目录的下界；
磁盘可用空间仍然单独测量，不受影响。
新增受控失败和重解析点的统计验收，不改 ACL，也不降低容量保护。

**三是长路径下的容量扫描漏算。**
用真实的打包文件补查时发现，一个 265 字符的文件会让 Python 读不到它的属性，
而旧的容量扫描只统计到 288 字节——
也就是说「长路径克隆成功」并不等于防护生效。

修复范围限定在本地文件访问用的 Windows 扩展路径上：

- 检查路径时仍然会查祖先目录有没有被替换成链接；
- 容量扫描把长路径下的打包文件也算进去，读不了的目录一律拒绝；
- 清理之前先确认目标落在本轮自己的目录范围内；
- Git 子进程继续使用普通的合法根路径。

新增真实 pack、发布、全目录字节一致性和不可读扫描的测试。没有注册表、PATH 或 ACL 的变更。

### 决策 8：浏览器溢出修复

独立浏览器复验时发现，特征结果里的连续长文本把 390px 宽的页面撑到了 554px。

修法是让列表换行，并在等待真实质量内容加载完成之后再验证页面没有溢出、质量表内部可以滚动。
失败的尺寸和最终结果都保留。本批不新增页面功能。

## Risks / Trade-offs

| 风险 / 权衡 | 说明 |
|---|---|
| 公开标签口径与生产合同不等价 | 审计结论只能回答「能不能用」，不能直接当作可用标签。多数结论可能是「不可用」。 |
| 13 维基准与项目的 14 维 | 没法直接对比效果，只能作可行性参考。 |
| 存储统计遇到不可读目录 | 改为返回下界而不是精确值，宁可保守也不夸大完整性。 |
| 长路径修复仅限本地文件访问 | Git 子进程仍然走普通的合法根路径，路径极端深的时候还是可能受限。 |
| 切分比例固定不调 | 不按效果调参，保证可复现性，代价是可能不是最优切分。 |

## Validation

- 专项覆盖：重复、日期缺失与冲突、无穷大、NaN、非法布尔、同时间分组、单类、
  来源篡改、用途隔离、资源限制与确定性。
- 对真实完整 CSV 做独立审计并保存汇总，保留首次失败记录。
- 按现有的全量后端、独立浏览器、严格 OpenSpec、文档契约流程验收。
- 新增生产兼容的变更之后，需要重建并完成全量与独立复验。
