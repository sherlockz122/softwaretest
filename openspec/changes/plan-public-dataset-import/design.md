## Context

现在的公开数据链路分三段：专项脚本下载 ApacheJIT 两个表与许可材料，审计脚本按固定列名检查结构、键、数值、时区与许可，导入函数把通过审计的目录封装成内容寻址资产。三段都能跑，但只认 ApacheJIT 这一种来源：审计脚本把文件名与列名写死，导入函数的来源校验由专项命令注入，资产清单里的能力位来自模块常量。

数据集创建接口只接受「已有资产的标识与来源摘要」，所以用户能挑到哪份数据，取决于运维此前把什么放进了资产库。

## 决策 1：以适配器声明加内容寻址资产为目标形态

一条导入规格描述一个来源：原文文件名、列映射、行键、事件时间列、标签列、许可字段、能力位与限制清单。导入按规格执行，资产清单记录规格版本。

这样第二个来源的接入只需要写一份规格与一份列校验，不需要复制一遍导入流程。

备选路径是不做规格、为每个来源写一份专项脚本。那样第一个来源最快，第三个来源起每份脚本都要重复审计与封装逻辑，也很难说清两份资产的口径差异。

## 决策 2：导入只走命令行，暂不做服务端出网与应用内上传

导入是低频、重量、需要人来判许可的操作。命令行加受监督子进程与超时上限，失败时整批回滚，符合现有任务体系的风格。

服务端出网下载会让应用进程对外发起请求，要另做域名白名单、重定向校验与体积上限；浏览器上传要另做临时目录、断点、病毒与压缩炸弹防护。这两块都值得做，但都不该塞进第一批。

备选路径是先做上传入口。收益是演示时更好看，代价是安全面与恢复逻辑立刻扩大，而这一批真正缺的是口径而不是入口。

## 决策 3：口径版本进清单，不在代码里悄悄改语义

适配器升级可能改变列语义，比如某个字段从计数改成比例。改动后必须产出新的口径版本，旧资产的清单与哈希保持不变，读的人能看出两份资产不同代。

备选路径是只靠代码仓库的提交历史自证。问题是资产会被拷出仓库单独使用，那时清单是唯一的自证材料。

## 决策 4：体检复用已有的审计规则，不重新发明

现有审计已经覆盖结构、键与标签一致性、数值有限非负、时间可解析、项目分组与单类组排除，并且有协作式超时。新规格只增加三件事：按声明取列名、把结论写进清单、把失败原因归类成可读的码。

备选路径是为导入另写一套校验。两套规则并行，日后必然出现同一份数据一边过一边不过的情况。

## 决策 5：第二个来源的选型留到实现时按数据可得性定

候选有三类。一是同一发布者的扩展数据，列结构与 ApacheJIT 接近，适配成本最低。二是另一套公开缺陷数据集，列语义不同但同样按提交粒度，需要重新定义能力位。三是我们自己的解析链路产出的仓库特征，它不是公开数据集，走的是解析任务而不是导入。

第一批只做规格与 ApacheJIT 适配器，第二个来源在实现时按可得性选，不在计划里假装已经定好。

## Risks / Trade-offs

- 许可风险：每个来源的许可与来源记录必须随资产保存，换来源时不能沿用 ApacheJIT 的许可字段。
- 标签噪声：公开数据集的缺陷标签多为弱监督结果，导入只能保证结构与口径一致，不能提高标签质量，能力位里必须写明未认证。
- 跨源重叠：两个来源可能含同一条提交，合并前要定义去重与优先级，否则训练集会重复计数。
- 单类组：某些项目组全部同一个标签，必须排除并记录原因，否则分层切分会失败。
- 体积与时限：单文件上限与总时限沿用现有预算，超限时明确失败，不做静默截断。

## Migration Plan

这次只出规格、方案文档与体检规则，不改实现。后续实现拆两批：第一批把 ApacheJIT 的现有规则抽象成适配器并保持资产标识不变，第二批接入第二个来源并补上传入口的独立设计。

既有资产的清单、哈希与数据集引用保持不变；接口清单不新增条目，因此 OpenAPI 基线不需要重新导出。

## Validation

文档层面跑严格 OpenSpec 校验与契约检查。实现层面的验证在对应任务里写明：真实 ApacheJIT 导入与审计一致性、同一来源重复导入的幂等、单类组项目被排除、键不对齐与许可不符的拒绝、路径越界在创建文件前被拒绝。细则见 [导入方案与格式口径](../../../docs/development/公开数据集导入方案与格式口径.md)。
