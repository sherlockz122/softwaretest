# Design: add-training-prediction-separation-and-concurrency

## Context

既有拓扑：FastAPI 提供在线 API（登录、数据集查询、模型运行查询、风险列表预测），Celery worker（Redis broker，prefetch=1，fenced 执行 + 至少一次投递）消费训练与数据集构建任务。预测路径读的是「已注册模型」的工件与报告，训练路径写的是「模型运行」的状态与产物——数据上已经分开（注册发布是显式动作），进程上也已经分开。缺的是契约：边界没有写成规格、没有测试锁住，界面文案也只是散点。

多用户并发方面，系统已有三件防具：幂等键（同请求重放返回同任务）、任务租约（claim/reconcile，崩溃恢复）、RBAC（成员只能操作自己的资源）。缺的是把它们捆成并发契约的测试与文档：两个用户同时训练、同一用户并发重复提交、构建与训练排队时的状态一致性。

## Goals / Non-Goals

**Goals:**

- 训练/构建走任务队列，预测走在线读已注册模型：两条链路的进程、数据、界面边界写成规格并被测试锁住。
- 多用户并发的隔离与一致性契约：并发请求不串扰、幂等去重、租约恢复、所有权校验在并发下依然成立。
- 界面职责文案成体系：训练页与历史风险列表互不混用。

**Non-Goals:**

- 不拆新的独立服务进程；不做多 worker 横向扩容与队列优先级；不做在线学习。
- 不把「训练时预测不可用」之类的现状问题留给部署层——本 change 只承诺既有拓扑下的边界行为。

## Decisions

### 决策 1：训练与预测的边界以「任务队列 vs 在线读取」为界，不引入新服务

技术选型：维持 Celery（训练/构建）+ FastAPI（查询/预测）双进程拓扑。训练请求一律落任务队列（202 接受），预测请求同步读已注册模型的工件与报告返回。规格只承诺：预测不依赖队列状态、不等待任何租约、训练排队不影响已发布模型预测。

备选路径：① 训练改在 API 进程内异步执行——阻塞事件循环或与请求生命周期耦合，重启即丢，明显倒退；② 预测也走任务队列——历史风险列表每次都要排队出结果，用户体验不可接受；③ 拆出独立「预测服务」进程——当前负载没有必要，属于过度设计。不采用。

### 决策 2：注册发布是训练→预测的唯一数据通道

技术选型：训练产物（工件 + 报告）在「注册发布」这一显式动作后才对预测路径可见；预测读取的工件与报告按哈希密封，读取不获取任何任务租约、不与训练中间状态共享可变对象。模型运行状态（训练中/失败）与预测可见性解耦：未注册的模型无论如何不可预测。

备选路径：① 训练一成功就自动可预测——训练中/训练完未评估的模型流入预测路径，破坏「先评估后发布」纪律；② 预测路径加分布式锁与训练互斥——没必要：预测只读密封工件，训练写的是运行记录，天然无共享写冲突。不采用。

### 决策 3：并发模型 = 幂等键去重 + 任务租约串行消费 + RBAC 所有权，三者组合即契约

技术选型：并发契约写成三条规则——（a）同一幂等键的重复请求返回同一任务（并发提交只产生一个任务）；（b）worker 按租约一次只执行一个任务实例，崩溃后 reconcile 恢复，租约内执行与状态更新是数据库事务封装的（fenced execution）；（c）资源操作校验所有权，跨用户操作 403。并发测试直接以「两用户同时训练」「同键并发重复提交」「构建与训练排队」三类场景锁定。

备选路径：① 引入全局训练互斥锁（同一时间只允许一个训练）——多用户并发的核心价值就是并行，一刀切锁死违背需求；② 把幂等去重放宽为「尽力而为」——并发窗口内出现重复任务，回滚成本高。不采用。

### 决策 4：worker 并发度维持 1，扩展方向写进文档而非代码

技术选型：当前单 worker、prefetch=1：一次执行一个任务，租约与事务语义最简单可靠。多用户并发靠队列排队 + 幂等去重满足；若未来任务量增长，扩展方向是增加 worker 进程数（Celery 天然支持），前提是租约与 fenced 执行已按进程安全设计——本 change 用文档记录该扩展路径，不实现。

备选路径：① 现在就开多 worker——引入并发执行下的租约竞争、资源上限（内存/CPU）问题，当前负载下得不偿失；② 线程池并发执行任务——训练是 CPU 密集的 numpy/sklearn 负载，GIL 下伪并发。不采用。

### 决策 5：界面职责边界用路由与文案双重固化

技术选型：训练入口只出现在模型页（/models），历史风险列表独立成页（/risk）只展示已注册模型的预测；两页文案互链但职责明确：「训练和预测是分开的两件事」。已有部分文案，本 change 补全并在前端测试中锁定文案与路由。

备选路径：① 把训练按钮放进风险列表页——职责混在一个页面，用户分不清「训练」与「预测」；② 只改文案不动路由——路由分离是职责分离的硬保证，文案只是软提示。不采用。

## Risks / Trade-offs

| 风险 / 权衡 | 说明 |
|---|---|
| 训练卡死占用唯一 worker | 有租约超时 + reconcile 恢复；预测路径不依赖 worker，业务不受影响。 |
| 并发构建/训练争抢资源 | 队列串行消费天然限流；文档写明单 worker 的资源上限与扩展路径。 |
| 幂等键并发窗口 | 幂等登记与任务创建在同一事务里（既有实现），并发重复提交只有一个生效。 |
| 预测读取训练中间状态 | 预测只读「已注册模型」的密封工件，训练中间状态只存在于运行记录，通道上不可见。 |

## Validation

- 单元：幂等键并发重复提交只产生一个任务；租约 reconcile 在并发场景下的恢复；所有权跨用户 403。
- 集成（真实 MySQL/Redis）：两用户同时训练互不干扰且各自产物正确；训练任务卡死（租约过期）时风险列表预测接口照常返回已注册模型结果；预测接口不产生任务队列消息。
- 前端：训练页与风险列表的职责文案与路由断言。
- 契约检查与追踪矩阵更新后整体跑一遍。
