# Change: add-training-prediction-separation-and-concurrency

## Why

用户明确要求「训练和预测要分开」与「多个用户并发」。系统目前的部署形态是：FastAPI 在线服务承担查询与预测（风险列表直接读已注册模型），Celery worker 消费任务队列承担训练与数据集构建——进程层面已经分开，但这条边界没有写成正式契约：没有测试证明「训练排队/卡死时预测不受影响」，界面也没有把「训练」与「预测结果」两条链路讲清楚。同时，多用户同时建数据集、同时训练的场景没有契约约束与并发测试：幂等键、任务租约、RBAC 所有权这些机制各自存在，但没有一个 change 把它们捆成「多用户并发」的正式能力。

## What Changes

- 把「训练走任务队列、预测走在线服务读已注册模型」写成正式契约：训练任务（构建、训练）不占用 API 请求路径；预测查询不依赖任务队列状态；训练排队或失败 MUST NOT 影响既有已发布模型的预测。
- 界面职责边界文案成体系：训练页只管「训练新模型」，历史风险列表只展示「已注册模型对历史数据的预测」，两者互不混用（与 add-dataset-14dim-and-split-choice 已落地的文案呼应并补全）。
- 多用户并发契约：同一用户与不同用户的并发请求依靠幂等键、任务租约与 RBAC 所有权隔离；并发训练/构建共用任务队列时按租约串行消费，互不覆盖；文档与测试明确并发上限与行为。

## Capabilities

### New Capabilities

- `training-prediction-separation`：训练与预测两条链路的进程边界、数据边界与界面边界。
- `multi-user-concurrency`：多用户并发创建、训练、查询时的隔离与一致性契约。

### Modified Capabilities

- `model-training`（训练队列语义与并发行为写进契约）。
- `historical-risk-list`（预测读取路径与训练队列解耦的契约）。

## Impact

**架构**

无部署形态变化：沿用 Celery（Redis broker）+ FastAPI 的既有拓扑。本 change 把边界写成契约并补齐测试：训练任务卡死时预测接口照常返回；预测接口不消费任务队列。

**后端**

预估少量硬化：预测路径对模型工件的读取不与任务租约共享可变状态（如已有隐患则修复）；并发测试覆盖两用户同时训练/构建。

**前端**

模型训练页与历史风险列表的职责边界文案补全（已有部分文案，本 change 成体系并加测试）。

**不在本次范围内**

不引入训练专用的独立服务进程（当前负载下 Celery 队列已足够）；不做横向扩容（多 worker 进程）与队列优先级；不做在线学习。

**关联追踪**

受影响文档：docs/04（训练与预测的进程/队列边界说明）、docs/08（训练页与风险列表职责文案）、docs/07 新增 US-33（训练预测分离）与 US-34（多用户并发）、PRD 非功能需求域。
