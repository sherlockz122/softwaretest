# Design: add-fix-recommendations

## Context

修复参考建立在已经验收的数据能力上：提交解析与作者身份、修复提交识别与证据等级、缺陷来源追溯的行级证据、十四维特征向量都已经入库。这次改动不新增数据源，只把已有数据组织成一种新的查询。合入前评审链路已经有候选预测页面和解释面板，修复参考面板作为它的补充出现。权限体系已有三种角色，只读角色可以查看仓库数据。

## Goals / Non-Goals

- 目标：给一次提交检索本仓库真实发生过的相似修复，附相似理由和证据链接；仓库详情页和候选预测结果页两个入口复用同一个检索实现。
- 非目标：不生成修复文本或补丁，不自动应用修复，不接入外部模型或网络服务，不把相似修复说成当前缺陷的根因结论，不修改已有预测与追溯接口的行为。

## Decisions

### 决策 1：建议只取本仓库真实修复提交，不生成新内容
课程要求的是高质量修复建议，质量最可靠的来源是仓库自己发生过的修复。检索结果全部来自已经解析并带有证据等级的修复提交，每条都有提交记录可查。生成式建议依赖外部模型，产出无法逐条追溯，这次改动不做。

### 决策 2：相似度由文件重叠、特征距离和证据等级共同决定
排序分三级：先按触及文件的重叠数量降序，重叠数相同的按十四维特征距离升序，距离仍相同的按修复证据等级优先。放弃只用特征距离的做法，因为文件重叠对评审员最好解释，理由写成「这条修复触及了你这次改动中的三个文件」比「向量距离 0.42」直观得多。

### 决策 3：检索覆盖全部历史，不设时间截止
修复参考是给人看的检索材料，不是训练特征，不存在把未来信息泄漏进训练的问题。允许返回时间上晚于目标提交的修复，能给评审员多一个「这个文件后来被怎么修过」的参照。训练链路的时间截止规则不受任何影响。

### 决策 4：不建新表，实时查询并限额
修复参考是读多写少、单次数据量小的查询，从提交、修复证据、缺陷追溯和特征表实时计算，省掉一张需要维护一致性的缓存表。候选扫描行数和返回条数都设上限，防止在提交历史很长的仓库上拖慢接口。

### 决策 5：两个入口共用一个查询服务
仓库详情页的提交修复参考和候选预测结果页的同类修复面板，背后是同一个检索实现，只换检索对象（提交编号或候选改动的触及文件），避免两套相似度逻辑各自漂移。

### 决策 6：接口为只读查询，纳入现有权限
新增只读查询接口，未登录请求被拒绝，三种角色都能查询，接口不触发任何任务或写入。

## Risks / Trade-offs

| 风险/权衡 | 说明 |
|---|---|
| 小仓库修复历史少，参考列表短或为空 | 空状态明确说明仓库尚无修复历史，不拿其他仓库的数据硬凑 |
| 文件重叠与特征距离可能指向不同候选 | 排序以文件重叠为先，特征距离只在重叠数相同时决定先后，相似理由里写清生效的是哪一条 |
| 实时查询在长历史仓库上可能变慢 | 依靠索引、候选扫描行数上限和返回条数上限兜底，接口响应时间纳入演示环境的实测 |

## Validation

- 单元测试：排序规则的手算夹具、空历史、限额截断、非法提交编号。
- 集成测试：在真实 MySQL 上用一个已采集仓库的数据核对返回内容、排序和证据链接。
- 浏览器实测：仓库详情页与候选预测结果页两个面板的展示、空态和跳转。
- 端到端：在演示环境对一个真实仓库走通缺陷来源追溯后查看修复参考，并把证据登记进追踪矩阵。
