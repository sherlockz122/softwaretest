## Context

NFR-03 判的是在线接口的延迟，而已有的性能实测都在后台任务这一侧。要把两件事分开，还要让结论能被别人重跑，就得有脚本、有原始记录、有环境与数据量的固定方式。这次改动只补这三样东西，不动接口实现。

## Goals / Non-Goals

**Goals**

- 让"至少 100 次有效请求"这句话落到可执行的脚本与可核对的原始记录上。
- 让分位数、吞吐、错误率、环境、数据量、模型版本六项在同一份汇总里出现。
- 让页面级的能力有一次真实浏览器走查记录，而不是只有组件测试。

**Non-Goals**

- 不做容量规划，也不推断多实例或更大数据量下的表现。
- 不因为压测通过就宣称模型效果合格；延迟与效果是两件事。
- 不为尚未实现的候选预测接口造数据。

## Decisions

### 决策 1：压测对象限定在线接口，后台成本只用于推算数据量上限

NFR-03 的条文判的是点一次预测、翻一页列表的响应时间，解析与特征内核的耗时属于后台任务，两者不能互换。已经有实测数据的部分继续留在证据底稿里，只用于回答"演示数据能放多大"，不参与 P95 的计算。

### 决策 2：有效请求用三道关判定，不只认状态码

只看状态码会把返回 200 的错误外壳也算进样本，分位数会虚低。脚本要求状态码为 200、响应体是 JSON、且包含该接口约定的关键字段，三项都满足才算有效。失败请求单独计数并进入错误率，不回填样本。

### 决策 3：串行与固定并发分开汇总

四并发下的排队时间会抬高尾部分位数，把它和串行样本混在一起，算出来的 P95 既不代表串行也不代表并发。脚本对两组分别计算，报告里两行并列，读的人自己选对应场景。

### 决策 4：分位数用最近秩法自己算，不引入统计库

样本量在百级到千级，最近秩法够用且口径可以写进文档，读的人能复算。实现只有几行，配一个单元测试固定住边界情形，比依赖第三方库的默认插值方式更可信。

### 决策 5：原始记录入库，报告数字由脚本生成

手抄数字无法复盘，也容易被质疑。脚本把每次请求写一行逗号分隔值记录，汇总同时写一份 JSON，报告里的表格从这两份文件抄录，并写明对应的文件名。

### 决策 6：演示数据用仓库自带的工程夹具，训练一次并保留工件

夹具能在几十秒内生成上千行样本，行数可控、内容固定，适合做延迟对照。它同时声明自己不是真实采集数据，能力位里把候选发布标成不支持，因此用它训练出来的运行可以读风险列表，但不能发布成候选模型。这一层限制保留在证据里，报告只按"能测延迟"来用。

### 决策 7：本机没有可用的容器运行时，改用直连进程跑同一套代码

`compose.yaml` 要求容器引擎，本机装着的引擎后台没有起来，因此这次用本机 MySQL 8.0 与 Redis 直连进程起同一份应用代码，端口与 `compose.yaml` 的后端端口保持一致。差异写在报告的运行环境一节：容器内是 Linux 加固定内存参数，本机是 Windows 加同样的内存参数，两者不互相替代。

## Data Constraints

原始记录只写接口标识、序号、耗时、状态码、是否有效与失败原因，不写响应体，也不写令牌与密码。压测使用的账号是一次性引导账号，口令只存在本机环境变量里，不入库。

请求次数上限设为两千次，超过时脚本拒绝执行，避免误操作把演示环境打满。分页参数固定取页面实际使用的值，风险列表取默认页与页大小上限两种。

## Failure Recovery

服务在压测过程中不可用时，失败的请求按无效样本计数，脚本继续跑完剩余次数并在汇总里记录首个失败的时间点与状态码类别。汇总与原始记录仍然照常写出，方便区分"服务挂了"与"服务慢"。

中途终止时已有记录保留在输出文件里，不写半行；汇总文件采用先写临时文件再替换的方式，避免出现半份 JSON。

## Security Controls

脚本复用现有的登录接口拿访问令牌，令牌只在内存里传递，不打印也不落盘。环境信息只采集机器型号、核心数、内存、操作系统与解释器版本，不采集用户名与主机名以外的身份信息。

## Test Strategy

分位数、有效请求判定与汇总口径抽成纯函数，用单元测试覆盖样本为空、全失败、样本量小于下限、并列耗时与分页越界几类边界。端到端部分靠一次真实压测与一次浏览器走查，原始记录与截图一起入库，结论只在记录齐全时才写进报告。

## Migration Plan

不需要数据迁移。新增的脚本与文档互不依赖，可以分两次提交；先把脚本与单元测试合入，再补实测记录。
