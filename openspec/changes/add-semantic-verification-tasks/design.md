# Design

## Task binding and transaction boundaries
A38 POST /semantic-assets/{asset_id}/verifications has no request body or path parameter other than a 64-lowercase-hex asset ID, and requires Idempotency-Key. Current active Member+ authorization precedes filesystem observation. One actor scope covers semantic.verify; replays return the original task and changed IDs conflict. The new payload contains asset ID, original receipt/provenance references, semantic-asset-read-v1 rule identity and a digest of the new consumer executable sources. Source snapshots are hashes, not executable imports of frozen research producer code. No floats, secrets or raw text enter the task payload/result.

Existing TaskService owns queueing/outbox, claim, expiry/recovery, owner/Admin cancellation/retry and bounded retry relationships. No root business table is necessary for an integrity-only task: each attempt retains its fixed payload; a successor uses the same root and binding, and only the current attempt execution token can finish itself. A38 returns task_id/status; A29/A30 expose semantic_asset_id, safe state and the final result. Publication rechecks task type, version/binding, execution token, active unexpired lease, cancellation, and receipt identity; success and audit are one DB transaction. Snapshot success states that verification passed at that time, never that files can no longer change.

## Worker resources and errors
Worker mounts semantic assets read-only. asset_reader.Budget remains 60 seconds and calls a task heartbeat/lease/cancel check during bounded file/row operations; source identity is checked at both ends. Local regular-file IO plus bounded formats constrain the operation, but cooperative checks are not an OS hard CPU/RSS/IO quota. Unknown IO/consumer errors fail with controlled safe codes; DB failures leave the lease for existing recovery. No raw subprocess stderr or source content is logged. A verified result records asset/origin/rule/consumer binding, dimensions/partitions, payload hashes and unchanged restricted capabilities; it never stores vectors or raw member text. Full verification restarts after interruption; no partial result is published.

## Installer lock and legacy compatibility
Use a new persistent regular-file lock (v2), held with nonblocking POSIX flock or Windows byte-range locking until publication exits. Lock only the short final critical section after the bounded copy/verification; keep the existing catalog limit recheck and idempotent target verification inside it. Owner PID/start/nonce metadata is bounded and diagnostic only, never proof of liveness. Never unlink the OS lock path, including on release: unlinking would permit a second inode and concurrent writers. A legacy .publication-lock blocks new publication rather than being deleted by age or guessed PID. Operators must stop old installers before upgrading; mixed old/new writer versions are unsupported and explicit. OS kill releases a v2 lock without deleting assets or failed attempts. Tests use real independent processes and forcibly terminate the holder, then reacquire; separate corruption/legacy/link/size failures preserve old asset bytes.

## UI and qualification

Windows byte locks also deny reads of the locked byte from another handle. The persistent file reserves byte0 for locking and stores diagnostic owner JSON after that byte; bounded diagnostic reads start at offset1 and never determine liveness. Initial test signals must be hidden files in the catalog so they cannot masquerade as published asset IDs. The original failed cross-process run remains evidence, and contention/kill/reacquisition assertions remain required.

A valid v2 marker with a bounded but partial owner record can result from process exit during metadata IO. Only after obtaining the OS lock and verifying the same regular single-link inode, the next holder may rebuild this diagnostic text. Unrecognized markers, links, oversized paths and legacy locks still fail closed; legacy contention retains the original SEMANTIC_ASSET_INSTALL_BUSY code. A DB NOWAIT row lock in the real runtime test traps a committed Worker claim before publication, enabling deterministic SIGKILL without a product delay flag. CI creates the host-owned semantic bind root before Docker does; no system ACL change is required.
Member/Admin can request a verification, retries of a lost response reuse the same operation key, Viewer remains read-only. Task center filters semantic.verify while retaining status/paging; task details link back to the fixed asset and show version/receipt/time/safe failures. Existing TaskActions own cancel/retry and redirect to successors. Loading/error/stale route state and 390px overflow are verified. Task success does not change catalog capabilities or expose training/publish controls.

## Acceptance and rollback

The disposable pre-cleanup evidence collector must explicitly accept semantic.verify while preserving its existing five-field projection, 1000-row/256KiB limits and rejection of unknown types, payloads and messages. An actual child-process/database capture regression must cover the new task. The initial full browser run passed20 UI cases but correctly failed the overall acceptance because this type was omitted from the collector allowlist; retain that failed summary/cleanup evidence and repeat the full new-volume run after updating and rebuilding the collector image.

Use one stdlib-only task-kind registry for claim, task filtering and evidence validation so later kinds cannot diverge between these paths. An independent contract test compares that registry to the UI's type filter inventory and exercises the safe evidence envelope for each kind; arbitrary unregistered values remain rejected. Include the registry in the verification executable binding. This does not change the existing task state machine, roles or qualification.
