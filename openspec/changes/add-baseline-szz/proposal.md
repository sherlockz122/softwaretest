# Change: add-baseline-szz

## Why

系统已经能判断哪些提交是修复提交——先由缺陷关键词这类启发式规则给出候选，再由人工复核确认。
但还缺最关键的一环：这次修复删掉或替换掉的那几行代码，最初是哪一次提交写进来的。

没有这条证据链，JIT 缺陷预测最核心的问题——某次提交是否引入了缺陷——就无从回答，
模型也就拿不到训练标签。

SZZ 单独做成一个 change、而不是塞进数据采集里，是为了防止标签被污染：

- 采集阶段的异步任务状态不应该渗进标签；
- 还没被接受的同步数据不应该被当成输入；
- 事后才产生的证据（未来才发生的复核、才观测到的 Issue）不能倒推回历史标签。

## What Changes

- 新增异步的 SZZ 追溯（验收项 A13）和分页证据查询（A14）。
  启动时把整轮输入冻结下来：已完成的 Fix 轮次、当前接受的 HEAD 与私有快照、
  规则与解析与过滤的版本号、复核 revision，以及观察截止时间。
- 新增基于 Git blame 的缺陷引入行追溯。只对唯一父提交的删除行和替换行执行受监督的 `git blame`；
  指向直接父提交算合法结果，根提交、merge 提交，以及内容被过滤略过的情况一律明确记为 Unknown，
  不做猜测。
- 新增可恢复的原子执行。输入固定，每 10 条证据连同进度在一个事务里原子提交；
  租约失效后后继 Worker 可以恢复，支持取消和重试，并有容量保护。
- 输出带「可用时间」的候选缺陷证据。查不到证据的一律是 Unknown。
- 明确不做：clean（干净提交）的成熟度判定和完整历史审计放到不可变数据集阶段；
  本批不推断任何负标签。

## Capabilities

### New Capabilities

- `baseline-szz`：以 Git blame 为基线的缺陷引入行追溯能力，包含输入冻结、可审计的追溯与过滤、
  可恢复的原子执行，以及带权限控制的查询接口。

### Modified Capabilities

没有。这次改动不改变任何已有能力的行为。

## Impact

- **数据库**：新增一次迁移，加三张表分别存 SZZ 轮次、追溯项和来源链接，并在仓库表上补 SZZ 的状态字段。
- **代码复用**：登录认证、任务与 outbox 事务框架、原生 Git 监督机制、既有的加锁依赖都沿用，
  这次改动不重复实现。
- **非目标**：不合并到 main 分支，不向远程 Issue 写入。
- **资源**：工程数据预计占用 D 盘 0.5～3 GiB，数据与构建的峰值另行估算。
- **关联追踪**：User Story US-05；验收项 A13～A14；测试 UNIT-SZZ、INT-SZZ、UI-SZZ。
