# Design: add-baseline-szz

## Context

开始做这次改动时，系统已经具备安全克隆与仓库接入、提交与文件变更解析、
Fix 证据识别与人工复核，以及通用的异步任务、心跳、检查点和重试框架。
也就是说，「哪些提交是修复提交」这一步已经能给出可信答案。

缺的是下一步：修复删掉的那些行，源头在哪里。

这次改动复用已经验收的认证与任务框架，只新增 SZZ 自己的业务逻辑，不重复实现框架。

## Goals / Non-Goals

**Goals:**

- 给定一轮已完成的 Fix 判定，产出可追溯、可审计的候选缺陷引入行证据。
- 保证同一轮 SZZ 的输入在运行期间不被改动，结果可复现。
- 执行过程可中断、可恢复，恢复后不产生重复或矛盾的结果。
- 对外只暴露脱敏、分页、有权限控制的查询接口。

**Non-Goals:**

- 不做 clean（干净提交）的成熟度判定，不定义观察窗口 W，不做冲突与完整覆盖审核，这些属于不可变数据集阶段。
- 不推断任何负标签。查不到证据就是 Unknown，不等于「没有缺陷」。
- 不训练、不评估模型。
- 后续的数据集阶段必须同时限制事件时间和标签可用时间这两个口径，不能把「未知」当成 0。
  这次只负责把这两个时间点如实记下来。

## Decisions

### 决策 1：只接受已经冻结的 Fix 轮次

SZZ 启动时，只接受与仓库当前接受的 HEAD 和快照一致、并且已经完整结束的 Fix 轮次。
启动事务先锁仓库，再锁这一轮底下的全部判定，加锁顺序固定，避免死锁。

冻结的内容包括规则候选、复核状态、revision、创建与复核时间，以及全部证据摘要。

为什么要这么做：Fix 判定本身是可以人工复核的，复核会改动复核状态。
如果 SZZ 跑到一半复核被改了，同一个 SZZ 的结果就和当时的输入对不上，也没法复现。
冻结之后，复核变更只能体现在新一轮 SZZ 里。

### 决策 2：时间语义

- 观察截止时间默认取数据库的 UTC 时间；调用方显式传入的时间必须带时区，而且不能在未来。
- 标签可用时间取这几个时间里的最大值：Fix 创建时间、判定创建时间、有效复核时间、
  Issue 观测时间、Fix 事件时间。
- 任何晚于观察截止时间才出现的输入，一律记为 Unknown。
  不允许用「当前状态」倒推历史。
- 高置信度的规则候选和人工确认分别保留来源标记，不声称人工已经确认了全部规则样本。

### 决策 3：Git 追溯与「什么算代码行」

追溯范围固定为 `baseline-szz-v1`：只认唯一父提交；merge 提交和根提交记为 Unknown。

- 只对解析完整的普通文本文件做逐行回溯，看它父版本里对应的行是谁写的。
- 使用解析阶段留下的文件和删除行信息，并和本地的 Git 数据核对。
- 默认只跟踪整个文件的重命名；不开启跨文件的行移动跟踪，也不调用任何外部工具。

过滤规则按语言区分，宁可保守也不误判：

| 语言 | 过滤规则 |
|---|---|
| 全部语言 | 只过滤真正的空行，不把 Python 的缩进空白和字符串里的空白当成空行 |
| Python | 把整个文件做一次语法分词，只过滤单独成行的注释；分词失败就一律记 Unknown |
| Java | 区分行注释和块注释，字符、字符串和文本块也各自识别；遇到 Unicode 转义、或者代码本身没闭合，一律记 Unknown |
| 其它语言 | 本批只过滤空行，这是明确的限制 |

不启用那种可能吞掉代码的通用正则。

以下情况保留 Unknown 或明确标记为排除：文档路径、submodule 与符号链接、
二进制、编码异常、超大小、超数量、状态有歧义。
新增文件没有旧行；删除文件回溯到旧路径。
代码行只保存 SHA256，不保存作者邮箱，也不保存原始的 blame 输出。

### 决策 4：证据与标签的边界

保留的字段有：修复提交的 SHA、父提交 SHA、旧路径与行号、blob 与行摘要、来源 SHA 与原始行、
Git 路径表示。

给出 candidate_buggy 需要三条同时满足：

1. 输入可见性——来源在接受的 HEAD 可达、且解析版本相同的集合里；
2. 来源覆盖——来源已验证是父提交的祖先；
3. 时间条件——如果时钟倒退导致来源事件晚于修复事件，记为 Unknown。

标签可用时间随证据一起保存。它是算法候选，不等同于人工真值。

以下几种情况不会自动生成 clean：没有旧代码行、状态未知、不是候选。
负例成熟度、观察窗口 W、以及冲突与完整覆盖审核，都留给数据集 change。

### 决策 5：并发读必须在同一个快照下

MySQL 在这个隔离级别下，创建事务里的幂等查询可能先读到一份较早的数据快照，
之后才等到仓库锁、拿到 Fix 的最终发布状态。

隐患在于：后面读 Fix 轮次和判定时看到的是最新已提交的状态，
如果查证据时用的还是前面那份旧快照，两边就对不上。

做法是让查证据也读最新状态，不混入旧快照。
特征和 SZZ 一起修正这一处，并用受控的双事务时序用例验证：
晚发布的证据摘要和标签可用时间被完整冻结，同时不改变已有轮次和追溯算法。

### 决策 6：执行、原子性与资源保护

表结构是 szz_run、szz_item、szz_link 三张表。
item 在启动时就把冻结输入存下来；结果只在批次提交时才落库。

- 每 10 项提交一次：唯一链接、结果、检查点和进度在同一个事务里提交；最后的批次带上成功审计。
- 拒绝旧令牌、过期租约、非最新任务、非根任务、版本不符和哈希不符。
- 失败回执不覆盖已经成功的结果。
- 互斥关系：SZZ 与同步、Fix 互斥；Fix 复核可以并行，并行时旧输入不变。
- 复用已有的 blob、diff、索引、输出和 deadline 保护机制。
- 每个修复最多 10000 条待追溯行；超出部分保留 Unknown，
  同时保留其它文件已经完成的证据，不伪造「完整覆盖」。
- 启动时和每一批都检查：512 MiB 增长额度和 2 GiB 紧急余量。D 盘不足就停止，不转移到 C 盘。
- 接口每页最多 100 条。对外返回的数据里不含快照路径、令牌、邮箱或源码。
- 证据只在本机脱敏留存。

## Risks / Trade-offs

| 风险 / 权衡 | 说明 |
|---|---|
| 其它语言只过滤空行 | Java 和 Python 之外的语言，注释行会被当成代码行，可能产生假证据。这是本批明确接受的限制。 |
| 每个修复 10000 行的上限 | 超大提交没法完整覆盖。选择保留 Unknown 加已完成的证据，而不是伪造完整覆盖。 |
| 不使用 `-M` 和 `-C` | 只做整文件重命名跟踪，跨文件移动的代码可能追不到源头，结果偏保守。 |
| 一律记 Unknown，不推断 clean | 负例样本会不足，训练数据更瘦，但避免了把「没查到」错当成「没问题」。 |
| 证据只在本机脱敏留存 | 便于审计但不可共享，换一台机器复现需要重跑。 |
| 冻结输入导致复核之后必须重跑 | 多一次计算开销，换来结果可复现。 |

## Validation

- 真实 Git 的 golden 用例，MySQL 与迁移验证。
- 并发、权限、幂等、冻结、时间边界、有限历史和空库。
- 故障注入、真实 Worker 强杀、后继恢复。
- 独立新卷的浏览器验收。

规则依据：

- [Git blame](https://git-scm.com/docs/git-blame)
- [Python tokenize](https://docs.python.org/3.11/library/tokenize.html)
- [Java 词法边界 JLS](https://docs.oracle.com/javase/specs/jls/se21/html/jls-3.html)

Java 部分只做词法判断，不是编译器级的语义验证，有歧义的输入不当作 clean。
