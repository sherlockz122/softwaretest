## 1 分支策略

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 维护者负责的分支 | 合并和维护不属于本开发任务，不向其写入 |
| `wang` | 用户指定的开发及团队同步对照基线 | 小步提交，仅推送 origin/wang，保持可构建和可测试 |
| `feature/<us-id>-<slug>` | 单个故事或紧密相关任务 | 从 `wang` 创建，完成后通过 PR 合入 `wang` |
| `fix/<issue-id>-<slug>` | 缺陷修复 | 从目标基线创建，PR 关联缺陷和回归测试 |

不新增长期 `develop` 分支。若团队规模或发布节奏变化，需要通过文档决策和 PR 修改本规则。

用户指定当前有效规格、规划和已验收实现为团队后续同步标准；不等待或迁就外部旧文档，不假定其它分支已同步。本阶段仅维护wang和本机环境，main及其它分支职责由维护者承担。非作者PR评审要求保留，个人提交不冒充其证据。外来材料按 [隔离决策](decisions/2026-10-14-基线权威与外来材料隔离.md) 处置。

## 2 提交与 PR

提交信息采用 `type(scope): subject`，例如：

```text
feat(szz): persist line-level blame evidence
test(features): add hand-calculated entropy fixture
docs(US-01): clarify repository URL validation
```

PR 标题包含 User Story，例如 `feat(US-05): implement baseline SZZ`。PR 正文必须包含：

- User Story 和 OpenSpec change/task；
- 改动范围与非目标；
- 测试命令和结果；
- API、数据迁移及兼容性影响；
- 安全和隐私检查；
- 截图或演示证据（涉及 UI 时）。

合并前至少一位非作者审阅。不得为通过检查而删除或降低有效测试。

## 3 OpenSpec 工作流

每个 change 按以下顺序推进：

`proposal → specs → design → tasks → implementation/test → verification → archive`

规则：

1. 编码前必须存在可验收的正常、异常和边界场景。
2. tasks 拆分为可以独立验证的工作，不使用“完成模块”之类不可核验描述。
3. 实现过程中发现规格错误时先更新 change，不允许只改代码。
4. 只有实现、测试和证据齐备后才能归档。
5. 归档后当前规格必须与实际产品一致。

计划 change：

|---|---|---|
| `bootstrap-application` | 工程、最小认证、可靠任务与运行验收；第五阶段已归档 | S0 |
| `add-data-collection` | US-01～US-04 | S0/S1 |
| `add-baseline-szz` | US-05候选证据已实现；成熟度由feature-dataset继续 | S1 |
| `add-feature-dataset` | US-06～US-10 | S1/S2 |
| `add-public-dataset-audit` | 第十四阶段真实公开数据/历史评估适配前置审计，已建立独立规格 | 滚动前置批次 |

## 8 需求变更

需求变更流程：

1. 描述问题、价值和影响范围；
2. 更新或新建 OpenSpec change；
3. 更新受影响的 `docs/` 文档和追踪矩阵；
4. 评审范围、兼容性、迁移和测试；
5. 通过 PR 合并后实施；
6. 验收后归档 change。

紧急修复可以缩短评审周期，但不能跳过规格、测试和证据补录。
