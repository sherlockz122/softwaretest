# DefectGuard 开发协作与迭代计划

## 1 分支策略

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 稳定、可演示基线 | 禁止直接推送，只接受阶段验收 PR |
| `wang` | 当前个人独立开发基线 | 允许个人小步提交，仅推送 origin/wang，保持可构建和可测试 |
| `feature/<us-id>-<slug>` | 单个故事或紧密相关任务 | 从 `wang` 创建，完成后通过 PR 合入 `wang` |
| `fix/<issue-id>-<slug>` | 缺陷修复 | 从目标基线创建，PR 关联缺陷和回归测试 |

不新增长期 `develop` 分支。若团队规模或发布节奏变化，需要通过文档决策和 PR 修改本规则。

当前 `wang` 的文档和实现尚未与团队同步，上表的团队协作流程属于后续协作约定建议。本阶段不向 `main` 或其他分支推送、合并或覆盖内容；是否合入 `main` 由维护者另行决定，不属于当前个人开发职责。个人试开发提交不等于完成课程要求的非作者 PR 评审证据。

## 2 提交与 PR

提交信息采用 `type(scope): subject`，例如：

```text
feat(szz): persist line-level blame evidence
test(features): add hand-calculated entropy fixture
docs(US-01): clarify repository URL validation
```

PR 标题包含 User Story，例如 `feat(US-05): implement baseline SZZ`。PR 正文必须包含：

- User Story 和 OpenSpec change/task；
- 改动范围与非目标；
- 测试命令和结果；
- API、数据迁移及兼容性影响；
- 安全和隐私检查；
- 截图或演示证据（涉及 UI 时）。

合并前至少一位非作者审阅。不得为通过检查而删除或降低有效测试。

## 3 OpenSpec 工作流

每个 change 按以下顺序推进：

`proposal → specs → design → tasks → implementation/test → verification → archive`

规则：

1. 编码前必须存在可验收的正常、异常和边界场景。
2. tasks 拆分为可以独立验证的工作，不使用“完成模块”之类不可核验描述。
3. 实现过程中发现规格错误时先更新 change，不允许只改代码。
4. 只有实现、测试和证据齐备后才能归档。
5. 归档后当前规格必须与实际产品一致。

计划 change：

| Change | 范围 | 目标 Sprint |
|---|---|---|
| `bootstrap-application` | 工程、最小认证、可靠任务与运行验收；已创建，准备完成后实施 | S0 |
| `add-data-collection` | US-01～US-04 | S0/S1 |
| `add-szz-labeling` | US-05、标签成熟度和证据链 | S1 |
| `add-feature-dataset` | US-06～US-10 | S1/S2 |
| `add-model-evaluation` | US-11～US-15 | S1/S2 |
| `add-review-prediction` | US-16～US-19 | S2 |
| `add-dashboard-governance` | US-20～US-23 | S2/S3 |

## 4 Sprint 计划

| 阶段 | 目标 | 可演示增量 | 不纳入本阶段 |
|---|---|---|---|
| Sprint 0 第 1～3 周 | 需求、设计、仓库与规格基线；小数据技术探针 | 当前文档集、追踪矩阵、修订后的 `add-data-collection`、小仓库解析探针 | 大仓库全量、8 模型 |
| Sprint 1 第 4～6 周 | 首条历史数据 MVP | 最小登录与权限、限定提交窗 → 解析 → baseline SZZ → Kamei 14 → 时间切分 → LR/RF → 指标 → 历史风险列表 | 完整用户管理页面、全量大仓库、完整 SHAP UI |
| Sprint 2 第 7～9 周 | 核心指标和合入前场景 | 8 模型、语义输入、双类指标、校准、解释、候选预测、趋势和任务页 | 低价值附加功能 |
| Sprint 3 第 10～14 周 | 功能冻结、测试与加固 | 安全/可靠性/性能证据、E2E、缺陷闭环、OpenSpec 归档；必要的管理能力 | 未评审的新功能 |
| Final 第 15～16 周 | 验收与答辩 | 可运行系统、测试报告、代表性 change 全链路、演示脚本 | 新功能 |

## 5 容量和优先级规则

- 故事点只表示相对复杂度、风险和工作量，不换算固定人日。
- Sprint 只承诺团队平均速度约 80%，其余容量用于联调、缺陷和文档。
- Sprint Review 后根据实际速度重估剩余 Backlog，并同步看板与 OpenSpec。
- 课程 Must 未完成前不启动 P2 模型或高保真视觉优化。
- 先在小仓库和限定提交窗口验证正确性，再扩大数据规模。

## 6 CI/CD

PR 阶段执行格式、静态检查、单元/集成测试、算法 fixture、OpenAPI 漂移、OpenSpec 校验、前端构建和依赖安全扫描。

合入 `main` 后构建带代码 SHA 的镜像或工件，并在配置了演示环境时执行部署和冒烟测试。模型全量训练作为独立任务运行，不阻塞普通 PR。

## 7 项目管理与周报

- 看板卡片必须标注 User Story、Sprint、OpenSpec change/task、负责人和状态。
- 推荐状态为 `Backlog → Specified → Implementing → Verifying → Done`。
- 每周五周报记录已完成、下周计划、阻塞、风险和需要决策的事项。
- 缺陷使用 Issue 或等价工具管理，并关联测试、提交和 change。
- 个人贡献以提交、PR、评审、任务、测试和文档记录共同证明。

## 8 需求变更

需求变更流程：

1. 描述问题、价值和影响范围；
2. 更新或新建 OpenSpec change；
3. 更新受影响的 `docs/` 文档和追踪矩阵；
4. 评审范围、兼容性、迁移和测试；
5. 通过 PR 合并后实施；
6. 验收后归档 change。

紧急修复可以缩短评审周期，但不能跳过规格、测试和证据补录。

## 9 当前风险和处理

| 风险 | 处理策略 |
|---|---|
| 大仓库采集和 SZZ 超时 | 先小仓库和固定窗口；批量、checkpoint、缓存和限流 |
| SZZ 噪声与标签右截尾 | 证据分级、人工抽样、Unknown、观察窗口和版本化 |
| 类别不平衡导致指标虚高 | PR-AUC、MCC、PofB20、Popt；采样只在 train |
| 深度模型缺少真实语义输入 | Sprint 2 交付最小 tokenizer 和 TextCNN；不冒用 DeepJIT 名称 |
| 非功能验证过晚 | S1/S2 同步建设幂等、安全和性能探针，S3 正式验收 |
| 文档与实现漂移 | OpenAPI/迁移/OpenSpec CI 检查和追踪矩阵复核 |

## 10 开发启动门槛

开始具体 change 实现前应满足：

- 团队共享实施前本文档集应被团队确认；当前仅在个人 `wang` 试开发，用户已授权本分支基线，不冒称团队已确认；
- change 包含 proposal、specs、design 和 tasks；
- 正常、异常与边界验收场景完整；
- 技术依赖和本地运行方式明确；
- 对应测试 fixture 和证据位置已规划。

当前先完成 `bootstrap-application` 的第 0 组准备，再按工程 → 认证 → 可靠任务 → 页面与实际 E2E 的顺序实施。通用 async_task、outbox 和 A29～A32 由该 change 唯一负责；后续采集、训练和治理 change 复用它，只增加各自业务 payload、checkpoint 和页面内容。[存储预算](development/存储预算与命令使用.md) 是本机实施前置条件。
