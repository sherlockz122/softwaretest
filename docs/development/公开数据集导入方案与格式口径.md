# 公开数据集导入方案与格式口径

## 1. 这份文档解决什么

「可加载已有公开数据集」这条需求要的不是又一个下载脚本，而是一句话能回答的问题：手上这份公开数据能不能进产品，进了以后按什么口径使用。

下面先把已经存在的三段链路和它们的限制写清，再给出原文与派生的格式、口径规则、导入路径的选型与备选、适配器声明草案与体检失败码。

## 2. 现状：三段链路与它们的限制

| 环节 | 入口 | 做什么 | 限制 |
|---|---|---|---|
| 取得 | `scripts/fetch_public_dataset.py` | 按固定超文本传输协议（HTTPS）来源与固定修订下载两个表、许可文本、上游预处理源码与发布元数据 | 只认 ApacheJIT 一种来源；来源地址与大小、摘要写死在模块常量里 |
| 审计 | `scripts/audit_public_dataset.py` | 检查结构、键、数值、时间、许可与项目分组，输出可用性与诊断 | 文件名与列名写死；结论落在报告文件里，不进资产 |
| 导入 | `packages/mining/public_assets.py` 的导入函数 | 校验来源后把目录封装成内容寻址资产，派生逐行归一化文件与质量文件 | 来源校验由专项命令注入；能力位是模块常量，不是资产自带 |

应用侧只有一个入口：创建数据集时引用已有资产的标识与来源摘要。也就是说，用户能挑到哪份数据，取决于运维此前把什么放进了资产库。换一个公开数据集，今天没有入口。

## 3. 原文格式

### 3.1 主表 `apachejit_total.csv`

十八列，逗号分隔，表头必须与下列顺序完全一致，多一列少一列都算结构不符。

| 序号 | 列名 | 含义 | 校验 |
|---|---|---|---|
| 1 | `commit_id` | 提交编号 | 与日期表按（第 1 列，第 2 列）联合做行键 |
| 2 | `project` | 项目标识，形如 `apache/activemq` | 决定项目分组与单类组排除 |
| 3 | `buggy` | 发布标签，布尔文本 | 只接受两种取值，解析后必须两类齐备 |
| 4 | `fix` | 发布侧的修复元数据，布尔文本 | 是元数据，不是产品口径的确认修复 |
| 5 | `year` | 发布方的年份分层字段 | 只作分层，不参与时间切分 |
| 6 | `author_date` | 作者时间，秒级时间戳 | 唯一允许用于时间切分的列 |
| 7～18 | `la` `ld` `nf` `nd` `ns` `ent` `ndev` `age` `nuc` `aexp` `arexp` `asexp` | 十二个数值特征 | 必须有限且非负；小数照原样保留 |

十二个数值列是本来源的口径，不是产品的十四维口径：其中没有 `lt`，`ent` 与计数的语义也与产品侧不同。填零或改名接进产品特征列会造出含义错位的训练输入，只能作为外部研究输入使用。

### 3.2 日期表 `apachejit_date.csv`

八列：`commit_id`、`project`、`bug_date`、`fix_date`、`buggy`、`fix`、`date`、`year`。行键与主表一致，参与判定的列是标签与修复标记，两表必须完全对齐，既不能有主表缺失的键，也不能有日期表缺失的键。

`bug_date` 与 `fix_date` 的原始记录里存在无时区与自相矛盾的情况，审计把这些记成诊断而不静默改写；时间切分一律用主表的 `author_date`。

### 3.3 伴随文件

`acquisition.json` 记录首次取得的真实时间，`zenodo-record.json` 是发布元数据，`neurojit-LICENSE.txt` 与 `neurojit-data_utils.py.txt` 固定许可与上游预处理源码。导入时这些文件随源一起进清单，许可校验读的是这几份文件而不是代码常量。

## 4. 派生格式

导入完成后，资产目录按内容寻址命名，内含四类文件：

| 路径 | 内容 |
|---|---|
| `source/` | 原文副本，逐文件摘要与大小进清单 |
| `normalized.jsonl` | 一行一条归一化记录，每行是规范化的 JSON 文本 |
| `quality.json` | 行数、标签分布、审计摘要、数值列清单、能力位、限制与语言范围 |
| `manifest.json` | 文件清单、来源取得信息、质量文件摘要、资产标识与内容哈希 |

归一化记录包含十七个字段，其中对外展示与训练用到的关键几项是：`commit_id`、`canonical_repository`、`sample_granularity`（当前恒为提交粒度）、`event_epoch` 与 `event_clock`、`published_label` 与 `label_confidence`、`numeric12` 与 `published_fix_metadata`。其余字段现在取固定值或空值，作用是显式声明缺口：`label_available_at` 为空表示没有可核验的标签可用时间，`defect_types` 与 `location` 为空、`type_status` 为 `unknown`、`languages` 为空且 `language_status` 为 `per_row_unverified`。

质量文件里的能力位把能做什么与不能做什么一次说清：原始存档与归一化已完成，研究数据集就绪、语义、历史回放、候选发布、类型预测与定位全部为未完成。限制清单逐条列出弱监督标签、非真实在线模拟、负例覆盖未认证、语言与类型未认证、预处理与模型未在此步骤发生、跨源重叠未核验。

## 5. 口径规则

1. 行粒度是提交。同一个（项目，提交）组合只能出现一次，重复即拒绝。
2. 三层项目名（`apache/hadoop`、`apache/hadoop-hdfs`、`apache/hadoop-mapreduce`）归并成同一个规范仓库名，避免同一仓库被切成三份。
3. 标签是发布方的弱监督结果，不是人工金标。能力位与限制清单都要保留这一点。
4. 修复标记是发布元数据，不能当成产品链路里经过证据与复核的确认修复。
5. 时间切分只用 `author_date`；同一时间戳的样本整组落在同一分区，不拆散。
6. 训练、验证、测试比例在创建数据集时显式声明，默认 70/15/15，不按结果调整。
7. 任一项目组只有一个标签时整组排除，并记录排除原因；其余组照常导入。
8. 每年份分层只用于统计，不参与切分，也不作为标签可用时间。
9. 能力位与限制清单随资产走。读取方按资产清单判定用途门槛，不按代码常量。

## 6. 导入路径的选型与备选

### 6.1 三条候选路径

| 路径 | 做法 | 成本 | 主要风险 |
|---|---|---|---|
| A 命令行导入 | 运维把已下载并审计过的目录交给导入命令，命令写资产并输出摘要 | 最低，复用现有审计与封装 | 需要人操作；不能从页面上点 |
| B 服务端拉取 | 应用按固定来源自行下载再导入 | 中，要做域名白名单、重定向校验、体积与时限 | 应用进程获得出网能力，攻击面变大 |
| C 应用内上传 | 浏览器上传压缩包，服务端解包校验后导入 | 高，要做临时目录、断点、压缩炸弹与病毒防护、失败回滚 | 安全与恢复逻辑一次扩到很大 |

### 6.2 结论

第一批做 A，并把规格与体检抽出来，使 B 与 C 将来只是新增一个触发入口而不是重写一遍导入。

选 A 的理由是这一批真正缺的是口径与入口的自证能力，不是交互形态。B 与 C 的安全面与恢复逻辑都足以单独立项，塞进第一批会把导入本身挤掉。

备选路径是先做 C。收益是演示更直观，代价是导入的核心契约还没定就先写上传，日后改口径要连上传接口一起改。

## 7. 适配器声明草案

一份规格描述一个来源，至少包含下列字段：

| 字段 | 说明 | 必填 |
|---|---|---|
| `source_id` | 来源标识，进入资产清单 | 是 |
| `files` | 原文文件名与各自角色（主表、日期表、许可、元数据、上游源码） | 是 |
| `columns` | 主表与日期表的列序，必须与声明完全一致 | 是 |
| `key_columns` | 行键列名，至少两列 | 是 |
| `event_column` | 事件时间列，且必须是唯一可用于切分的列 | 是 |
| `label_column` | 标签列与允许取值、解析规则 | 是 |
| `numeric_columns` | 数值特征列，需给出有限非负约束 | 是 |
| `license_source` | 许可文本文件名与允许的许可标识 | 是 |
| `cohort_aliases` | 需要归并的项目名映射 | 否 |
| `capabilities` | 该来源支持的能力位 | 是 |
| `limitations` | 该来源的限制清单 | 是 |
| `adapter_version` 与 `schema_version` | 规格与口径版本，写入资产清单 | 是 |

规格本身要进版本控制，资产清单记录它当时用的是哪个版本，这样同一份数据隔一年再导入也能说清当时的口径。

## 8. 体检五项与失败码

| 阶段 | 检查内容 | 失败码（拟定） |
|---|---|---|
| 结构 | 表头与列序、文件是否齐、编码是否可解码 | `PUBLIC_SCHEMA_INVALID` |
| 键 | 两表行键集合一致、键内无重复 | `PUBLIC_JOIN_MISSING`、`PUBLIC_JOIN_CONFLICT`、`PUBLIC_DUPLICATE_SAMPLE` |
| 数值 | 有限、非负、长度在界内 | `PUBLIC_NUMERIC_INVALID`、`PUBLIC_FIELD_LIMIT` |
| 时间 | 时间列可解析、时间戳非负 | `PUBLIC_TIME_INVALID` |
| 许可与来源 | 许可标识在允许集合内、来源记录摘要与实际文件一致 | `PUBLIC_LICENSE_UNVERIFIED`、`PUBLIC_SOURCE_DRIFT` |

另外两条与资源相关：单文件与总字节超限给 `PUBLIC_FILE_LIMIT` 与 `PUBLIC_BYTE_LIMIT`，超时给 `PUBLIC_DEADLINE`。任何一条失败都在创建资产目录之前停下，不留半份资产。

## 9. 待决问题

1. 第二个来源选哪个。候选分三类：同一发布者的扩展数据（列结构接近，适配最省）、另一套按提交粒度的公开缺陷数据（列语义不同，要重新定义能力位）、以及我们自己解析链路产出的仓库特征（它不是公开数据集，走解析任务而不走导入）。
2. 两个来源含同一条提交时怎么去重。需要先定优先级，否则训练集会把同一条提交算两遍。
3. 能力位要不要按来源分组成一张矩阵，还是继续每份资产自带一份。现在是一份一存，来源多了以后可能要看跨来源对照表。
4. 上传入口的安全边界。压缩炸弹、超大单文件、断点续传与失败回滚这四件要一起设计，否则做出来的入口不敢开给人用。

## 10. 重跑与核对

真实来源的下载与审计按既有命令重跑，本文引用的行数与标签分布以审计输出为准：

```powershell
.\.venv\Scripts\python.exe -m scripts.fetch_public_dataset
.\.venv\Scripts\python.exe -m scripts.audit_public_dataset --output runtime\acceptance\stage14\public-audit.json
```

导入与资产核对：

```powershell
.\.venv\Scripts\python.exe -m scripts.public_asset --help
```

字段名与常量要对得上时看两个文件：`packages/mining/public_dataset.py` 的列定义与审计规则，`packages/mining/public_assets.py` 的导入、归一化与清单结构。
