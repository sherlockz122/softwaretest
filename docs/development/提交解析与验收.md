## 使用与恢复

1. 按 [工程启动](工程启动与验收.md) 重建 API/Worker 共用镜像；运行 maintenance migrate 到 `0005_repository_sync` 后启动 full。不要 stamp、手工建表或降级正常开发库。
2. Member/Admin 在已克隆仓库详情选择提交窗口：留空表示克隆时 HEAD 的全部可达历史，N 表示按 committer time/SHA 排序后的最近 N 条。首个窗口固定后不能用另一 key 改写；失败/取消通过当前任务 A31 重试。
3. 页面显示已提交批次数量、总数、规则版本、提交列表及文件状态。只有全部窗口提交成功后才显示解析完成；空仓库成功为 0/0。部分入库可供检查，不能当成完整训练输入。
4. 超过执行时间（默认1800秒，可显式配置 `DG_REPOSITORY_PARSE_TIMEOUT_SECONDS`）或资源限制返回稳定分类码；不自动删库/删 Git 数据、放宽限制或改盘。租约中断默认最多三个 successor；同键重放不会新建窗口。

## 固定策略 native-pydriller-v1

- 原生 Git rev-list 固定 HEAD，再按 committer epoch asc、SHA asc 稳定排序。author/committer UTC 时间及原始分钟偏移均保存；父 SHA 按 Git 原顺序保存，不要求父提交在窗口或时间排序前面。
- 作者采用email-normalized-v1：有效UTF-8邮箱trim/casefold后SHA-256；无效编码按strip/ASCII lower后的原始字节哈希，并在身份键中区分raw/UTF-8，防止替换字符合并不同作者。无邮箱按名字同规则建键，版本与键唯一。显示名保留首个别名（最多256字符），不保存原始邮箱，不应用mailmap/隐式别名合并。哈希减少直接暴露，不声称匿名化；Git原始数据仍含公开作者信息。特征阶段需要独立版本化别名规则。
- metadata/commit object最多1MiB；扫描输出最多32MiB，文件索引4MiB，单提交最多4096个文件记录。超限明确失败，保留已有checkpoint，不暗中截断整个历史。窗口参数最多10000000只是请求边界，不是默认导入上限。
- 非 merge 使用 Git diff-tree 的 root/唯一父、50% rename、rename 候选阈值1000，不执行 external diff/textconv。merge 保存消息/父关系，`merge_skipped`，不存歧义的 combined diff；后续 SZZ 默认跳过 merge，别的策略必须新版本。
- NUL 分隔 raw/numstat 保留重命名、删除、Unicode、tab/newline路径；路径显示使用UTF-8，原始双路径的哈希和blob SHA保留以免替换字符造成身份碰撞。索引 ordinal 唯一。符号链接仅作为blob读取，不检出/跟随；submodule 明确记录状态。
- LA/LD 来自 Git numstat，二进制为 null；原 LOC 是父blob物理行数（包含最后一行无换行，不是 Lizard有效代码行数）。blob >1MiB、diff >256KiB、单提交累计保留diff >1MiB分别记 `blob_limit`、`diff_limit`、`commit_diff_limit`，不存部分patch。UTF-8不兼容文件记 encoding；涉及多文件的路径 patch 记 ambiguous_patch。二进制记 binary，不伪造零行数。
- 保存完整受限patch（含尾空白），PyDriller 2.12 仅处理该patch的hunk行号；不使用其不受本项目进程监管的 Repository 遍历器、内容/复杂度属性。禁止全局/系统配置、replace object、可选锁、网络协议；不检出代码，不运行hook/仓库脚本。所有命令有同一deadline、输出上限、磁盘检查和租约心跳，原输出不进入日志/API。
- 每10个提交一个事务：作者/commit/file upsert + checkpoint processed/last SHA + task counts；最后批次连同成功状态/审计同事务。checkpoint保存HEAD、窗口、规则版本、plan hash/总数，与root任务链绑定。每个业务写入检查 execution_token、有效lease、状态、latest task/root；旧worker无权修改。恢复时复算plan并校验最后SHA，不删以前批次。数据库提交回执丢失也保留已提交数据。

## 资源与复验

启动/每命令/每批次检查共享D盘可用空间，要求512MiB下一轮增长预算+2GiB余量；命令包装器另外按构建/测试实际峰值检查。Parser只删除自己的UUID临时目录，永不清理已发布bare。Docker/WSL继续位于D，fresh使用独立D路径和新卷。空间不足提前停止，用户补足后可重试；禁止C盘自动回退。

本机使用项目Python 3.11、`DG_DOCKER_EXE`绝对路径、`PYTHONUTF8=1`与D盘包装器运行 `pytest tests/test_parsing.py`。完整后端含runtime故障回归；`Test-FreshEnvironment.ps1 -Browser`复验真实公开GitHub clone→Worker parse→页面持久读取。本机复用Edge，Linux CI用Chromium；不跳过真实网络失败。JUnit/log/截图/manifest在 `runtime/acceptance/stage7`，仅本机脱敏留存，不上传artifact。

## 后续必须遵守

同步不得原地改写本次bare/窗口；新HEAD用独立快照与祖先检查，强推进入requires_review，不能删除已入库历史。更改身份/merge/diff/排序规则要新版本和可审计重算方案。Fix只产生证据，不把未解析/略过内容当作clean；Kamei不能将最近N窗口当作完整作者/文件历史，数据集必须检查覆盖度、成熟度和版本。SZZ单独change，真实容量探针决定扩大规模，质量不足时不能靠磁盘充足代替CPU/内存检查。
