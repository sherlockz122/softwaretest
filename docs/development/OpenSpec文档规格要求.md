# OpenSpec 文档规格要求

本文说明 `openspec/changes/` 下每个 change 的文档**必须长什么样**，
以及为什么长这样。汇报时若被问到"你们的变更文档是怎么组织的"，可以直接照本文回答。

规格来源：`openspec/config.yaml` 与 OpenSpec CLI v1.4.1 的 `spec-driven` schema 模板。
**校验命令**（项目根目录执行）：

```bash
openspec validate --all --strict
```

当前状态：**9 passed, 0 failed**（8 个活动 change + 1 个 spec）。

---

## 1. 一个 change 由哪些文件组成

```
openspec/changes/<change-name>/
├── proposal.md          ← 为什么做、做什么、影响什么
├── design.md            ← 怎么做，为什么这么选
├── tasks.md             ← 拆成可勾选的实施项
└── specs/
    └── <capability>/
        └── spec.md      ← 这个 change 新增/修改的正式行为契约
```

- **一个 change 一件事**。`add-` 是新增能力，`optimize-` 是性能类改造，名字用短横线小写。
- `proposal.md` / `design.md` / `tasks.md` **三件套必填**。
- `specs/` 只在**行为契约发生变化**时才需要；纯重构可以没有。

## 2. 语言与写作风格

### 2.1 语言规则

来自 `config.yaml` 的 `locale` 设置：

| 部分 | 语言 |
|---|---|
| **结构标题**（`## Why`、`## ADDED Requirements`、`### Requirement:`、`#### Scenario:`） | **英文**，不得翻译 |
| **判定关键词**（`SHALL` / `MUST` / `**WHEN**` / `**THEN**` / `**AND**`） | **英文**，必须加粗 |
| **正文、标题名、说明** | **中文** |

例如：

```markdown
### Requirement: 仓库克隆            ← "Requirement:" 英文，能力名中文
系统 SHALL 支持……                   ← 判定词英文，句子中文

#### Scenario: 不安全 URL             ← "Scenario:" 英文，场景名中文
- **WHEN** URL 使用非允许协议         ← 关键词英文加粗，内容中文
- **THEN** 系统在建立连接前拒绝请求
```

### 2.2 写作风格

模板只规定骨架，正文要写成正常的中文。下面几条是这套文档的硬要求。

**写完整的句子。** 主谓宾齐全，该有的连接词补上，不要写成名词短语堆叠的电报体。

- 不好：*「重试读取 checkpoint 并执行 upsert，不先删除已成功的数据。」*
- 好：*「重试时会读取检查点，用 upsert 覆盖写入，不会先把已经写成功的数据删掉。」*

**尽量少加粗。** 加粗只留给真正需要强调的地方。
一整段里每个技术名词都加粗，等于什么都没强调，读起来像一堵标签墙。
每份文档正文里的加粗控制在个位数。

**英文标识符要么不出现，要么先解释。**
字段名、接口路径、迁移编号、版本号和测试编号可以出现，
但第一次出现时要用中文说清它是什么，也不要连着堆三个以上。纯粹为了显得专业的缩写直接删掉。

- 不好：*「异步 `task(type, scope_key, idempotency_key)` 唯一；同键异载荷返回 409。」*
- 好：*「异步任务按「任务类型 + 作用域 + 幂等键」唯一；同一个幂等键配上不同请求内容时返回 409。」*

**编号可以当索引，不能当句子骨架。**
`A07`、`UNIT-FEAT-01`、`0007_szz` 这类编号在追踪矩阵和测试项里有用，保留；
但正文要靠文字把逻辑讲清楚，不能指望读者去查编号表。

**引号别滥用。** 用「」强调一个术语就够了，不要整段都在打引号。

### 2.3 不该写进文档的内容

下面几类不属于变更文档，出现就是噪音：

- **免责声明。** 比如「上述任务全部完成不等于采集能力可用于算法层」
  「本 change 的个人验收不代表团队审批通过」「本清单不宣称本阶段已完成」。
  这些是汇报时嘴上说的话，不是设计文档的内容。
- **状态指路。** 比如「具体状态见 `tasks.md`」「详见遗留问题表」。文档本身就该写清楚状态。
- **后续工作的指路牌。** 比如「后续接入 v2 在线持久化、数据集迁移 A17～A19，详见遗留问题表」。
  确实要划边界，就在 `Non-Goals` 或 `Impact` 的「不在本次范围内」里用一句话说清楚。
- **用阶段编号当标题。** 比如 `## 第十二阶段：特征纵向集成`。分组标题写内容，不写它是第几个阶段。
- **流程信息。** PR 审批、分支合并、CI 状态这类不进任务列表。

## 3. proposal.md

### 3.1 规范骨架

```markdown
# Change: <change-name>          ← H1 固定格式，必须与目录名一致

## Why                            ← 为什么需要这个变更
## What Changes                   ← 改了哪些东西（要点列表）
## Capabilities                   ← 新增/修改了哪些能力
### New Capabilities
### Modified Capabilities
## Impact                         ← 数据库、后端、范围、追溯关系
```

### 3.2 各节写什么

- **Why** —— 要回答"**不做会怎样**"。不是复述需求，而是讲清楚当前的缺口与代价。
  例：*"当前系统没有任何数据入口，模型训练无从谈起。"*
- **What Changes** —— 用短句列点，每条一个可验证的改动。
- **Capabilities** —— `New Capabilities` 列出本 change 引入的能力名（与 `specs/` 下的目录名对应）；
  `Modified Capabilities` 列出被改变行为的已有能力。**没有就明确写"无"，不要留空。**
- **Impact** —— 分 **数据库 / 后端 / 存储资源 / 不在范围内 / 关联追踪** 写。
  关联追踪要给出 User Story 编号、基线编号、受影响文档链接。

## 4. design.md

### 4.1 规范骨架

```markdown
# Design: <change-name>          ← H1 固定格式

## Context                        ← 背景与约束
## Goals / Non-Goals              ← 目标与非目标（Non-Goals 是防误解的关键）
## Decisions                      ← 关键决策
### 决策 1：……
### 决策 2：……
## Risks / Trade-offs             ← 风险与权衡
## Validation                     ← 怎么验证
```

### 4.2 各节写什么

- **Context** —— 依赖了什么、复用了什么、边界在哪。**明确说明本 change 不重复实现的既有能力。**
- **Goals / Non-Goals** —— Non-Goals 尤其重要：它防止别人以为"没写就是没做"或"写了就该做"。
- **Decisions** —— 每条决策写**选择 + 理由 + 约束**。
  必须覆盖的几类（`config.yaml` 强制要求）：
  - **数据与存储**：表结构、唯一约束、事务边界
  - **失败与恢复**：可重试 / 不可重试、checkpoint、租约栅栏
  - **安全**：输入校验、凭据、网络边界
  - **资源与容量**：限额、余量检查、降级策略
- **Risks / Trade-offs** —— 用表格：**风险/权衡 | 说明**。
  要写真实代价（例："Worker 并发为 1 → 吞吐受限，换取资源可控"），不要只写"风险已缓解"。
- **Validation** —— 列具体验收手段：单元 / 集成 / 浏览器 / 规模探针 / 新卷验收。

表格是允许且推荐的；标题编号用**中文**（`### 决策 1：幂等与事务`）。

## 5. tasks.md

### 5.1 规范骨架

```markdown
# Tasks                           ← H1 固定，无名称

## 1. <分组名>                     ← 分组编号必须从 1 开始、连续
- [ ] 1.1 <任务>
- [x] 1.2 <已完成任务>

## 2. <分组名>
- [ ] 2.1 <任务>
```

### 5.2 规则

- 分组标题**必须是** `## <数字>. <名称>`，数字连续。
- 任务项**必须是** `- [ ] <分组号>.<序号> <描述>`，编号与所属分组一致。
- **只在证据完成后才勾选**（`- [x]`）。禁止"计划完成就勾"。
- 不要写 PR 审批、分支合并、CI 状态这类**流程信息**进任务列表。
- 文件末尾不要挂免责声明、状态指路或后续工作的引用块。任务列表写完就结束。

## 6. specs/<capability>/spec.md

### 6.1 规范骨架

```markdown
## ADDED Requirements                      ← 变更级 spec 从这一行开始，无 H1

### Requirement: <能力行为名>
系统 SHALL <可验证的行为陈述>。
（可续行补充 SHALL / MUST 约束）

#### Scenario: <场景名>
- **WHEN** <触发条件>
- **THEN** <系统必须产生的可观测结果>
- **AND** <补充结果>

#### Scenario: <另一个场景>
- **WHEN** ...
- **THEN** ...
```

修改已有能力时用 `## MODIFIED Requirements`；删除用 `## REMOVED Requirements`。

### 6.2 规则

- **一条 Requirement 下必须有至少一个 Scenario。** 没有场景的需求无法被测试，校验会失败。
- 场景类型要覆盖三类：
  1. **正常路径** —— 一切正常时发生什么
  2. **边界条件** —— 空值、上限、并发、中断
  3. **非法输入** —— 拒绝什么，返回什么错误
- `SHALL` 用于行为要求，`MUST` 用于强制约束，`SHOULD` 用于建议——**不要混用**。
- 条件与结果**必须是可观测的**。写不出可观测结果，说明需求还没想清楚。
- 场景名用中文，但**不要写"测试用例 1"这种编号式命名**，写清场景语义。
- 同一份 spec 里的场景**不得相互矛盾**。

## 7. 校验与查看

```bash
openspec validate --all --strict        # 严格校验全部 change
openspec validate <change-name> --strict # 只校验一个
openspec view                            # 交互式查看
openspec status --change <name> --json   # 查看某 change 的完成进度
openspec instructions <artifact> --change <name> --json  # 查看某个产物的填写说明
```

**`--strict` 会检查**：H1 格式、必需小节是否齐全、任务编号是否连续、
每条 Requirement 是否至少有一个 Scenario、关键词是否正确加粗。

## 8. 汇报时的常见问题

**Q：这些文档是 AI 写的吗？**
A：文档骨架由 OpenSpec 模板约束，内容是团队基于实际实现填写的。
规格（`spec.md`）是用 `openspec validate --strict` 机器校验的，
写错格式会直接报错——所以它的结构不是风格问题，是有格式约束的。

**Q：为什么 proposal / design / tasks 要分开？**
A：三者回答不同问题。`proposal` 回答**为什么做**，`design` 回答**怎么做**，
`tasks` 回答**做到哪了**。混在一起会导致"改了实现就顺手改了范围"，
而范围变更本该走一次评审。

**Q：变更完成后怎么办？**
A：`openspec archive <change-name>` 归档，`specs/` 下的契约会合并进主规格，
成为下一轮变更的基线。归档前必须 `validate --strict` 通过。

**Q：为什么文档里不写「本次验收不代表算法精度达成」这类话？**
A：那是汇报时口头要讲清楚的边界，属于结论和态度的表达，不是设计文档的内容。
文档要写的是「做了什么、为什么这么做、现在到哪一步」。
把免责声明写进文档，反而会让真正该写清楚的范围和状态被稀释掉——
范围该写在 `Goals / Non-Goals` 里，状态该由任务勾选体现。

## 9. 改前 / 改后对照

第 2 节那些要求已经写进两个 AI 每次都会读的地方：

- `openspec/config.yaml` 的 `context` 和 `rules`——OpenSpec 的工作流在动笔前会读它，
  并把它当作硬约束（可以自己跑 `openspec instructions proposal --change <名字> --json` 看到）。
- 仓库根目录的 [AGENTS.md](../../AGENTS.md)——Claude Code、Codex、Cursor、Copilot
  之类的工具会自己加载，`CLAUDE.md` 只是指向它。

所以不用指望谁记得住，规则是被自动读到的。下面这一节是拿来核对和讲给人听的：
左边这些都是本项目 `openspec/changes/` 里**真实出现过**的句子。

| 毛病 | 改前 | 改后 |
|---|---|---|
| 免责声明 | 本 change 保持活动状态。上述任务全部完成不等于采集能力可用于算法层。 | 整段删掉。任务列表写完就结束。 |
| 状态指路 | 具体状态见 `tasks.md`。后续接入 v2 在线持久化、数据集迁移 A17～A19，详见遗留问题表。 | 整段删掉。确实要划边界，就在 `Non-Goals` 或 `Impact` 里用一句话说清。 |
| 套话式声明 | 无。本 change 只是扩展框架任务的业务参数，不修改任何已有能力的规格级行为。 | 没有。这只是扩展框架任务的业务参数，不改变任何已经验收过的能力行为。 |
| 术语堆叠 | 迁移 `0007_szz`：新增 `szz_run`、`szz_item`、`szz_link` 三张表，并在 `repository` 上补状态字段 | 新增数据库迁移：建 SZZ 轮次、追溯项和来源链接三张表，以及仓库的 SZZ 状态，并验证降级可以安全回退 |
| 数字堆砌 | 本机生产代码全量运行：378 通过、1 个夹具失败；合计 379 个后端场景、20 个前端场景、15 个独立浏览器场景，共 414 个不同场景。 | 后端全量测试基本跑通，只有一个夹具因为断言里写的路径不对而失败，改掉之后安全相关的那一组也全部通过。 |
| 实现细节外泄 | `CloneExecutor` 通过 `GIT_CONFIG_*` 注入 `core.longpaths=true`；`DriveInfo` 测量可用空间 | 执行克隆的组件在 Windows 上给受控的 Git 命令单独打开长路径支持；磁盘可用空间仍然单独测量 |
| 空值直写 | 相关特征为 `null` 且有稳定原因 | 相关特征留空并给出稳定的原因 |
| 加粗墙 | 一个技术名词就是一处加粗，一段读下来全是标签 | 正文加粗控制在个位数，只留真正要强调的 |

其中能机器判的几条已经进了 CI。`python -m scripts.check_contracts` 会扫
`openspec/changes/` 下的文档（`archive/` 跳过，归档是历史记录），
命中免责声明、状态指路、用阶段编号当标题，或者正文加粗超过 10 处，就直接报错。
文风本身没法靠脚本判断，那部分靠第 2 节的要求和上面这张表。
