# 缺陷数据覆盖与缺口清单

## 1. 这份清单判什么

「完整的项目对应缺陷数据」有两种读法，两种都在这份文档里回答。

第一种读法：数据集里每一行提交，带不带完整的缺陷信息。本文第 2 节到第 5 节回答这个，结论是标签有了、证据与分类还缺。

第二种读法：工程自身记录的那些缺陷（看板缺陷管理表里的条目）与数据集里的提交行对不上。第 6 节单独说这件事。

两者不要混：前者说的是被挖掘数据集的标签质量，后者说的是我们自己在开发过程中发现的问题。

## 2. 逐行现在有什么

归一化记录共十七个字段，与缺陷相关的部分是下面这些。

| 字段 | 现在的内容 | 可靠程度 |
|---|---|---|
| `published_label` | `buggy` 或 `clean` | 发布方的 SZZ 弱监督结果，不是人工金标 |
| `label_confidence` | 固定文本，标明是弱监督 | 自描述，无进一步证据 |
| `label_available_at` | 空 | 没有可核验的标签可用时间，因此不能做双时间回放 |
| `event_epoch` 与 `event_clock` | 作者时间的 UTC 秒 | 主表 `author_date`，与日期表的 `date` 有多行不一致 |
| `published_fix_metadata` | 布尔 | 发布侧的修复元数据，不是产品口径的确认修复 |
| `defect_types` | 空 | 没有类型 |
| `type_status` | `unknown` | 显式声明类型未知 |
| `location` | 空 | 没有缺陷位置 |
| `languages` | 空，`language_status` 为逐行未验证 | 来源以 Java 为主，未逐行确认 |
| `semantic_available` | 假 | 没有语义输入 |
| `numeric12` | 十二个数值 | 有限非负，可作为外部研究输入；不是产品十四维 |

一句话概括：每一行都能回答「这条提交被发布方标成什么」，回答不了「它为什么有缺陷、缺陷在哪、属于哪一类、什么时候才能知道」。

## 3. 覆盖矩阵

| 缺陷信息维度 | 公开数据集 | 我们自己解析的仓库 | 证据位置 |
|---|---|---|---|
| 是否缺陷（二分类标签） | 有，弱监督 | 有，SZZ 与 Fix 证据链路 | `packages/mining/szz.py`、`fix.py` |
| 标签来源与时点 | 无可用时点 | 有 Issue 观测时间与复核状态 | `packages/mining/issues.py` |
| 修复提交与修复行 | 只有布尔的修复元数据 | 有逐行 blame 证据与候选行 | `packages/mining/fix.py` |
| 缺陷类型 | 无 | 无 | 能力位 `type_prediction` 为假 |
| 缺陷位置（文件或函数） | 无 | 无 | 能力位 `localization` 为假 |
| 严重度与影响面 | 无 | 无 | 无字段 |
| 语言 | 未逐行验证 | 有按文件的判定结果 | 特征质量页 |
| 负例覆盖是否完整 | 未认证 | 未认证 | 限制清单 |
| 是否为人工金标 | 否 | 否 | 限制清单 |
| 跨来源同一条提交去重 | 未认证 | 未认证 | 资产清单 `language_scope` 与限制清单 |

## 4. 现有数量口径

公开数据侧，第十四与第二十阶段的真实审计记录如下，都是既有测量结果，这次没有重新下载核对：完整 106,674 行，其中发布 `buggy` 28,239 行、`clean` 78,435 行；十五个项目字段组里十四个组的每个分区都有两类，`hadoop` 组全部为 clean 因而被排除，它的 11,964 行缺独立原始来源。十五个字段组归并成十三个规范仓库标识。

真实数据集落地时按声明比例切分为训练 74,672 行（clean 52,782、buggy 21,890）、验证 16,001 行（11,838、4,163）、测试 16,001 行（13,815、2,186），构建耗时 26.047 秒。

来源比较侧，原始链接 162,818 条，28,239 条 `buggy` 的缺陷时钟与选中修复时间全部与原链接吻合，其中 5,740 条不是原始最早修复；334 条 `clean` 同时出现在原始候选中；157 条原始链接的修复时间早于缺陷时间。定向复核包 85 条，当前 83 条待处理、2 条未决。

这些数字说明什么、不说明什么要分清：时钟吻合说明标签与来源记录自洽，不说明标签正确；334 条重叠不等于 334 条确定误标；85 条定向包不是随机抽样，不能用来估计噪声率。

## 5. 缺口清单

| 缺口 | 现状 | 影响 | 补齐动作 | 优先级 |
|---|---|---|---|---|
| 缺陷类型 | 恒为 unknown | 无法做类型预测，也无法按类型分层评估 | 先定类型来源（发布方字段、Issue 标签或人工抽样），再谈预测 | 高 |
| 缺陷位置 | 空 | 无法做定位，也无法把风险落到文件 | 复用解析链路的逐行证据，先把公开数据的定位能力标注为不可得 | 中 |
| 标签可用时间 | 空 | 不能做历史回放与双时间评估 | 需要 Issue 创建时间或复核时间作为知识时点，公开数据不提供 | 高 |
| 负例覆盖 | 未认证 | 干净样本可能只是没被链接到，不是真的干净 | 定义负例取得规则并抽样核验 | 高 |
| 金标子集 | 无 | 所有指标都建在弱监督标签上 | 抽分层样本做双人独立复核，报告一致性 | 中 |
| 噪声率 | 未估计 | 无法给出指标的可信区间 | 按预声明分层概率抽样，不用定向包冒充 | 中 |
| 跨源去重 | 未认证 | 两个来源合起来训练会重复计数 | 按规范仓库名与提交编号去重，记录优先级 | 中 |
| 语言覆盖 | 逐行未验证 | 不能声称跨语言泛化 | 逐行判定语言，或明确声明只覆盖 Java | 低 |
| 严重度与影响面 | 无字段 | 无法排序修复优先级 | 需要新来源，暂不承诺 | 低 |
| 工程缺陷与数据行关联 | 看板缺陷条目与数据集提交行是两套编号 | 不能回答「我们修过的哪个问题影响了哪批数据」 | 需要一条显式映射，短期先声明两者不互通 | 低 |

## 6. 工程自身的缺陷记录与数据集的关系

看板缺陷管理表里记的是我们开发过程中发现的问题，编号自成一套；数据集里记的是被挖掘仓库的提交与标签，编号是那些仓库的提交哈希。两者目前没有任何字段关联。

因此今天能回答「我们的哪个缺陷影响了哪次构建」，回答不了「我们的哪个缺陷影响了哪批训练数据」。要回答后者，需要给缺陷条目加上受影响的数据集标识或规则版本，这属于看板治理的范围，本文只把差距写清。

## 7. 补全路线

第一批先把能定的定了：类型与位置在公开数据里确认不可得，就在资产清单与数据集摘要里显式写不可得，不再留空字段让人误读；同时把负例取得规则写成规格。

第二批补标签可用时间：从我们自己的解析链路里取 Issue 观测时间，做一份真正带知识时点的数据集，与公开数据的分权评估分开报告。

第三批做金标子集与噪声估计：按预声明分层抽样、双人独立复核、报告一致性与置信区间，用结果反过来校准弱监督标签的可信度。

三批都不改变已有资产、已有数据集的哈希与已有模型的评估结论；新口径产出新版本，旧版本原样保留。
