### 4.1 开始框架及采集实现前

| 问题及依据 | 影响 | 建议决策 |
|---|---|---|
| `06` 的 Sprint 1 排除认证，但 `02`、`04` 的业务接口要求 Viewer/Member/Admin；US-22 同时包含可延期的用户管理 | 前后端可能分别按匿名访问和登录访问实现 | 将最小登录、预置用户、角色校验前置；用户管理页面仍可后置。若采用开发身份替身，必须限定本地测试且不计入安全验收 |

| `02` 状态图没有 stale，重试又画成原任务 `failed → queued`，正文要求 successor | 数据与 UI 对终态、重试关系理解不一致 | 明确 stale 是状态还是健康标记；原任务终态保留，重试创建新任务；补取消与成功竞态规则 |
| 首个 change 先写 MySQL 再入 Redis，未说明中间失败如何恢复 | 数据库有 queued 记录但任务永远不执行 | 采用事务 outbox，或持久任务扫描补投；声明重复投递、租约和旧 Worker 写入的处理方式，做故障注入验证 |
| SSRF 要求覆盖 DNS、重定向和实际连接，但尚无 Git 传输层实施方案 | URL 预校验通过后，Git 仍可能独立解析地址或重定向 | 做小型传输探针，落实连接地址控制、重定向策略、协议限制及资源限制；仅验证字符串不能算完成 |
| API 多为清单，表结构多为摘要 | 可支持规划，但尚不足以直接生成全部实现 | 只先细化首批接口的字段、响应、错误码及首批表的字段类型、外键、唯一约束和迁移 |

幂等还需约定：相同 key、不同 payload 如何返回冲突；作用域是否包含操作者；key 缺省策略；重复 URL、不同 commit_limit 如何处理。取消请求已接受与任务实际 cancelled 应有明确区别。

### 4.2 开始 SZZ、特征和数据集实现前

| 问题及依据 | 影响 | 建议决策 |
|---|---|---|
| `commit_label` 含 `snapshot_at`，主键却只有 `(commit_id,label_version)` | 同一规则在 T1/T2 的标签无法并存，重算可能覆盖历史数据集依据 | 增加不可变 label snapshot/run 标识；数据集引用具体快照及不可变特征结果/工件 |
| 时间切分约束了特征与预处理，但未明确训练时标签的可得时间 | 可能用训练截止之后才发生的修复证据训练，再声称模拟当时预测 | 区分回顾性评估和上线时点回放；后者约束训练标签可见截止点，测试标签可在未来成熟后用于评分 |
| `commit_limit` 只定义输出规模，未定义历史预热和标签观察范围 | 前 N 条之前的作者/文件历史缺失会使 EXP、AGE 等失真；SZZ 可指向窗口外提交 | 分开定义采样窗口、历史上下文范围、修复观察范围；不足时标记原因，不直接填 0 当真实历史 |
| 拓扑处理顺序与按 committer time 切分同时出现 | 时间戳倒置、并列时间、分支合并时存在歧义 | 定义祖先可达性与时间边界的共同规则，增加时间戳异常和分叉合并夹具 |
| `FIX` 为“确认的 Fix”，但候选预测采用 0/unknown | 训练推理分布可能不一致，也可能引入事后 Issue 信息 | 将用于特征的即时 Fix 判断与用于标签的事后证据分开；训练和预测共享同一可见性策略 |
| Kamei 公式尚有边界空缺 | 实现者可能得出不同结果 | 固定子系统映射、根目录、零 churn、首次文件、重命名历史、NUC 去重口径、SEXP 跨子系统计数及 LT/AGE 聚合，逐项手算断言 |

SZZ 还需明确支持的语言及注释过滤范围、未能追踪的 blame、窗口外提交的保存方式、冲突证据优先级；`buggy` 与 `unknown` 的判定条件可能重叠，应确定优先级。原始父 SHA 列表也应保存，不能只存 `parent_count`。

当前表清单没有清楚表达 SZZ run、feature run 与通用 task、版本、统计的对应关系。可选独立 run 表或类型化任务元数据，但应先选定一种，避免 API 有 run ID 而数据库无法定位运行结果。

### 4.3 开始模型和候选预测实现前

| 问题及依据 | 影响 | 建议决策 |
|---|---|---|
| US-10 标为 Optional，但固定模型组合包含依赖 message/diff 的 TextCNN | 可选输入实际是必做模型的前置依赖 | 把最小语义管线列为该模型必需依赖，或评审调整深度模型组合；不能同时保留两种冲突定义 |
| 候选 branch/diff 的预测粒度不明确 | UI 期待多个提交结果，API 示例却返回单一结果 | 首版优先单 commit；随后定义 branch 是逐提交评分还是聚合评分。聚合变更不应直接当作训练时单提交分布 |
| 裸 diff 无 author、message、event_time；base/candidate 仅存可移动 ref | 无法完整计算经验特征，也难以复现输入 | 定义缺失信息及未知作者规则，保存解析后的 base/candidate SHA、输入摘要、版本和必要元数据 |
| Popt 未固定最优/最差曲线、积分区间及零 Effort 规则；PR-AUC 计算形式未明确 | 不同实现的指标不可比较 | 在指标 change 中写明公式及边界手算例；同时明确无 buggy、全零 Effort、20% 边界取整和并列排序 |
| 所有模型要求校准和解释，但接口仅提供抽象方法 | 深度模型解释及小验证集校准可能超出预期工作量 | 在 LR/RF 阶段先验证校准、解释和保存加载契约，随后为每个插件声明支持策略与失败条件 |
| `05` 要求重跑工件哈希一致 | 哈希证明具体工件完整性，不必然代表不同训练重跑产生字节相同文件 | 区分原工件完整性校验与重跑可复现性；后者检查数据、预测及指标容差，确定性输出才要求字节一致 |

`04` 还缺 Fix 证据查询的明确契约，以及模型运行列表、导出等部分页面所需读接口。应在相应 change 开始前补齐。A03 刷新接口需要明确凭 refresh/session 认证，不能要求尚未过期的 access token 才能刷新。

## 6 框架具体做到什么程度

沿用 `02` 的目录结构，但按实际实现创建包，不一次性建大量空模块。

首批交付：

- 根级 `pyproject.toml` 与依赖锁；API/Worker 共享 Python 业务代码。
- `apps/api`：应用入口、统一错误、request_id、配置校验、健康检查、最小认证。
- `apps/worker`：Celery 入口、可查询任务、心跳及失败写回的最小实现。
- `apps/web`：Vue 路由、布局、API 客户端、仓库和任务的最小页面。
- `packages/domain`、`packages/persistence`：本轮需要的状态、接口、SQLAlchemy 模型及迁移。
- `deploy`：Compose、持久卷和健康依赖；`.env.example` 仅放示例值。
- `tests`：最小集成冒烟、状态约束测试和小型 Git fixture 基础设施。
- CI：先执行现有代码实际需要的检查、测试和前端构建，后续随算法及接口补 OpenAPI、fixture 等门槛，禁止用空测试冒充完整通过。

依赖版本在初始化时验证兼容性后锁定；本次没有检查本机 Docker/Python/Node 可用性，也没有安装依赖或验证运行环境。环境可用性是 B 阶段第一项。

建议以一个小的 `bootstrap-application` change 描述框架、最小权限和运行验收，映射 NFR 与 US-01/02 的前置能力；也可以放在现有 change 的第 0 组任务，二选一，避免两个 change 重复拥有同一任务。名称是建议，目前未创建。

## 7 分支与提交安排

用户当前希望先在 `wang` 独立试开发，可直接在该分支小步提交，`main` 保持稳定。进入正式多人协作后按 `06` 从 `wang` 建短期 feature 分支，PR 回 `wang`；阶段验收后再 PR 到 `main`。当前个人试开发方式应在协作说明中明确为阶段安排。

建议提交批次：

1. 文档基线与采集规格对齐。
2. 最小工程框架与可运行说明。
3. 数据库迁移、任务状态及集成验证。
4. 仓库安全接入和解析。
5. Fix 证据及仓库/任务界面闭环。

每批实际通过相应检查后再提交，不把大量未验收功能积累成一次提交。需要正式合并时遵守现有非作者评审要求；个人本地试验不等于完成课程的 PR 协作证据。

## 8 下一次开发的具体起点

先处理 A 阶段并确定首批接口与状态机，然后完成 B 阶段的可运行链路。第一个技术验收目标是：

> 启动系统后，用户能从页面发起一个后台任务，刷新后仍能看到数据库保存的状态；Worker 实际消费任务并写回结果；相关检查在 CI 中可重复运行。

随后立即用真实仓库采集替换演示任务，交付 C 阶段。此时再扩展算法，框架设计才能由实际数据链路检验。
