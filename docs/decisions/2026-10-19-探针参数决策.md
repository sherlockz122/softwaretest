## 1. 这份记录要解决什么

Sprint 0 的技术探针跑了两个仓库（`apache/commons-cli` 2,257 提交、`apache/activemq` 12,600 提交），产出的结论要变成产品里能用的**默认值**。有三个参数必须由探针定，不能靠拍：

| 参数 | 决定什么 | 定错了的后果 |
|---|---|---|
| 仓库时间窗口 | 从哪一段历史开始算提交 | 太短取不到样本，太长拖垮运行时间 |
| 标签观察窗口 W | 提交之后等多久才认定「不会被修复」 | 太短会把真实缺陷当成 clean |
| 输入上限 | 单次任务最多处理多少提交 | 超时、内存打爆、磁盘写满 |

三个参数分别落在不同的代码位置，**互不替代**，不能用一个数贯穿。

## 2. 参数一：仓库时间窗口

### 2.1 已有实测

| 项 | commons-cli | activemq |
|---|---|---|
| 默认分支提交数 | 2,257 | 12,600 |
| 可算特征提交 | 2,172（96.2%） | 11,600（92.1%） |
| 全分支提交数（**不采用**） | 2,325 | 16,378 |
| 探针实际取数起点 | 全历史 | **2013-01-01** |
| 该窗口内非合并非机器人提交 | — | 5,025 |
| 该窗口内 fix 提交（规则 C） | 233 | **1,337** |

取 2013-01-01 的原因：ActiveMQ 在 2005 年开始，早期提交的消息规范与现在差异大，且老提交的缺陷记录不完整。

### 2.2 与产品实现的差距

产品用的是 `history_coverage = full | recent_window`，其中 `recent_window` 表示「最近 N 次提交的有限历史，同步后也不补全旧历史」。

**探针按绝对日期（2013-01-01）测，产品按最近 N 实现，两者语义不同**，结论不能直接搬。需要决定的是：

- 方案 A：默认按绝对日期（跨仓库可比，但小仓库取不满）
- 方案 B：默认按最近 N 提交（规模可控，但「2013 年」这种结论作废）
- 方案 C：两者都支持，按仓库规模自动选择（需要一条切换规则）

### 2.3 可补充：最低样本量换算

窗口长度的下限其实由「切分后测试集还剩多少正例」决定，不是凭感觉定的。产品当前按 **70/15/15** 时间切分，测试集占 15%。

两个仓库的缺陷引入率差别很大：ActiveMQ **18.5%**（1,117 / 6,028）、commons-cli **9.6%**（216 / 2,172）。同样要达到某个测试集正例数，低缺陷率的仓库需要多得多的提交。

| 目标 | 需要 BIC 总数 | ActiveMQ（18.5%）需可算提交 | commons-cli（9.6%）需可算提交 |
|---|---|---|---|
| 测试集正例 ≥ 30 | 200 | 约 1,080 | 约 2,083 |
| 测试集正例 ≥ 100 | 667 | 约 3,605 | 约 6,946 |

> 依据类型：**推断**。算式是 `BIC 总数 = 目标正例 / 0.15`，`可算提交 = BIC 总数 / 缺陷引入率`，缺陷引入率取自实测。这一步只给量级，不构成实测证据。

这也解释了为什么 commons-cli 那类小仓库指标波动大：它全历史只有 216 个 BIC，测试集约 32 个正例，`PofB20`、`Popt` 这类排序指标在 32 个正例上极不稳定。

### 2.4 待补证据

- 在 2 个以上的仓库上验证「最近 N 提交」与「绝对日期」得到的缺陷引入率差异
- 小仓库（提交数 < 2,000）在两种方案下的可用样本量

### 2.5 建议取值（待签字）

| 字段 | 建议取值 | 依据 | 适用范围 | 超出范围时的行为 | 回退条件 |
|---|---|---|---|---|---|
| 默认窗口模式 | **按仓库自适应**：大仓库用绝对日期，小仓库退化为全历史 | 推断（§2.3 换算），提交数不足时选窗口没有意义 | 全部仓库 | 提交数低于下限时改用全历史 | 若全历史仍不足，拒绝训练而非降低切分比例 |
| 可算提交下限 | **约 3,600**（对应测试集约 100 个正例） | 推断（§2.3） | 缺陷引入率 10%~20% 的仓库 | 低于下限时提示样本不足，建议换仓库或扩大窗口 | 若坚持训练，测试集正例数必须写入报告 |

## 3. 参数二：标签观察窗口 W（**最高优先级**）

### 3.1 已有实测

观察窗口覆盖率：提交级、代码行口径，即「首次修复落在 W 个月内的 BIC 占比」。

| W | commons-cli | activemq |
|---|---|---|
| 6 个月 | 67.1% | **43.7%** |
| 12 个月 | 73.1% | 54.3% |
| **24 个月** | 80.2% | **68.1%** |
| 36 个月 | 84.4% | 73.9% |

**覆盖不是常数**，两个仓库差 20 个百分点以上，必须按仓库实测。

**补充：给出细粒度曲线。** 上表只有 6/12/24/36 个月四个点，不足以支撑「90 天会怎样」。`probe/out/gaps.csv` 里有逐条 `gap_days`，可以按任意 W 重算。

计算口径（与上表对齐并已对账）：只取非语义行命中的首次修复，按引入提交去重，ActiveMQ 共 **1,037 个 BIC**。该口径下 12 / 24 / 36 个月复现为 54.3% / 68.1% / 73.9%，与上表一致；6 个月复现为 43.4%，与上表 43.7% 差 0.3 个百分点，疑为原计算的边界取整。

| 60 天 | 31.1% | 68.9% |
| **90 天（产品当前默认）** | **35.2%** | **64.8%** |
| 120 天 | 39.2% | 60.8% |
| 180 天（6 个月） | 43.4% | 56.6% |
| 270 天（9 个月） | 48.9% | 51.1% |
| 365 天（12 个月） | 54.3% | 45.7% |
| 540 天（18 个月） | 61.6% | 38.4% |

反推目标覆盖率所需的窗口：

| 60% | 约 508 天（16.7 个月） |

### 3.2 W=90 天的出处（已查明，不是「无人解释」）

#### 3.2.1 它不是随手填的，是明确标注过的占位政策

| 事项 | 查证结果 |
|---|---|
| 引入提交 | `a0f760c`（2026-10-11，wk593909951）`feat(dataset): add maturity and immutable time-split kernel` |
| 代码位置 | `packages/mining/dataset.py:33`，`window_days: int = 90` |
| 后续补充 | `11e9149`（同日）加入知识延迟 `L=7`，以及 `packages/mining/historical_replay.py` 的 `horizon_days: int = 90` |
| 外部参照 | `5ec49f6`（10-14）在《外来材料吸收与处置清单》里写明：**「单仓库六个月窗口『已定』通用参数 → 不采用外部固定值」** |

仓库内共四处明确声明它是**未实测的实验政策**：

> 《成熟度与时间数据集验收》：默认观察窗 W=90天，可预声明1～3650天；**它是工程政策，不是已完成真实项目缺陷延迟分布分析的结论**。

> 《历史回放与可知特征合同》：默认W=90天，假设知识延迟L=7天；**这些是实验政策，不是实测延迟**。

> 《历史回放与可知特征验收》：默认W90/L7**不是已实测政策**；参数在看测试结果之前预声明，不按结果调参。

> 《外来材料吸收与处置清单》：现行默认90天/7天延迟是预声明实验政策，**需按真实来源测量而非金标事实**。

#### 3.2.2 所以这不是「冲突」，是「占位符到期」

90 天当初就是**等实测的占位值**，文档还专门锁了「不得观察测试结果后调窗」，所以没人凭感觉改它。这也是为什么它能一直留着——按规矩，必须等一份实测才能动。

**本探针正是它要求的测量。** §3.1 已经给出答案：W=90 天覆盖 35.2%，64.8% 的 BIC 等不到修复。

**含义**：按 90 天做成熟度判定，约三分之二的真实缺陷引入提交会被当成 clean 负例，直接污染训练标签。这可能是 LR/RF 首轮 PofB20 低于常数先验的原因之一。

### 3.3 精确位置：三处 90 与一处 7

| # | 位置 | 名称 | 作用 |
|---|---|---|---|
| 1 | `packages/mining/dataset.py:33` | `Policy.window_days: int = 90` | `time-labels-v1` 成熟度窗口的**定义处** |
| 2 | `packages/mining/dataset_source.py:72` | `_load(..., window_days=90)` | **函数默认参数**，显式传给 `Policy(...)`，覆盖 #1 |
| 3 | `scripts/audit_dataset.py:22` | `--window-days`，`default=90` | CLI 默认值，再覆盖 #2 |
| 4 | `packages/mining/historical_replay.py:31` | `ReplayPolicy.horizon_days: int = 90` | `historical-horizon-replay-v1` 的观察期 |
| 5 | `packages/mining/historical_replay.py:32` | `ReplayPolicy.knowledge_lag_days: int = 7` | 知识延迟 L |

#### 3.3.1 三个 90 是一条覆盖链，只改一处不会生效

调用关系是 `CLI(--window-days) → _load(window_days=90) → Policy(window_days=90)`。三处都写死了 90，任何一处漏改，行为都不会按预期变化：

- 只改 #1 `Policy.window_days`：**无效**，因为 #2 的 `_load` 显式传了自己的 90
- 只改 #1 和 #2：命令行工具仍会用 #3 的 90 覆盖

这是必须一次性改齐的三处。

#### 3.3.2 四个参数的语义分判

**#1 / #2 / #3 是同一个概念**：`time-labels-v1` 的成熟度窗口。用法在 `dataset.py:261-271`：

```
event_time + window > snapshot_at        -> immature（观察期不足，不判 clean）
clean 需观察到 event_time + window 之后，且多轮 observed_at >= event_time + window
```

这正是探针测的 W，同一个东西，**可以按 §3.4 改成 730 天**。

**#4 概念相同但受额外约束**：`historical_replay.py:200,219` 里 `end = event + horizon_days`，只有 `fix_time <= end` 才算 buggy。但判 clean 还额外要求 `coverage_complete` 且 `end <= source.coverage_end`（第 225-229 行）。**若把 horizon 改成 730 天，`coverage_end` 也要能覆盖到那么远，否则标签会全部落到 `negative_censored_or_incomplete`。**

**#5 是另一个量，不该跟着改**：知识延迟只出现在 `available = fix_time + lag`（第 220 行）与 `available = end + lag`（第 230 行），作用是判定 `as_of` 那一刻标签是否已知。它**不改变覆盖率**，只把可用时间往后推。7 天与 90 天不是同一尺度，W 改成 730 时 L 应保持独立，并有自己的实测依据。

#### 3.3.3 剩余待确认

- **知识延迟 L=7 天同样未实测**：《历史回放与可知特征合同》写明它是实验政策。它对应的是「缺陷修复落地后多久团队才知道」，与观察窗口是两个不同的测量
- commons-cli 的原始间隔未入库（`probe/out/` 只有 ActiveMQ 的 `gaps.csv`），其 67.1% / 73.1% / 80.2% / 84.4% 无法复算
- 在 16 个公开来源上抽样复测覆盖率，确认 24 个月对研究数据集是否成立
- `DatasetSource._load` 与 CLI 各自持有默认值，属于配置重复。改参数时应改为从 `Policy` 单一来源取值，否则同类不一致还会再出现

### 3.4 建议做法：W 按仓库标定，固定默认值只作回退

#### 3.4.1 为什么不该有一个统一的 W

两个仓库在同一个 W 上差距极大：

| W | commons-cli | activemq |
|---|---|---|
| 6 个月 | **67.1%** | 43.7% |
| 24 个月 | 80.2% | **68.1%** |

若统一取 24 个月：commons-cli 早在 6 个月就已达标，后面 18 个月属于白白丢弃可用样本（它全历史只有 216 个 BIC，丢掉尾部影响很大）。
若统一取 90 天：ActiveMQ 只覆盖 35.2%，约三分之二的 BIC 被误标 clean。

**两个方向都错。W 必须是每个仓库自己算出来的。**

#### 3.4.2 标定规则

对每个仓库，用其自身的 BIC→fix 间隔分布（SZZ 跑完即有）求：

```
W* = min{ W : coverage_repo(W) ≥ 阈值 }
约束：W* ≤ 该仓库可观测跨度（否则等于把整段历史排除）
      W* ≥ 最短可用窗口（下限，避免样本太少）
样本不足（BIC 太少、历史太短）时，回退到固定默认值
```

`probe/probe_coverage.py` 已经能算出任意 W 的覆盖率，标定只是在这条曲线上取点。

**标定结果必须写入该数据集不可变的策略快照**，否则同一次训练不可复现。

#### 3.4.3 阈值本身还没定（这是本节最大缺口）

阈值取多少，直接决定 W。两种候选逻辑：

**候选 A：覆盖率阈值。** 取 65% 意味着接受「约三分之一的真实 BIC 被误标 clean」。
但 65% 这个数本身没有依据，是我为了给出具体建议临时取的。要站得住，它应该由下游能容忍的假阴性率反推，而不是拍。

**候选 B：边际收益拐点。** 看每多给 30 天窗口换来多少覆盖增量（ActiveMQ）：

| 区间 | 覆盖率变化 | 每 30 天增益 |
|---|---|---|
| 0 → 30 天 | 26.8% → 31.1% | — |
| 30 → 60 天 | 31.1% → 35.2% | 4.1 |
| 60 → 90 天 | 35.2% → 39.2% | 4.0 |
| 90 → 120 天 | 39.2% → 43.4% | 4.2 |
| **120 → 180 天** | 43.4% → 48.9% | **2.1（折半）** |
| 180 → 270 天 | 48.9% → 54.3% | 1.8 |
| 270 → 365 天 | 54.3% → 61.6% | 1.7 |
| 365 → 540 天 | 61.6% → 68.1% | 1.3 |
| 540 → 730 天 | 68.1% → 73.9% | 1.0 |

拐点在 **约 120 天**，此后每 30 天的增益从 4.0 掉到 2.1 并持续下降。按候选 B，ActiveMQ 的 W* 只有 4 个月左右，覆盖率 39.2%。

**两个候选给出的答案差 6 倍。** 这说明 W 不能在没有明确目标函数的情况下定下来。

#### 3.4.4 我的判断

倾向于 **候选 A（覆盖率阈值）**，理由是目标本身是「避免把未修复的 BIC 当 clean」，这是正确性问题，不是成本问题；代价（丢掉尾部样本）应该作为约束另算。

但阈值的数值必须先定，否则 W 无从谈起。建议下一步先回答一个更简单的问题：**能被误标为 clean 的 BIC 占比，最多容忍多少？** 这个数定了，W 就是算出来的，不是选出来的。

#### 3.4.5 建议取值（待签字）

| 字段 | 建议取值 | 依据 | 适用范围 | 超出范围时的行为 | 回退条件 |
|---|---|---|---|---|---|
| W 的决定方式 | **按仓库标定**：`W* = min{W : coverage(W) ≥ 阈值}` | 实测：两仓库达标所需窗口差 4 倍以上 | 全部仓库 | — | — |
| 固定默认值 | **待定**，仅作冷启动回退 | 缺依据：任何单一常数都会在另一类仓库上偏低或偏高 | 无法标定的仓库 | 标定失败时使用 | 该仓库后续产出 SZZ 结果后重新标定 |
| 覆盖率阈值 | **待定**（候选 65%，无下游依据） | 未定 | 全部仓库 | — | — |
| 标定结果记录 | **写入数据集不可变策略快照** | 与方法学一致：同一训练必须可复现 | 全部仓库 | — | 窗口变更产生新快照，不覆盖旧结果 |
| W 不足时的数据处置 | **不判 clean，标 Unknown 并排除出训练** | 观察期不足不能当负例 | 全部仓库 | — | 若某仓库正例过少，先延 W 再考虑弃用该仓库 |

> 90 天的处置：出处已查明是占位政策，而政策原文要求「**需按真实来源测量**」。但这个测量不是给所有仓库一个统一新常数，而是**换掉固定默认值的做法本身**。修改时必须一次改齐三处默认值（`dataset.py:33`、`dataset_source.py:72`、`audit_dataset.py:22`），`historical_replay.py:31` 的 `horizon_days` 另行评估，`knowledge_lag_days` 不动。

## 4. 参数三：输入上限

### 4.1 已有实测（注意：两套实现不能混用）

**探针脚本的实测**（`probe/probe_perf.py`，简化版内核，14 维只算对 6 个）：

| 项 | 数值 |
|---|---|
| 单提交耗时 | 133.4 ms |
| 30 分钟可处理提交数 | 13,491 |
| SZZ 全量运行时间 | 57.3 / 62.7 / 80.8 分钟（三次，极差 41%） |

**生产内核的性能探针**（`scripts/probe_features.py`，合成线性仓库）：

| 项 | 200 提交 | 1,000 提交 |
|---|---|---|
| 耗时 | 0.276 s | 4.870 s |
| 单提交 | 1.38 ms | 4.87 ms |
| 内存峰值（tracemalloc） | 0.868 MiB | 4.311 MiB |

单提交成本从 1.38 ms 涨到 4.87 ms（3.5 倍），与生产内核祖先扫描为 **O(N²)** 的结论一致。

### 4.2 为什么 13,491 不能直接用

两个原因：

1. 那个数是在**简化版内核**上测的，生产内核多了严格祖先校验、文件历史追溯、缺失原因记录
2. 生产内核是超线性的，**不能用 200 和 1,000 两点做线性外推**

### 4.3 可补充：按 O(N²) 拟合出的参考曲线

用上表两个实测点解 `t(N) = a + b·N²`：

```
b = (4.870 − 0.276) / (1000² − 200²) = 4.785 × 10⁻⁶
a = 0.276 − b × 200²                 = 0.085
```

得到 `t(N) = 0.085 + 4.785×10⁻⁶ · N²` 秒。据此推算：

| 提交数 | 预测耗时 | 备注 |
|---|---|---|
| 1,000 | 4.87 s | **实测点** |
| 2,000 | 约 19 s | 补测检查点 |
| 5,000 | 约 2.0 分钟 | 补测检查点 |
| 10,000 | 约 8.0 分钟 | 补测检查点 |
| 19,400 | 约 30 分钟 | 30 分钟预算对应的提交数 |
| 20,000 | 约 32 分钟 | 已超预算 |

**这条曲线只能当参考，不能当结论**，三个理由：

1. **外推倍数太大**：最远的实测点是 1,000 提交，推 19,400 是约 19 倍外推，二次模型在大 N 处误差会被放大
2. **仓库是合成的**：`scripts/probe_features.py` 跑的是合成线性历史，没有真实 Git 对象读取、没有数据库写入。真实仓库只会更慢，所以这条曲线是**下界**
3. **只拟合了两个点**：两点定二次模型必然过拟合，补第三个点（2,000 或 5,000）之后必须重拟合

**内存方面**：200 → 1,000 提交时，内存从 0.868 MiB 涨到 4.311 MiB，提交数涨 5 倍而内存涨 4.97 倍，**接近线性**。按线性外推，19,400 提交约 84 MiB（tracemalloc 统计的 Python 分配峰值，不是 RSS）。所以在这套合成探针里**时间是主要约束、内存不是**；真实仓库的 Git 对象与数据库连接会改变这个结论，仍需实测。

### 4.4 待补证据

- 在真实 Git 仓库（非合成）跑 2,000 / 5,000 / 10,000 提交，记录耗时、内存峰值、磁盘增量
- 补第三个点后重拟合，确认 O(N²) 是否在某个规模后变成 O(N³)（祖先扫描叠加文件历史追溯时可能出现）
- 与存储预算联动：D 盘余量有限，命令必须带 `-ExpectedGrowthGiB`

### 4.5 建议取值（待签字）

| 字段 | 建议取值 | 依据 | 适用范围 | 超出范围时的行为 | 回退条件 |
|---|---|---|---|---|---|
| 单任务提交上限 | **待实测** | — | — | — | — |
| 超限行为 | **拒绝并提示，不静默截断** | 推断：静默截断会让数据集与声明的窗口不一致，指标无法复现 | 全部仓库 | 返回明确错误 + 建议缩小窗口或分片 | 若改为分片，必须记录分片边界与合并方式 |
| 内存上限 | **待实测** | 现有数据仅覆盖到 1,000 提交 | — | — | — |
| 磁盘上限 | **必须走 `-ExpectedGrowthGiB`，超出即停** | 团队既有纪律 | 全部命令 | 停止并告知，不转 C 盘 | — |

> 上限的数值一律留空。按探针阶段定的纪律：**缺证据的参数宁可写「暂定 + 附实测依据 + 超限拒绝」，也不写推算值冒充实测值。** 上面那条拟合曲线只用于设定补测检查点。

## 5. 附：三套 fix 口径，引用时必须说明是哪一套

探针过程中出现过三个「ActiveMQ fix 数」，各自成立但**人口不同**，报告里引用时不能混用：

| 数值 | 产出脚本 | 提交范围 | 文本字段 | 其它过滤 | 用途 |
|---|---|---|---|---|---|
| **1,337** | `probe/probe_szz.py` | 默认分支 | **完整消息** | 2013 起 / 剔合并 / 剔机器人 | **对外唯一引用值**（复现验证一致） |
| 3,566（23.6%） | `probe/probe_fixrule.py` | 全分支 `--all` | 仅标题 `%s` | 剔合并 / 剔机器人 | 规则选型用，人口不被产品采用 |
| 3,448（27.4%） | 复核脚本 | 默认分支 | 完整消息 | 含合并 / 含机器人 | 缺陷编号影响面分析 |

已核实的两个方法学问题：

1. `probe_fixrule.py` 只搜标题，同人口下比完整消息少 **219 条（−16.4%）**，而 Kamei 搜的是 changelog。规则选型（剔除 `resolve` / `close`）因此是在「仅标题」人口上做的
2. `probe_fixrule.py` 用的是 `--all`（16,378），而结论表明确写「全分支不采用」

## 6. 与 Kamei 14 维口径裁决的关系

三个参数与特征口径相互独立，但有一条交叉：

本轮裁决结论是 **`feature_version` 保持 `kamei14-dg-v1` 不变**，因此已跑出的特征与标签（含缺陷引入率 18.5%）继续有效，不需要重跑。

详见 `probe/Kamei口径裁决表.md`。该表的核心结论：

- 14 项里 10 项与原文一致
- Entropy 保留归一化、REXP 保留连续年、AGE 保留 churn 加权，三处均为已知偏差，不升版
- FIX 不采用论文的缺陷编号条款（实测会引入 42.3% 功能类噪声，fix 占比从 26.6% 冲到 79.4%）
- 归一化派生列（`LA/LT`、`LD/LT`、`LT/NF`、`NUC/NF`）、log 变换、共线性剔除放到数据集与训练层，不碰内核
