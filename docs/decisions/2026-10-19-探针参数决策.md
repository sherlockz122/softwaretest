## 1. 这份记录要解决什么

Sprint 0 的技术探针跑了两个仓库（`apache/commons-cli` 2,257 提交、`apache/activemq` 12,600 提交），产出的结论要变成产品里能用的**默认值**。有三个参数必须由探针定，不能靠拍：

| 参数 | 决定什么 | 定错了的后果 |
|---|---|---|
| 仓库时间窗口 | 从哪一段历史开始算提交 | 太短取不到样本，太长拖垮运行时间 |
| 标签观察窗口 W | 提交之后等多久才认定「不会被修复」 | 太短会把真实缺陷当成 clean |
| 输入上限 | 单次任务最多处理多少提交 | 超时、内存打爆、磁盘写满 |

三个参数分别落在不同的代码位置，**互不替代**，不能用一个数贯穿。

## 2. 参数一：仓库时间窗口

### 2.1 已有实测

| 项 | commons-cli | activemq |
|---|---|---|
| 默认分支提交数 | 2,257 | 12,600 |
| 可算特征提交 | 2,172（96.2%） | 11,600（92.1%） |
| 全分支提交数（**不采用**） | 2,325 | 16,378 |
| 探针实际取数起点 | 全历史 | **2013-01-01** |
| 该窗口内非合并非机器人提交 | — | 5,025 |
| 该窗口内 fix 提交（规则 C） | 233 | **1,337** |

取 2013-01-01 的原因：ActiveMQ 在 2005 年开始，早期提交的消息规范与现在差异大，且老提交的缺陷记录不完整。

### 2.2 与产品实现的差距

产品用的是 `history_coverage = full | recent_window`，其中 `recent_window` 表示「最近 N 次提交的有限历史，同步后也不补全旧历史」。

**探针按绝对日期（2013-01-01）测，产品按最近 N 实现，两者语义不同**，结论不能直接搬。需要决定的是：

- 方案 A：默认按绝对日期（跨仓库可比，但小仓库取不满）
- 方案 B：默认按最近 N 提交（规模可控，但「2013 年」这种结论作废）
- 方案 C：两者都支持，按仓库规模自动选择（需要一条切换规则）

### 2.3 时间窗口敏感性实测（两仓库）

**做法**：分子分母同起点。分子 = 引入时间 ≥ 起点 的去重 BIC 数（`is_noise=0` 口径）；分母 = 事件时间 ≥ 起点 的默认分支提交数。复现：`python probe/probe_window_sensitivity.py <仓库> <gaps.csv> [标签]`。

**activemq**（BIC 只能从 2013 起观测）：

| 起点 | BIC | 提交 | 引入率 | 仅非合并 |
|---|---|---|---|---|
| **2013** | 1,037 | 6,028 | **17.2%** | 19.9% |
| 2015 | 562 | 4,344 | 12.9% | 15.9% |
| 2018 | 178 | 2,660 | 6.7% | 9.3% |
| 2020 | 124 | 2,218 | 5.6% | 8.0% |
| 2022 | 89 | 1,617 | 5.5% | 7.5% |

起点早于 2013 的行无效——BIC 已被同期群过滤掉，分母却继续增长。

**commons-cli**（全历史 BIC 可用）：

| 起点 | BIC | 提交 | 引入率 | 仅非合并 |
|---|---|---|---|---|
| 2002 | 165 | 2,257 | **7.3%** | 7.5% |
| 2005 | 116 | 2,095 | 5.5% | 5.7% |
| 2008 | 100 | 1,879 | 5.3% | 5.5% |
| **2010** | 55 | 1,656 | **3.3%** | 3.4% |
| 2013 | 48 | 1,576 | 3.0% | 3.1% |
| 2018 | 40 | 1,355 | 3.0% | 3.1% |
| 2022 | 30 | 1,138 | 2.6% | 2.7% |

**按「最近 N 次提交」切**（分子分母同窗口）：

| 最近 N | activemq | commons-cli |
|---|---|---|
| 1,000 | **6.1%** | **2.9%** |
| 2,000 | 5.4% | 5.5% |
| 4,000 | 11.7% | — |
| 8,000 | 13.0% | — |

#### 2.3.1 两类敏感，成因不同

**commons-cli 的 7.3% → 3.0% 是真实的阶段性差异**：2002–2009 那段代码的改动密度与今天不同，2010 之后稳定在 3.0% 上下。

**activemq 的 17.2% → 5.5% 主要不是质量变好，是右截尾**：越近的提交，其修复还没发生，BIC 尚未暴露。「最近 N」窗口因此会把缺陷引入率系统性压低。

#### 2.3.2 由此得到一条窗口设计规则（本节最有价值的产出）

**数据窗口的右端必须预留 W 的观察期。** 有效数据区间是 `[起点, 快照时间 − W]`，不是 `[起点, 快照时间]`。

不预留的话，最近 W 内的提交会被当成 clean，把缺陷率压低、clean 比例抬高。这和 §3 的观察窗口是同一个问题的两面，**必须一起处理，不能各定各的**。

这也解释了 commons-cli 全历史 9.6% 与 2013 起 3.2% 相差三倍：大部分不是质量变化，是窗口截断。

### 2.4 可补充：最低样本量换算

窗口长度的下限其实由「切分后测试集还剩多少正例」决定，不是凭感觉定的。产品当前按 **70/15/15** 时间切分，测试集占 15%。

两个仓库的缺陷引入率差别很大：ActiveMQ **17.2%**（1,037 / 6,028，2013 起同窗口口径）、commons-cli **9.6%**（216 / 2,257，全历史）。同样要达到某个测试集正例数，低缺陷率的仓库需要多得多的提交。

| 目标 | 需要 BIC 总数 | ActiveMQ（17.2%）需可算提交 | commons-cli（9.6%）需可算提交 |
|---|---|---|---|
| 测试集正例 ≥ 30 | 200 | 约 1,163 | 约 2,083 |
| 测试集正例 ≥ 100 | 667 | 约 3,878 | 约 6,946 |

> 依据类型：**推断**。算式是 `BIC 总数 = 目标正例 / 0.15`，`可算提交 = BIC 总数 / 缺陷引入率`，缺陷引入率取自实测。这一步只给量级，不构成实测证据。

这也解释了为什么 commons-cli 那类小仓库指标波动大：它全历史只有 216 个 BIC，测试集约 32 个正例，`PofB20`、`Popt` 这类排序指标在 32 个正例上极不稳定。

### 2.5 待补证据

- 小仓库（提交数 < 2,000）在两种方案下的可用样本量
- activemq 若要做全历史对比，需要跑 `probe_szz.py <仓库> all`（受 `MAXFIX=1500` 限制，预计 60~130 分钟）

### 3.1 已有实测

观察窗口覆盖率：提交级、代码行口径，即「首次修复落在 W 个月内的 BIC 占比」。

|---|---|---|
| 6 个月 | 67.1% | **43.7%** |
| 12 个月 | 73.1% | 54.3% |

| 36 个月 | 84.4% | 73.9% |

**覆盖不是常数**，两个仓库差 20 个百分点以上，必须按仓库实测。

**补充：给出细粒度曲线。** 上表只有 6/12/24/36 个月四个点，不足以支撑「90 天会怎样」。`probe/out/gaps.csv` 里有逐条 `gap_days`，可以按任意 W 重算。

### 3.2 W=90 天的出处（已查明，不是「无人解释」）

#### 3.2.1 它不是随手填的，是明确标注过的占位政策

| 事项 | 查证结果 |
|---|---|
| 引入提交 | `a0f760c`（2026-10-11，wk593909951）`feat(dataset): add maturity and immutable time-split kernel` |
| 代码位置 | `packages/mining/dataset.py:33`，`window_days: int = 90` |
| 后续补充 | `11e9149`（同日）加入知识延迟 `L=7`，以及 `packages/mining/historical_replay.py` 的 `horizon_days: int = 90` |
| 外部参照 | `5ec49f6`（10-14）在《外来材料吸收与处置清单》里写明：**「单仓库六个月窗口『已定』通用参数 → 不采用外部固定值」** |

仓库内共四处明确声明它是**未实测的实验政策**：

> 《成熟度与时间数据集验收》：默认观察窗 W=90天，可预声明1～3650天；**它是工程政策，不是已完成真实项目缺陷延迟分布分析的结论**。

> 《历史回放与可知特征合同》：默认W=90天，假设知识延迟L=7天；**这些是实验政策，不是实测延迟**。

> 《历史回放与可知特征验收》：默认W90/L7**不是已实测政策**；参数在看测试结果之前预声明，不按结果调参。

> 《外来材料吸收与处置清单》：现行默认90天/7天延迟是预声明实验政策，**需按真实来源测量而非金标事实**。

#### 3.2.2 所以这不是「冲突」，是「占位符到期」

90 天当初就是**等实测的占位值**，文档还专门锁了「不得观察测试结果后调窗」，所以没人凭感觉改它。这也是为什么它能一直留着——按规矩，必须等一份实测才能动。

**本探针正是它要求的测量。** §3.1 已经给出答案：W=90 天覆盖 35.2%，64.8% 的 BIC 等不到修复。

**含义**：按 90 天做成熟度判定，约三分之二的真实缺陷引入提交会被当成 clean 负例，直接污染训练标签。这可能是 LR/RF 首轮 PofB20 低于常数先验的原因之一。

### 3.3 精确位置：三处 90 与一处 7

| # | 位置 | 名称 | 作用 |
|---|---|---|---|
| 1 | `packages/mining/dataset.py:33` | `Policy.window_days: int = 90` | `time-labels-v1` 成熟度窗口的**定义处** |
| 2 | `packages/mining/dataset_source.py:72` | `_load(..., window_days=90)` | **函数默认参数**，显式传给 `Policy(...)`，覆盖 #1 |
| 3 | `scripts/audit_dataset.py:22` | `--window-days`，`default=90` | CLI 默认值，再覆盖 #2 |
| 4 | `packages/mining/historical_replay.py:31` | `ReplayPolicy.horizon_days: int = 90` | `historical-horizon-replay-v1` 的观察期 |
| 5 | `packages/mining/historical_replay.py:32` | `ReplayPolicy.knowledge_lag_days: int = 7` | 知识延迟 L |

#### 3.3.1 三个 90 是一条覆盖链，只改一处不会生效

调用关系是 `CLI(--window-days) → _load(window_days=90) → Policy(window_days=90)`。三处都写死了 90，任何一处漏改，行为都不会按预期变化：

- 只改 #1 `Policy.window_days`：**无效**，因为 #2 的 `_load` 显式传了自己的 90
- 只改 #1 和 #2：命令行工具仍会用 #3 的 90 覆盖

这是必须一次性改齐的三处。

#### 3.3.2 四个参数的语义分判

**#1 / #2 / #3 是同一个概念**：`time-labels-v1` 的成熟度窗口。用法在 `dataset.py:261-271`：

```
event_time + window > snapshot_at        -> immature（观察期不足，不判 clean）
clean 需观察到 event_time + window 之后，且多轮 observed_at >= event_time + window
```

这正是探针测的 W，同一个东西，**可以按 §3.4 改成 730 天**。

**#4 概念相同但受额外约束**：`historical_replay.py:200,219` 里 `end = event + horizon_days`，只有 `fix_time <= end` 才算 buggy。但判 clean 还额外要求 `coverage_complete` 且 `end <= source.coverage_end`（第 225-229 行）。**若把 horizon 改成 730 天，`coverage_end` 也要能覆盖到那么远，否则标签会全部落到 `negative_censored_or_incomplete`。**

**#5 是另一个量，不该跟着改**：知识延迟只出现在 `available = fix_time + lag`（第 220 行）与 `available = end + lag`（第 230 行），作用是判定 `as_of` 那一刻标签是否已知。它**不改变覆盖率**，只把可用时间往后推。7 天与 90 天不是同一尺度，W 改成 730 时 L 应保持独立，并有自己的实测依据。

#### 3.3.3 剩余待确认

- **知识延迟 L=7 天同样未实测**：《历史回放与可知特征合同》写明它是实验政策。它对应的是「缺陷修复落地后多久团队才知道」，与观察窗口是两个不同的测量
- commons-cli 的原始间隔未入库（`probe/out/` 只有 ActiveMQ 的 `gaps.csv`），其 67.1% / 73.1% / 80.2% / 84.4% 无法复算
- 在 16 个公开来源上抽样复测覆盖率，确认 24 个月对研究数据集是否成立
- `DatasetSource._load` 与 CLI 各自持有默认值，属于配置重复。改参数时应改为从 `Policy` 单一来源取值，否则同类不一致还会再出现

### 3.4 建议做法：W 按仓库标定，固定默认值只作回退

#### 3.4.1 为什么不该有一个统一的 W

两个仓库在同一个 W 上差距极大：

| W | commons-cli | activemq |
|---|---|---|
| 6 个月 | **67.1%** | 43.7% |
| 24 个月 | 80.2% | **68.1%** |

若统一取 24 个月：commons-cli 早在 6 个月就已达标，后面 18 个月属于白白丢弃可用样本（它全历史只有 216 个 BIC，丢掉尾部影响很大）。
若统一取 90 天：ActiveMQ 只覆盖 35.2%，约三分之二的 BIC 被误标 clean。

**两个方向都错。W 必须是每个仓库自己算出来的。**

#### 3.4.2 标定规则

对每个仓库，用其自身的 BIC→fix 间隔分布（SZZ 跑完即有）求：

```
W* = min{ W : coverage_repo(W) ≥ 阈值 }
约束：W* ≤ 该仓库可观测跨度（否则等于把整段历史排除）
      W* ≥ 最短可用窗口（下限，避免样本太少）
样本不足（BIC 太少、历史太短）时，回退到固定默认值
```

`probe/probe_coverage.py` 已经能算出任意 W 的覆盖率，标定只是在这条曲线上取点。

**标定结果必须写入该数据集不可变的策略快照**，否则同一次训练不可复现。

#### 3.4.3 阈值本身还没定（这是本节最大缺口）

阈值取多少，直接决定 W。两种候选逻辑：

**候选 A：覆盖率阈值。** 取 65% 意味着接受「约三分之一的真实 BIC 被误标 clean」。
但 65% 这个数本身没有依据，是我为了给出具体建议临时取的。要站得住，它应该由下游能容忍的假阴性率反推，而不是拍。

**候选 B：边际收益拐点。** 看每多给 30 天窗口换来多少覆盖增量（ActiveMQ）：

| 区间 | 覆盖率变化 | 每 30 天增益 |
|---|---|---|
| 0 → 30 天 | 26.8% → 31.1% | — |
| 30 → 60 天 | 31.1% → 35.2% | 4.1 |
| 60 → 90 天 | 35.2% → 39.2% | 4.0 |
| 90 → 120 天 | 39.2% → 43.4% | 4.2 |
| **120 → 180 天** | 43.4% → 48.9% | **2.1（折半）** |
| 180 → 270 天 | 48.9% → 54.3% | 1.8 |
| 270 → 365 天 | 54.3% → 61.6% | 1.7 |
| 365 → 540 天 | 61.6% → 68.1% | 1.3 |
| 540 → 730 天 | 68.1% → 73.9% | 1.0 |

拐点在 **约 120 天**，此后每 30 天的增益从 4.0 掉到 2.1 并持续下降。按候选 B，ActiveMQ 的 W* 只有 4 个月左右，覆盖率 39.2%。

**两个候选给出的答案差 6 倍。** 这说明 W 不能在没有明确目标函数的情况下定下来。

#### 3.4.4 我的判断

倾向于 **候选 A（覆盖率阈值）**，理由是目标本身是「避免把未修复的 BIC 当 clean」，这是正确性问题，不是成本问题；代价（丢掉尾部样本）应该作为约束另算。

但阈值的数值必须先定，否则 W 无从谈起。建议下一步先回答一个更简单的问题：**能被误标为 clean 的 BIC 占比，最多容忍多少？** 这个数定了，W 就是算出来的，不是选出来的。

### 4.1 已有实测（注意：两套实现不能混用）

**生产内核的性能探针**（`scripts/probe_features.py`，合成线性仓库，项目要求的 **Python 3.11.17**，本机 Intel Core Ultra 7 155H，2026-10-20）：

**与旧记录的对账，得到一个明确结论。** 旧记录是 200 → 0.276 s / 0.868 MiB、1,000 → 4.870 s / 4.311 MiB。

| 项 | 旧记录 | 本次 3.11 实测 | 判断 |
|---|---|---|---|
| 1,000 提交**内存** | 4.311 MiB | **4.311 MiB** | **完全一致** |
| 1,000 提交**耗时** | 4.870 s | **11.316 s** | 慢 2.3 倍 |
| 200 提交内存 | 0.868 MiB | 0.858 MiB | 基本一致 |

内存逐字节吻合说明：旧记录与本次是**同一份代码、同一个解释器版本（3.11）**。因此那 2.3 倍的耗时差异**不是代码变化、也不是解释器差异造成的，而是运行机器的差别**（CPU 或当时的负载）。

**两个后果**：
1. 旧的两点拟合 `t = 0.085 + 4.785×10⁻⁶N²` 及其推出的「30 分钟可跑 19,400 提交」**作废**——它建立在另一台机器的耗时上。
2. **性能数据必须绑定机器**。本决策记录里的全部耗时都以本机（Ultra 7 155H）为准，换机器需重测；内存峰值与机器无关，可以跨机器引用。

作为交叉验证，同一台机器上 Python 3.12 跑出 200/1,000/2,000/5,000 = 0.278/10.869/62.503/429.456 秒，与 3.11 相差在 ±7% 以内，说明**解释器版本不是这组数字的主要影响因素**。

**但合成探针有根本局限**：它造的是线性链、每提交 1 个文件，而真实仓库平均每提交 6~15 个文件、且是带合并的 DAG。所以上面的数只能当参照。下面补真实仓库实测。

### 4.1.1 真实 Git 仓库实测（ActiveMQ）

用 `probe/probe_real.py`，同一台机器、Python 3.11、`history_coverage="full"`（完整算六项历史特征，含 `file_history` 回溯）：

| 提交数 | 耗时 | 每提交 | 内存峰值 |
|---|---|---|---|
| 200 | 0.490 s | 2.45 ms | 6.611 MiB |
| 500 | 1.672 s | 3.34 ms | 8.014 MiB |
| 1,000 | 7.562 s | 7.56 ms | 13.193 MiB |
| 2,000 | 22.063 s | 11.03 ms | 24.281 MiB |
| 5,000 | 113.135 s | 22.63 ms | 40.404 MiB |
| **12,600（全仓）** | **586.736 s（9 分 47 秒）** | 46.57 ms | **78.230 MiB** |

**最后一行是本记录里最可信的一行**：它是 ActiveMQ 全部 12,600 个提交、不经任何截断、完整历史，实测 9 分 47 秒。

**注意：这一行只覆盖内核。** 加上解析阶段后结论完全相反，见 §4.1.2。

### 4.1.2 端到端实测（含解析）

用官方探针 `scripts/probe_causal_features.py`（`NativeReader` + PyDriller 读 blob + `compute_causal`），依赖装齐后在本机跑：

| 规模 | 结果 |
|---|---|
| **100 提交** | **成功，134 秒**（1.34 秒/提交） |
| 200 提交 | **失败**：撞脚本写死的 300 秒解析上限（`REPOSITORY_PARSE_TIMEOUT`） |
| 1,000 提交 | **失败**：同上 |

**所以只有 100 这一个可用点。** 按 1.34 秒/提交线性外推（该阶段尚未表现出超线性）：

| 规模 | 端到端预计 |
|---|---|
| 1,000 提交 | 约 22 分钟 |
| **1,340 提交** | **约 30 分钟** |
| 12,600 提交（全仓） | 约 4.7 小时 |

**内核 0.047 秒/提交 对 端到端 1.34 秒/提交，差 28 倍。** 整个任务的耗时几乎全在解析阶段，不在特征内核。

#### 瓶颈定位

`packages/repositories/parser.py`：

- 第 152-156 行 `blob()`：**每个 blob 起两个子进程** —— `git cat-file -s <sha>` 取大小，再 `git cat-file blob <sha>` 取内容
- 第 245 行 `files()`：每个文件同时读**新旧两个 blob**，于是**每文件 4 次**子进程
- 第 159 行 `record()`：每个提交再起一个 `git cat-file commit`

ActiveMQ 平均每提交 **6.22 个文件**，于是每提交约 `1 + 6.22 × 4 ≈ 26` 次 git 子进程。实测 1.34 秒/提交，即**每次子进程约 52 ms**，与 Windows 进程创建开销量级一致。

**结论：瓶颈是子进程开销，不是计算量。**

还有一层放大。`command()`（第 88-124 行）每次调用都会：把 stdout/stderr 重定向到文件 → `subprocess.Popen` → **用 `time.sleep(0.02)` 轮询 `process.poll()`**，且每轮都调 `self.tick()`，而 `tick()` 里有 `shutil.disk_usage` 磁盘检查。于是每次子进程都额外叠了文件 I/O 与每 20 ms 一次的磁盘统计。

优化方向（属产品代码，需另开 `openspec/changes/`）：

1. 改用 `git cat-file --batch` 常驻进程，把每提交约 26 次调用压成 1 次流式请求
2. 轮询换 `process.wait()`，去掉 20 ms 粒度空转
3. `tick()` 里的 `disk_usage` 降频（如每 N 次调用查一次）

> 这属于产品代码，不在本决策记录范围内。此处只记录事实与定位；优化需另开 `openspec/changes/`。
>
> 另：这测的是 `NativeReader` 这条路径。`indexed_features.py` 的 v2 加速已在真实仓库上补测：200 / 1,000 / 5,000 / 12,600 提交分别 0.87× / 1.25× / **2.13×** / **1.01×**（相对 legacy）。**v2 在中间规模有效，到全仓规模收益消失**，内核在端到端里始终只占 3.4% 以内。无论生产走哪条，**解析都是唯一值得优化的对象**。

### 4.2 增长律：真实仓库是 1.71 次方，低于平方

200 → 12,600 提交（63 倍规模），耗时涨 1,197 倍：

```
k = ln(1197) / ln(63) = 1.71
```

各区间局部指数在 1.34 ~ 2.18 之间波动，整体 **k ≈ 1.71**。低于平方的原因是 ActiveMQ 历史是带合并的 DAG，一个提交的祖先集合远小于"它之前的所有提交"，`ancestry()` 的集合去重吃掉了共享部分。

**与合成探针的对照很关键**：合成给出 k = 2.06~2.43，真实只有 1.71。**合成数据会系统性高估大 N 的耗时，不能用它定上限。**

按 k = 1.71 外推（从 12,600 实测点出发，仅 1.9 倍）：

| 提交数 | 耗时 |
|---|---|
| 12,600 | 586.7 s（**实测**） |
| 24,000 | 约 30 分钟 |
| 30 分钟预算 | **约 24,000 提交** |

内存 5,000 → 12,600（2.52 倍规模）只涨 1.94 倍，**次线性**；按此外推 24,000 提交约 **137 MiB**。内存不是主要约束，但到万级提交已是百 MB 量级，必须计入容器/Worker 的内存限额。

### 4.2.1 两套探针的口径差异（引用时必须说明）

| | 合成 `scripts/probe_features.py` | 真实 `probe/probe_real.py` |
|---|---|---|
| 历史形态 | 线性链，每提交 1 文件 | ActiveMQ 真实 DAG，平均 6.22 文件/提交 |
| 覆盖 | full | full |
| `old_loc` | 真实 | **占位 1**（blob 读取不计入内核） |
| 窗口 | 从头构造 | 拓扑序**最老**的 N 个，保证祖先闭包；N=12,600 即全仓 |

`old_loc` 占位意味着 **`LT` 的值不可用**，但 `LT` 不参与任何循环，耗时与内存结论不受影响。

### 4.3 为什么 13,491 不能直接用

1. 那个数是在**简化版内核**上测的（`probe/probe_perf.py`，14 维只算对 6 个）
2. 它是按「毫秒/提交」线性除出来的，而真实增长是 1.71 次方，**不能线性折算**

### 4.4 这套数仍然不能作为最终结论

三个限制，都必须写进任何引用它的地方：

1. **小 N 的点有窗口偏移**：为保证祖先闭包，N < 12,600 时取的是拓扑序**最老**的 N 个提交，也就是 ActiveMQ 2005 年前后的早期历史，文件规模与近年不同。**只有 12,600 那一行是完整无偏的**
2. **`old_loc` 是占位值**：`LT` 不可用，但如上所述不影响耗时结论
3. **不含解析阶段**：Git blob 读取、二进制与编码判定在生产的解析阶段完成，不在内核计时内。实际端到端耗时会高于本表
3. **真实 Git 探针仍未跑成**：`scripts/probe_causal_features.py` 需要完整依赖（至少 `dnspython`），而 `.venv` 目前只有标准库（`ensurepip` 未成功）；它的 `--commits` 上限还写死为 1,000，要测 5,000/10,000 必须先改代码

### 4.5 待补证据

- **换机器重测**：旧记录在同一代码同一解释器下慢 2.3 倍，说明耗时强依赖硬件；上生产机前必须重测
- **第二个真实仓库**：1.71 次方是否稳定，需要 commons-cli 或其他仓库验证
- **窗口偏移**：小 N 的点取自早期历史；若要评估近年提交的单提交成本，需改成「最近 N + 完整祖先闭包」（祖先也要进快照，成本另计）
- **端到端耗时**：本表不含解析阶段（blob 读取、二进制与编码判定），实际端到端会更高
- 与存储预算联动：命令必须带 `-ExpectedGrowthGiB`

## 10. 落地状态

2026-10-30 这一批把已经定下来的取值落进代码，落地项与落点如下。对应的规格与任务在 `openspec/changes/apply-probe-parameter-defaults/`。

| 参数 | 落地取值 | 落点 | 状态 |
|---|---|---|---|
| 标签观察窗口 W | 默认 180 天 | `packages/mining/dataset.py` 的 `WINDOW_DAYS`，由它供 `Policy`、`DatasetSource._load`、`scripts/audit_dataset.py` 与 `ReplayPolicy.horizon_days` 四处使用 | 已落地，四处同源 |
| W 的标定阈值 | 目标覆盖率 70%，即容忍误标率 30% | `probe/probe_coverage.py` 的 `DEFAULT_TARGET`，并新增 `--target` 与 `--repo` 参数，直接输出该仓库的 W* 与右端代价 | 已落地 |
| 输入上限 | 700 提交 | `packages/repositories/parse_policy.py` 的 `COMMIT_LIMIT`，由 `apps/api/repositories.py` 的解析请求上界引用 | 已落地，提交窗口改为一对互斥字段 |
| W 按仓库标定结果 | ActiveMQ 790 天、commons-cli 280 天 | 由覆盖率探针按目标 70% 现算出，写入数据集策略快照后才生效 | 未落地，标定仍是人工取点 |

两处边界要写清楚，避免把落地理解得比实际宽：

- **提交窗口必须显式二选一。** 要么给 1 到 700 的条数，要么显式声明解析全历史，两者互斥，都没给出直接拒绝。原来"留空即全历史"的约定已取消，因为运行时用例和界面默认都在留空，那等于把全量解析当成默认路径。
- **自动标定没实现。** 探针现在能一条命令算出 W* 与右端代价，但从"算出来"到"写进策略快照"仍是人工一步。

取值依据：按 30% 容忍率标定，ActiveMQ 需 790 天、右端代价 6.2%，commons-cli 需 280 天、右端代价也是 6.2%，两个仓库的代价在这一档刚好相等；收到 25% 就变成 9.2% 与 14.1%，再收紧对小仓库不成比例，所以 30% 是能用的下界。完整对照可用 `probe/probe_coverage.py <gaps.csv> --repo <bare> --target <覆盖率>` 现算。
