# NFR-03 在线压测报告（2026-11-06）

## 1. 结论

常用列表查询与历史风险列表在演示数据量下达到验收计划的要求：串行一百次请求里最慢的接口 P95 为 87.57 毫秒，四并发下最慢的接口 P95 为 268.59 毫秒，两者都远低于 1 秒，错误率为零。

验收计划点名的另一条链路是候选预测，而当前代码里没有这个接口，探到的两个候选路径都返回 404。因此 NFR-03 这次只完成了一半：列表与风险列表的 P95 有证据，候选预测的 P95 仍然缺，缺的原因是接口不存在而不是测不出来。

这次结果只说明延迟，不说明模型效果。被测模型训练在工程夹具上，ROC-AUC 达到 1.0 是夹具按线性边界生成标签的必然结果，不能当作缺陷预测能力。

## 4. 方法

压测脚本是 `scripts/probe_latency.py`。对每个目标接口先发 5 次预热请求，再发 100 次计量请求，串行与四并发各跑一组，两组分别汇总。

有效请求要同时满足三条：状态码 200、响应体是 JSON 对象、包含该接口约定的关键字段。缺任一条就计入错误率并剔出分位数样本。

分位数用最近秩法在有效样本上计算，P95 取第 95 百分位对应的实际观测值，不做插值。

原始记录逐请求一行，写进 `probe/out/latency_nfr03_raw.csv`（1,470 条计量记录加表头）。汇总与环境、数据量、模型版本一起写进 `probe/out/latency_nfr03_summary.json`，本报告的表格从这份 JSON 抄录。

## 6. 判读

历史风险列表是这批接口里最慢的一个，串行 P50 约 71 到 76 毫秒，比列表接口高一个数量级。原因写在实现里：每次请求都重新读一遍 6,000 行的概率工件并逐行解析，没有缓存，也没有把结果落到数据库。这个代价随工件行数线性增长，行数上限是 20,000 行，因此最坏情况大约是三倍于本次数量级。本次仅验证当前数据量下达标，没有验证上限处的表现。

数据集列表串行 P50 约 73 毫秒，比模型列表慢，主要是因为响应里带每个数据集的摘要对象，序列化开销大；四并发下它的 P95 涨到 241.78 毫秒，是并发组里第二慢的接口。

四并发组的 P50 普遍是串行组的 3 到 4 倍，符合单进程 uvicorn 加同步阻塞处理的预期。这一组数值不能当成容量结论，它只说明在演示规模下四路并发仍然全在 1 秒以内。

吞吐是按每组实际墙钟时间算出来的有效请求速率，单接口视角，不含多接口混合的场景。

## 7. 复现

```powershell
# 建演示数据集与一次模型运行（需要可用的 MySQL 与 Redis，账号口令由本机环境变量提供）
.\.venv\Scripts\python.exe scripts\seed_demo_dataset.py --rows 6000

# 串行与四并发各一百次，写原始记录与汇总
.\.venv\Scripts\python.exe scripts\probe_latency.py `
  --base-url http://127.0.0.1:18000 `
  --run-id e300d428-6577-44c4-991d-3359aaefb027 `
  --requests 100 --warmup 5 --concurrency 1 --concurrency 4 `
  --csv probe\out\latency_nfr03_raw.csv `
  --json probe\out\latency_nfr03_summary.json
```

登录口令从 `DG_BOOTSTRAP_USERNAME` 与 `DG_BOOTSTRAP_PASSWORD` 读，脚本不把令牌写进记录。

重跑建数据脚本会得到新的数据集与运行编号，本报告固定的是这次那一组的编号；数据规模、切分比例、算法与超参数都由脚本参数与默认值定死，因此重跑的数字应当在同一量级，但不会是同一条记录。

建数据脚本用的夹具自述不是真实采集，能力位里候选发布为假，因此用它的运行可以读风险列表，但发布成候选模型会被拒绝，这一点与本次实测一致：发布请求返回 409 与 `MODEL_PURPOSE_INCOMPATIBLE`。

## 8. 与容器环境的差异

`compose.yaml` 起的是一组容器：MySQL 8.4、Redis 7.4、API 与 Worker 在 Linux 镜像里、前端由 nginx 提供。本次是 Windows 上的直连进程：MySQL 8.0.41、Redis 5.0.14、uvicorn 与 Celery 在宿主解释器里、前端用 Vite 开发服务器。

两边的内存参数对齐了数据库的 128 MiB 缓冲池与 Redis 的 128 MiB 上限，但没有对齐操作系统与文件系统差异。因此本报告的数字属于本机 Windows 环境的观测，不能替代容器环境下的复测；反过来，容器环境下的数字也不能替代本机这份记录。
