## 1 设计目标

界面应让用户清楚区分数据事实、模型结果和系统状态。任何风险分数都必须同时展示模型版本和限制说明；任何长任务都必须提供进度、终态和可行动错误。

首期以可用、可测试的响应式 Web 界面为目标，不把高保真视觉效果置于核心链路之前。

2026-10-09 第五阶段在 `wang` 已实现 /login、/tasks、/tasks/:id、/health。access/CSRF 仅在内存，整页刷新重新登录后返回原任务；列表每页 10 项、轮询及错误恢复，详情支持取消/后继重试。此段记录第五阶段当时状态；当前仓库/解析/同步/Fix/SZZ/特征质量页面已实现，数据集、模型和评审页面仍待实施。当前运行与验收见 [页面说明](development/页面使用与质量验收.md) 和 [第五阶段报告](reports/2026-10-09-第五阶段页面与持续验收报告.md)。

## 4 全局交互规则

- 导航只显示当前角色可访问入口；后端仍必须独立鉴权。
- 所有列表支持加载、空数据、错误、无权限和分页状态。
- 长任务创建成功后跳转或链接到任务详情，不用持续阻塞请求。
- 错误信息包含可行动建议和 `request_id`，不显示内部堆栈。
- 删除、发布模型、修改角色等高影响操作要求确认，并明确对象和后果。
- 标签、特征、数据集、模型和预测页面均展示对应版本标识。
- 成熟缺陷标签与模型预测不得使用相同图例或名称混淆。
- 风险等级除颜色外必须有文字或图标，不以颜色作为唯一信息载体。

## 5 核心流程

### 5.1 历史数据 MVP

```mermaid
flowchart LR
    A[仓库列表 添加仓库] --> B[任务详情 克隆解析]
    B --> C[仓库详情 Fix证据]
    C --> D[SZZ证据与标签]
    D --> E[特征质量]
    E --> F[创建时间数据集]
    F --> G[训练 LR RF]
    G --> H[指标与历史风险列表]
```

页面必须允许从任一阶段定位前置结果和失败原因，禁止只显示“处理中”而无阶段、心跳或数量。

### 5.2 合入前评审

```mermaid
flowchart LR
    A[选择仓库] --> B[填写 base 和 candidate]
    B --> C[校验 ref 或 diff]
    C --> D[运行预测]
    D --> E[风险队列]
    E --> F[解释和文件下钻]
```

预测提交前显示所选模型、特征版本和输入限制；结果页明确“用于安排审查顺序，不是自动合并或拒绝结论”。

## 7 页面状态和错误

每个核心页面至少实现以下状态：

- 首次加载 skeleton 或明确加载指示；
- 无数据空态，并提供下一步操作；
- 可恢复错误，提供重试；
- 输入错误，定位到具体字段；
- 任务失败，展示安全化摘要和 request/task ID；
- 权限不足，说明需要的角色但不泄露资源详情；
- 版本不兼容，展示实际版本和期望版本。

## 8 可用性与无障碍

- 键盘可以完成表单、筛选、分页和主要操作。
- 表单字段具有可关联标签，错误与字段绑定。
- 表格在窄屏允许横向滚动，并固定关键身份列。
- 图表同时提供图例、数值摘要或可访问表格。
- 状态颜色满足对比度要求，并辅以文字。
- 删除、取消、发布等按钮使用明确动词，禁用状态说明原因。

## 9 前端验收重点

- API 状态与页面状态一致，不用前端猜测任务终态。
- 请求竞态不会让旧响应覆盖新筛选结果。
- 重复点击写操作不会创建重复任务。
- token 失效有一致处理，登出后旧会话不可继续访问。
- 数值格式、时区、概率、百分比和缺失值展示统一。
- 测试同时覆盖正常、空态、异常、权限和版本不兼容场景。
