## 3 已确认的产品边界

产品同时服务两条核心链路：

1. 历史分析：仓库采集、Fix 证据、SZZ、特征、数据集、训练、评估和历史风险结果。
2. 合入前评审：对未合入默认分支的 commit、branch 或 diff 进行预测、解释与风险排序。

模型只提供辅助排序，不自动替代人工评审，不宣称概率代表确定缺陷，也不把 SHAP 描述为因果根因。

## 5 必须覆盖远程旧规格的纠偏

### 5.1 Fix 证据

远程旧规格中“提交消息出现 Issue ID 即标记为缺陷修复”的规则作废。最终规则为：

- 托管平台 Issue 被确认是 bug 且存在修复或关闭关系时，作为高等级证据；
- 带边界的缺陷修复关键词作为可配置的中等级证据；
- 只有普通 Issue ID、模糊词或回滚时，不自动判定为 Fix；
- 保存证据类型、值、规则版本、置信级别和人工复核状态。

### 5.2 SZZ 与标签

- 首期实现称为 baseline SZZ；未实现可靠重构检测前不得称为 RA-SZZ。
- 必须保存 Fix 提交、文件、修复行、blame 行和候选引入提交的行级证据。
- 引入 `buggy`、`clean`、`unknown`；年龄不足观察窗口或证据不足的提交为 `unknown`。
- `unknown` 不进入监督训练。

### 5.3 防泄漏与评估

- 所有历史特征只能使用当前提交发生前的数据。
- 时间顺序划分默认 70%/15%/15%，具体边界写入数据集记录。
- 填充、缩放、词表、采样只在 train 拟合；校准与阈值只使用 train/validation；test 只做最终评估。
- Effort 统一为 `LA + LD`；PofB20 不再与同义的 Recall@20%Effort 重复列示。

### 5.4 在线预测

仅对已经合入默认分支的历史提交打分不能满足即时预警。核心能力必须支持 `base_ref + candidate_ref` 或受限 diff 输入，并保证候选特征的历史部分截止到 base 时点。

## 6 分支与协作决策

- `main`：由维护者负责合并和维护，本开发流程不管理或判断其发布资格。
- `wang`：当前开发维护分支，其有效规格、规划与已验收实现为用户指定团队同步标准；不是其它分支已同步的声明。
- `feature/<us-id>-<slug>`：从 `wang` 创建的短生命周期功能分支。
- 当前允许直接在 `wang` 小步提交；需要拆分功能时可使用从 `wang` 创建的短期分支。
- 本阶段只推送 `wang`，不修改 `main` 或其他分支；后续是否合入 `main` 由项目维护者另行决定，不属于当前个人开发任务。
- 不再新增长期 `develop` 分支，避免与 `wang` 职责重叠。
- 合并前至少一位非作者审阅，并保存 PR、测试与 OpenSpec 证据。

## 7 允许通过实验确定的参数

以下参数不改变产品和架构基线，可在对应 OpenSpec change 中通过探针、数据探索或测试确定：

- 最终演示仓库和提交窗口；
- 标签观察窗口 `W`；
- Fix 关键词、Issue 集成方式和证据阈值；
- Naive Bayes 具体实现；
- TextCNN 词表、截断长度和训练规模；
- 性能测试硬件、数据量及并发口径；
- 后期是否从本地工件存储迁移到 MinIO。

参数确定后必须记录版本、依据和影响，不得事后使用测试集结果调参。
